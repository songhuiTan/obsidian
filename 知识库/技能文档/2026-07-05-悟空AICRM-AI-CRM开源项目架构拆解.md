## 文章概述

深度拆解开源项目 **悟空 AICRM**（"开源版 Salesforce + ChatGPT"），从代码层面分析 AI 到底怎么跟 CRM 结合。项目走"对话即工具"路线（Spring AI），而非"Agent 工作流"路线（LangGraph）。

**GitHub 仓库**：https://github.com/WuKongOpenSource/Wukong-AICRM

**技术栈**：Java 21 + Spring Boot 3.3 + PostgreSQL + Vue 3，AI 层基于 Spring AI

---

## 核心发现：AI 没有替换 CRM，而是在外面包了一层"对话层"

传统 CRM 功能全部保留（客户表单、任务看板、日历视图），AI 在旁边加了一个对话入口。两种入口并行。

### 新增 AI 功能
- 对话式 CRM 操作（LLM → Tool Call → Service）
- 知识库 RAG（上传文档 → Embedding → 向量检索）
- AI 任务/日程创建、邮件待办提取、会议纪要生成、简历解析
- 语义搜索（自然语言搜索客户/联系人/知识库）
- AI 计费额度管理（token 计量 + 双桶计费）

### 保持传统的功能
客户/联系人/产品 CRUD、跟进记录、任务看板、日历、项目管理（Kanban）、文件管理、RBAC 权限、组织架构、报表仪表盘

## 五个关键架构设计

### ① 多租户 + AI：每一层都有租户隔离
- 数据层：`TenantLineInnerInterceptor` 自动加 `tenant_id`
- AI 层：每个租户独立配置模型供应商、模型名称、参数——一个用 DeepSeek，另一个用通义千问
- 传统 CRM 多租户只隔离数据；AI CRM 的多租户还要隔离模型配置

### ② AI 动态构建，非硬编码
- `DynamicChatClientProvider`：每个请求来了，查当前租户配置 → 现场搭 ChatClient
- 切换模型无需重启服务
- 坏处：每次请求多一次配置查询（Redis 缓存可忽略）

### ③ 对话应用（ChatApplicationRegistry）
- 7 种对话应用：通用助手 / CRM 管理 / 产品 / 项目 / 知识库 / 通讯录 / 关系人
- 切换应用 = 换一组系统提示词 + 换一组可用工具
- 新增对话场景：registry 加一行注册就行，不改核心代码

### ④ 工具调用是 AI 操作 CRM 的唯一入口
- 14 个工具组覆盖所有 CRM 操作
- AI 不走数据库直连，所有操作通过 `@Tool` 接口走正常 Service 层
- 权限校验、租户隔离、数据校验一个不落
- **原则**：AI 不是绕过系统访问数据，是通过规范的工具接口访问数据

### ⑤ 双桶计费
- 赠送额度 + 购买额度，先扣赠送再扣购买
- 调用前预检额度，结束后按真实 token 扣减
- 不同模型按定价倍率折算 credits

## 架构范式对比

| 维度 | 对话即工具（悟空路线） | Agent 工作流（LangGraph） |
|------|----------------------|-------------------------|
| 复杂度上限 | 低。简单链路可靠 | 高。可拆多个节点 |
| 可调试性 | 差。LLM 决策路径不可控 | 好。路径在代码里定义 |
| 扩展新场景 | 快。加一个工具即可 | 慢。需要设计子图 |
| 适用场景 | 查/建/改/删操作 | 多步审批、条件分叉 |
| 状态管理 | 每个请求独立，prompt 窗口内 | 可持久化状态 |

> CRM 当前场景不需要有向图——对话交互模式很固定。但如果要做"自动销售流程"（客户超期未跟进 → 自动提醒 → 分配任务 → 超时升级），LangGraph 式架构就有必要了。

## MCP Server

项目自带 285 行 MCP Server，9 个只读工具，通过 stdio 协议暴露。可在 Claude Code 里直接查 CRM 数据。

设计克制，只做只读查询不做写操作——"不是把 AI 搬到 CRM 里，是把 CRM 数据搬到 AI 的工具箱里"。

## 可取设计 & 待改进

### ✅ 可取
- Provider 抽象层支持 8+ 模型供应商，关键词匹配自动推断模型能力
- 双桶计费 + token 估算，AI 成本可管理
- CLAUDE.md 700+ 行，极其详尽

### ⚠️ 待改进
- Prompt 在代码里硬编码，业务人员改 prompt 需找开发改代码
- 没有 A/B 测试机制，换模型靠直觉
- 上下文管理不透明，无明确截断/summarize 策略
- 没有状态持久化，跨步骤中间结果无法保存

## 与我当前生态的关联

- **MCP 设计参考**：285 行只读 MCP Server 的克制设计，可借鉴到 Hermes 的 MCP 工具设计中
- **工具调用即 ACL**：AI 只通过 `@Tool` 接口访问数据——这与 Hermes 的 tools/技能系统设计理念一致
- **对话应用多租户**：每个租户独立模型配置的思路，对多环境 Hermes 部署有参考价值
- **"对话即工具"vs"工作流即 Agent"** 的决策框架：对判断何时上 Hermes 的 `delegate_task`/多 Agent 编排有帮助
