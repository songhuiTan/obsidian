# Anthropic 最新拆解：Always-on Agents（常驻智能体）的完整落地思路

> **核心命题**：Always-on（永远在线）是**面向用户的体验**，不是底层程序的真实运行状态。大部分时间 Agent 处于休眠，只有被事件唤醒才短暂完成一轮工作，保存状态后再次休眠——以此实现跨会话的自主工作能力。
>
> 原文参考：<https://claude.com/resources/articles/building-always-on-agents>

## 为什么现在才谈落地

随着大模型推理成本持续下降、长周期任务判断力提升，常驻式 Agent 正从概念走向产品。文中给出的关键数据：**在长周期编码基准测试中，Opus 5.5 完成单任务的成本相比前代 Opus 5 降低 78%**（文章口径，未独立核验），让跨小时、跨天的长任务具备商业可行性。

但自主运行、无人看管的 Agent 会集中暴露四类工程问题：

- 事件丢失
- 状态错乱
- 权限失控
- 消息轰炸用户

Anthropic 的解法**不是写一套复杂的提示词**，而是用 5 套解耦的基础组件搭运行框架：

| 组件 | 职责 |
|------|------|
| **事件收件箱（Event inbox）** | 统一唤醒中枢，隔离所有触发源 |
| **定时器（Timers）** | 跟进提醒 + 周期调度，制造主动性 |
| **持久记忆（Memory）** | 跨多次休眠保持连续性 |
| **权限管控（Permissions）** | 无人值守场景的风险闸门 |
| **消息发件箱（Outbox）** | 把控输出、限流降噪 |

## 一、真实工作循环：Run 是原子单位

普通对话 Agent 的生命周期极简：用户发消息 → 模型响应 → 会话结束。

常驻 Agent 的原子单位叫 **Run（运行轮次）**：收到触发事件 → 执行任务 → 持久化全部状态 → 休眠。所有工作被切成一次次短暂的 Run，Run 被包裹在 **Session（会话）** 中，会话记录消息与工具调用历史。

![Agent 大部分时间处于 Asleep（no tokens spent）；一个 webhook 抵达后唤醒短暂的 Run：①事件抵达 ②会话开启 ③Agent 主循环运行 ④Run 回写状态，底部为跨 Run 存续的 Stored state](.../assets/2026-11-16-Always-on-Agents/img_002.png)

完整循环：

1. 外部事件抵达（用户消息、webhook 回调、定时时间到）
2. 唤醒 Agent，开启或接续已有会话
3. 执行 Agent 主循环，调用工具、思考决策
4. 把任务进度、记忆更新写入持久化存储
5. 输出结果或等待用户审批，随后再次休眠，等下一次唤醒

**精髓一句话**：把连续的长任务拆成无数次离散的短时运行，**依靠外部存储保存全部中间状态，而不是依赖模型上下文窗口记住一切**。真正的计算只发生在 Run 的一瞬，其余时间不消耗任何模型资源。

## 二、事件收件箱：统一的唤醒中枢

普通 Agent 多由用户消息直接触发；常驻 Agent 把所有触发源**隔离**——用户输入、第三方 webhook、后台任务完成通知——全部先投递到收件箱，而不是直接调用 Agent。

![事件收件箱结构：外部事件经 Handler 快速写入持久化事件表，后台 Worker 扫描待处理事件后触发 Run，保证崩溃可恢复、事件不丢失](.../assets/2026-11-16-Always-on-Agents/img_003.png)

收件箱本质是一张数据库表，三件基础部件：

| 部件 | 作用 |
|------|------|
| 持久化事件列表 | 数据库表，保存每条事件的发生时间、内容、会话关联 ID、执行状态 |
| HTTP 处理接口 Handler | 接收外部事件后**快速写入**数据表 |
| 后台工作进程 Worker | 持续扫描待处理事件，触发 Run |

解决的工程痛点：

- 避免多事件同时到达造成并发冲突
- 系统崩溃不丢事件，Worker 重启后重新拾取未完成任务
- 支持事件去重，防止重复执行
- 多条连续消息可合并成单次 Run，避免频繁重复应答

**最佳实践**：Handler 要快速应答，复杂校验放到 Agent 运行阶段；收件箱作为唯一事实来源；**同一收件箱同一时间只允许一个活跃 Worker**；短时间连续到达的多条事件合并为一轮（用户连发多条，Agent 只回一次）。

## 三、定时器：主动性的来源

收件箱处理外部事件，定时器负责两类主动任务：

- **跟进提醒（Follow-up）**：Agent 给自己设的时间点，如"一小时后检查对方是否回复邮件"
- **周期调度（Schedule）**：用户预设的重复任务，如每天早 8 点生成业务简报

![定时器不直接启动 Agent：Scheduler 轮询扫出到期定时器，更新记录（一次性标记完成／周期性推进下次时间）后向事件收件箱写入一条事件，再由 Worker 正常唤醒 Run](.../assets/2026-11-16-Always-on-Agents/img_004.png)

定时器**独立存放在另一张表**，不与收件箱混在一起。定时器本身不直接启动 Agent，而是由调度后台服务 Scheduler 轮询：

1. 找出所有到期定时器
2. 更新记录（一次性跟进标记完成；周期性任务更新下次执行时间）
3. 向事件收件箱写一条事件，由 Worker 正常唤醒 Agent

可自研调度服务，也可直接选用成熟的持久化执行引擎。

## 四、记忆：跨休眠的连续性

Agent 反复休眠、上下文窗口反复重置，记忆系统就是它的**外置大脑**。记忆同样独立持久存储（数据库或对象存储），脱离 Worker 进程生命周期。

**设计原则：记忆只保存无法再次查询获取的信息。** 若业务系统已有数据，记忆里只存指向数据源的指针，不要重复拷贝完整数据。

记忆文件分四类：

| 类型 | 作用 |
|------|------|
| **用户指令** | 用户设定的行为规则，**每次 Run 启动都必须加载**；用户不在场时，这套规则约束 Agent 行事方式 |
| **用户笔记** | 沉淀的偏好、角色、过往修正建议。量大时只加载索引，需要细节时按需读子文件 |
| **历史消息记录** | 记录已输出过什么，避免重复推送相同信息 |
| **任务进度文件** | 每个进行中任务一份进度文档，记已完成步骤与待办；新 Run 读取即可接续，无需全部重新推理 |

对应到具体落盘（见下图）：`instructions.md`（每次必加载）、`index.md` + `notes/` 子文件（笔记索引 → 按需展开）、`reported.md`（已推送过什么）、`progress/`（每任务一份进度）。

![记忆分层与落盘结构：用户指令 instructions.md 每次 Run 必加载；用户笔记 index.md 索引 + notes/ 子文件按需读取；历史消息 reported.md 记录已推送内容；任务进度 progress/ 每个进行中任务一份文档](.../assets/2026-11-16-Always-on-Agents/img_005.png)

**梦境（dreaming）机制**：Agent 空闲时复盘历史会话，提炼更新记忆、淘汰过时信息、挖掘跨会话模式。

上下文窗口是稀缺资源——每轮启动都要加载系统提示词、工具定义、基础记忆，这部分**固定开销建议用提示缓存降本**。会话过长时压缩历史消息或新建会话，**需长久留存的内容必须落地记忆，不能只靠上下文窗口**。

## 五、权限：无人值守的最大风险点

这是整个架构风险最高的模块。Agent 后台自主运行并掌握各类系统访问权限，一旦失控后果严重。三层安全机制：

| 机制 | 做法 |
|------|------|
| **凭证代理模式** | 密码、访问令牌等敏感凭据**不交给 Agent**。Agent 只发起不带密钥的请求，由外部代理组件注入真实凭证再转发。Agent 永远接触不到密钥 |
| **自动模式 Auto-mode** | 用分类器识别高风险动作、拦截危险行为、引导 Agent 找更安全方案。但**最高风险的决策仍必须交人类审核** |
| **延迟工具调用 Deferred tool calls** | 遇到需用户确认/补充信息的操作，Agent 终止本轮 Run、保存会话状态、发起审批请求。用户回复作为新事件进收件箱，唤醒 Agent 恢复会话。等待期间 Worker 可处理别的事件，不整体阻塞 |

![权限三层防护：敏感凭据由外部代理注入、Agent 不持密钥；分类器在 Auto-mode 下拦截高危动作；需确认的操作转为延迟工具调用，终止本轮 Run 并向用户发起审批](.../assets/2026-11-16-Always-on-Agents/img_006.png)

## 六、发件箱：把控输出，避免轰炸

普通对话生成内容直接流式推给用户；常驻 Agent 多在后台工作，用户不需要看每一步思考，只需要最终结果和关键摘要。

![发件箱与消息投递器：单次运行只产出三种结局——无需通知、发送消息、询问用户；消息进入发件箱表（时间／内容／状态，如 14:10 尚未收到回复·待发送），由后台消息投递器合并限流后推给用户，或经自有界面展示](.../assets/2026-11-16-Always-on-Agents/img_007.gif)

一次 Run 结束只有三种结局：

1. 向发件箱写入待推送消息
2. 判定无需通知任何人
3. 发起延迟工具调用请求用户确认

发件箱与收件箱对称，也是一张表 + 配套 **Dispatcher** 分发服务：

- Agent 产出消息先写发件箱，标记 `pending`
- Dispatcher 决定何时、以何种形式推送给终端用户
- 支持消息限流、失败重试、合并多条通知

简单场景可跳过完整发件箱，只用一个 `send` 工具直发；但**产品化落地尤其是消息降噪、异常容错，完整发件箱架构必不可少**。

一条重要的产品体验准则：Agent 应当**从安静起步，逐步赢得用户的注意力**，配合评估体系找推送频率的平衡点，不要一上来就高频输出。

## 七、整机闭环

![五组件闭环全景（原图为动图）：What starts a run（Timers→Event inbox）→ What a run works with（A run in a session ⇄ Memory / Permissions，可自设 follow-up 回到 Timers）→ What leaves a run（Outbox → The user），用户的回答案为一条事件回到收件箱](.../assets/2026-11-16-Always-on-Agents/img_001.gif)

定时器或外部系统产生事件 → 写入事件收件箱 → Worker 拾取、启动 Run、开启或恢复会话 → 运行之初读取记忆拿到用户指令与任务进度 → 每步工具调用经权限校验 → 完成本轮更新记忆 → 产出消息送发件箱 → 分发到用户。

运行中 Agent 还可设置新定时器，到期又生成新事件回到收件箱；用户回复通知，回复同样作为事件再次唤醒 Agent。

> 每一次 Run 都短暂结束，但这套循环永不停歇。这就是 Always-On 体验背后的全部逻辑：**不是模型永不关机，而是事件、队列、存储、调度组件相互配合，让 AI 仿佛一直在场。**

## 八、Anthropic 自己的两个产品样本

| 产品 | 形态 |
|------|------|
| **Claude Duet** | 常驻型个人 Agent。用户没给任务时自己去查邮箱、日历、账单，判断有没有该做的事；**拥有独立虚拟机和浏览器**，可在用户设备关闭时继续运行；连接数千外部服务，但发消息、付款、签文件前仍需用户批准 |
| **Slack 里的 Claude Tag** | 持续记住频道对话与工作历史，可被 @ 领取任务；也会在"环境感知"模式下主动插入对话，提醒被遗漏事项或跟进停滞线程 |

这两个不是"等你提问才开口"的助手，而是有连续上下文、有自己节奏、在权限边界内主动做事的**在场者**。但 Anthropic 也承认这仍是早期形态：误读对话、误判优先级、个人事务处理偏弱都是真实存在的问题。

## 九、产品落地的四条结论

很多开发者做自主 Agent，习惯把全部希望寄托于模型提示词能力，试图让模型记住几天前的细节、处理并发、处理崩溃重试。但**长周期自主 Agent 的能力上限，很多时候不取决于模型多聪明，而在于外围工程架构**。

1. **不要迷信"模型什么都能记住"**：上下文窗口始终有硬边界，重要状态一定外置到记忆存储，不要全塞进 prompt
2. **自主不等于放任**：无人值守场景安全优先级最高，权限隔离、审批回调不能省略
3. **解耦是稳定性关键**：把触发、运行、记忆、输出拆开，模型调用失败也不会丢事件、丢进度，系统可重试恢复
4. **用户体验要克制**：主动 Agent 最大负面体验就是消息泛滥，发件箱的限流降噪是产品不可或缺的一环

未来会有越来越多产品不再局限"一问一答"的对话范式，转而采用常驻 Agent 范式：后台监听业务变化，到合适时机主动汇报进展，等用户确认后继续推进任务。

## 战略分析

### 与现有体系的对照

这篇文章描述的五个组件，在这台机器的 Hermes Agent 上已经**各自存在，但是散装的**——这是最有价值的判断。逐项对照：

| 维度 | Anthropic 参考架构 | 当前 Hermes 栈 | 差距 |
|------|-------------------|---------------|------|
| 触发（收件箱） | 事件表 + Handler + 单 Worker 扫描，去重合并 | Weixin 消息轮询 + cronjob 定时 + webhook 订阅（`webhook-subscriptions` skill） | 无统一事件表：多来源触发各自调用 Agent，没有去重、没有"同收件箱单 Worker"约束，并发靠运气 |
| 主动性（定时器） | 定时器独立表 + Scheduler 轮询 → 转成事件 | `cronjob` 直接唤起会话，不走队列 | **缺跟进提醒（follow-up）能力**：cron 只能设死时间点，不能"一小时后自己回来查一下" |
| 记忆 | 四类分层：用户指令/用户笔记/历史消息/任务进度 | Memory 工具（2200 字符硬预算）+ TencentDB 四层记忆（L0–L3）+ session_search | 记忆层最厚，但**"任务进度文件"这一层缺失**——跨会话长任务是靠 context rebuild 硬扛，不是读进度文件续做 |
| 权限 | 凭证代理 + 分类器 + 延迟工具调用 | 审批闸门（approval）+ 扫描器拦截 | 有闸门但没有**凭证代理**：API key 走环境变量，Agent 进程可见真凭据 |
| 输出（发件箱） | pending 表 + Dispatcher 限流/重试/合并 | 平台直接回复 + MEDIA 附件 | 无发件箱。长任务完成即推，没有限流、没有"从安静起步"的克制机制 |
| 休眠成本 | Run 之间零模型消耗 | 会话常驻上下文，每轮重发全量历史 | **成本结构最不一致的一环**：Hermes 走的是"长上下文常驻"路线，Anthropic 走的是"短 Run + 外部状态"路线 |

### 最有借鉴价值的一个点

**任务进度文件（progress file per task）**。这是五件套里唯一能力缺口明确、改造代价最小、收益最直接的一项。当前跨会话长任务（比如批量归档、多步重构）续做的机制是记忆 + 会话历史 + 我自己重建上下文，本质是**重新推理**；Anthropic 的方案是每个进行中任务一份进度文档，新 Run 只读文件接上——省 token 且不漂移。

它和已有的 `cognition-ledger` skill 是一回事的不同实现：那个 skill 已经有"长任务认知账本协议"的雏形（多文件、多工具、多轮推理时记账），但目前是**会话内**的账本，不是**跨 Run 持久化**的账本。把它的落盘位置从会话内挪到磁盘上的固定路径，就基本拿到了 Anthropic 这个组件。

### 不建议照搬的部分

- **不要为了这套架构去做"休眠"**：Hermes 是端侧常驻进程（launchd + gateway），模型调用才是成本项，进程不是。Anthropic 的休眠是为云端多租户省算力设计的，在单机场景里引入事件队列 + Worker 扫描反而增加故障面。
- **发件箱的限流可以先不做**：当前的问题是消息太少、太长，不是太多。限流架构在这个规模是过度设计——符合 ponytail 的取舍。
- **凭证代理值得做但不是现在**：它要求一个独立的代理进程持有密钥，改造面覆盖所有 API 调用点，收益是安全等级提升一档。属于"知道有这条路，等有真实的多用户/托管需求再上"。

### 一句话结论

这篇文章的工程价值不在五个组件的名字，而在它把「自主 Agent 的可靠性」从**模型能力问题**重新定义成**队列与状态管理问题**——这个视角转换对当前栈的直接启示是：**长任务的续做不该依赖记忆检索，该依赖一份明确写在磁盘上的进度文件**。其余四个组件，当前栈要么已经有等价物，要么在单机规模下不划算。
