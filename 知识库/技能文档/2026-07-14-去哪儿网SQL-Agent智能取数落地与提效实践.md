## 核心要点

### 背景与挑战

传统取数流程：产运提需求 → 数分沟通 → 排期 → 开发 → 交付，平均每个需求 **1.9 天**。

痛点：
- **查数难**：底表数据体量大、管理混乱、口径不统一、脏数据多
- **取数难**：产运大多不会写 SQL，复杂 SQL 门槛高
- **使用难**：跨平台执行跑数，交互复杂，等待时间长

2024 Q4 国内机票业务数据：人均跑数 188 个，失败率高，P60 耗时长。

### 方案演进：从单体到多 Agent

**阶段一：单体 Agent**
- 将各类知识直接注入 Agent
- 暴露问题：规则遵守不稳定（十条规则只遵守部分）、信息过载、行业黑话理解差
- Prompt 工程优化收效甚微

**阶段二：拆分生成 + 优化 Agent**
- **生成 Agent**：只负责生成 SQL，不关注语法正确性
- **优化 Agent**：格式修正、语法校验、补充默认条件
- 仍存问题：语法问题小概率出现、大量工具单次调用不够、缺少任务规划

**阶段三：引入 React 机制**
- 模型思考 → 调用工具 → 生成 SQL → 语法检查 → 重试/结束
- 设置重试阈值防止无限循环

**阶段四：需求细化 Agent**
- 在生成前增加需求细化 Agent
- 按预定义规则模板对自然语言进行补充细化（查询字段、分组、时间范围、筛选条件等）
- 解决"SQL 是明确的，自然语言是模糊的"问题

**阶段五：意图确认 Agent**
- 发现表达二义性问题（如"昨天积分第二名的代理商"→ 总量 vs 单笔）
- 抽离意图识别模块：对用户问题改写，必要时反问确认
- 意图明确后才进入 SQL 生成流程

### 知识库设计（六个模块）

1. **字段语义**：业务语义相关知识
2. **表结构信息**：表中的字段信息
3. **术语库**：行业黑话和专业术语
4. **模板库**：高频复杂 SQL 的思考模板
5. **表限制条件**：各表个性化的默认限制条件
6. **表关联知识**：多表关联关系

### 迭代机制

Case 集（人工补充 + 日常沉淀）→ 评测 Agent 定时评测 → 生成报告 → 分析问题（知识缺失补知识库 / Agent 问题修 Agent）

### 最终整体架构

```
用户提问 → 追问Agent（清空上下文/修复/追问判断）
  → 问题改写（意图明确，消除歧义）
  → 规则补充（自然语言→接近SQL表达）
  → 知识召回（RAG，关键词+相似度匹配）
  → 生成Agent（参考历史QA生成SQL + 自检）
  → 优化Agent（补充默认条件、语法校验，重试阈值内修正）
  → 执行结果 + 反馈入口
```

### 落地效果

- 流程从 **7 步 → 1 步**，零协作、零等待
- 数分团队不再承接日常取数需求，转向更有价值的数据分析
- **SQL 整体准确率 85%+**

### 经验总结

1. **验证数据准备**：从数据平台反向获取历史实际执行过的 SQL，再补自然语言问题，确保 Case 集贴近真实业务
2. **Single Agent → Multi-Agent**：先单 Agent，遇到问题再拆，不要一开始就拆
3. **展示执行过程**：让用户看到思考、生成、优化等过程，提升等待体验
4. **尽早小范围上线**：AI 项目的问题只有真实用户使用才会暴露
5. **多模型选择**：根据场景选模型，综合成本+速度+效果

### 未来展望

- 从 SQL 生成走向**数据分析决策**
- **业务域自动选择**：通过业务域 Agent 自动判断用户权限和问题归属
- 以 **API 和 Skill** 形式对外提供
- 降低知识库运维成本
