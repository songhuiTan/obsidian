## 一、Agent 在企业中的定位

传统企业软件 = **记录系统**（CRM/ERP/项目管理等）。
Agent 增加了一个新层：**认知与行动层**。

企业软件三层架构：
```
用户入口与交互层
        ↓
  认知与行动层 ← Agent
        ↓
  业务记录层（SaaS）
```

Agent 价值 = 完成的任务数 × 任务价值。

---

## 二、为什么是 AI Coding

Coding Agent 的天然优势：
1. **上下文清晰** — 代码、依赖、配置都在仓库中
2. **工具天然存在** — 终端、文件系统、搜索、编译器、测试框架、Git
3. **验证机制完整** — 编译/测试/运行结果可验证
4. **恢复成本低** — Git 可回滚

> Manus 使用 CodeAct，Codex、Claude Code 延续类似思路。

---

## 三、Workflow vs Agent 选型

| 象限 | 特征 | 推荐方案 |
|------|------|----------|
| 固定流程、规则稳定 | 步骤清楚，异常少 | **Workflow** |
| 专业场景、行动少 | 业务知识重 | **知识工程 + Skill + 知识图谱** |
| 通用复杂任务 | 多轮行动 | **通用 Agent**（Deep Research、Coding Agent） |
| 专业复杂任务 | 专业知识 + 多轮行动 | **业务型 Agent** |

两个核心判断维度：**横轴 — 业务知识专业程度；纵轴 — 行动/循环/工具数量。**

---

## 四、Agent 产品形态

- **垂直能力** → 放进成熟产品（如 CRM 客户分析）
- **通用能力** → 独立产品（统一任务入口）
- **混合结构**：桌面端（本地上下文） + 云端（业务系统） + SaaS（记录）

---

## 五、稳定性问题

生产级 Agent 需提供：
1. **工具链路透明** — 用户看到执行路径
2. **Human in the Loop** — 高风险动作人工确认（发送消息、改数据、删除、支付等）
3. **行为监测与回溯** — 任务日志、工具调用、上下文版本
4. **清晰的成果区** — 对话视图 + 执行过程 + 项目视图 + 成果视图

---

## 六、多 Agent

> 先区分 **产品设计** 和 **技术实现**。

- **产品侧**：用户是否需要认识多个长期 Agent（人事 Agent、财务 Agent、写作 Agent）
- **技术侧**：任务是否需要 Sub-agent 或 Agent Team（并行、隔离上下文、权限控制）

两个关键问题：
1. 用户是否需要长期认识多个角色？
2. 当前任务是否需要多个执行单元协作？

## 七、Agent 技术架构（完整八层）

```
1. Agent Loop          — ReAct 循环，多轮/重试/状态保存
2. Tool 层             — 文件/搜索/浏览器/数据库/企业API/MCP
3. Context 层          — System Prompt/历史/身份/权限/Skill…
4. 编排与会话管理       — 状态保存/历史压缩/上下文窗口/任务恢复
5. Skill 与插件层      — 方法沉淀/业务Know-how/脚本/模板
6. 观测与评估           — Token/调用/时间/错误/反馈/完成率
7. 任务与调度           — 定时/Heartbeat/后台队列/超时/重试
8. 治理层              — 身份/权限/数据范围/审阅/日志/成本/风险策略
```

### Harness 的核心职责

> Harness = 模型外围的一整套运行机制。

- 最小 = 只是 ReAct Loop
- 生产 = Context + Permission + Memory + Hook + Tool + Skill + 状态管理 + 异常处理

调试 Agent 的大量问题出现在 **Harness** 而非模型：
```
- Tool 描述不清晰
- 参数定义模糊
- System Prompt 内部冲突
- Skill 触发条件不准确
- 历史消息污染当前判断
- 某条遗留 Hook 阻挡操作
- 工具结果过长挤占上下文
- 权限信息没有及时更新
```

完整 Trace 链路需要检查：模型实际收到什么消息 → 工具名称和描述 → 模型为何选这个工具 → Runtime 实际执行了什么 → 工具返回了什么 → 下一轮 Context 如何组装 → 哪条规则影响了最终判断。

## 八、Tools

Tool = 可调用能力的说明书：`Name + Description + Parameters + 返回结果 + 错误类型`

设计关注四点：**声明 → 输入 → 执行 → 输出**

- 描述模糊直接影响模型选择
- 参数尽量结构化
- 执行环境处理权限/超时/幂等性
- 结果要方便模型继续判断

> 后端埋藏最多的工作 = 各种 Tools 和 CLI 改造
> 前端最多的工作 = 构建 Skills 生态

---

## 九、Skills

Skill 文件夹结构：
```
skill/
├── SKILL.md       — 任务目标、适用场景、执行步骤
├── references/    — 操作手册、详细资料
├── scripts/       — 可直接执行的脚本
└── assets/        — 模板、样式、可复用物料
```

### Tool、Skill、Pipeline、Agent 区别

| 概念 | 解决的问题 |
|------|-----------|
| Tool | Agent 可以执行什么动作 |
| Skill | 某类任务应该怎样完成 |
| Pipeline | 谁在什么阶段用什么能力完成交付 |
| Agent | 谁长期承担这类任务 |

> Skill 代表能力，Pipeline 代表交付过程。**两者必须配合。**

Pipeline 需要明确：所处阶段 → 谁负责 → 用什么 Skill/Tool → 输入/输出 → 失败处理 → 人工确认节点。

## 十、生产级 Agent 六阶段

```
阶段1：能聊天 → 阶段2：能调用工具(最小Loop)
→ 阶段3：能规划产出成果 → 阶段4：能长时间运行
→ 阶段5：能被治理(身份/权限/审阅/成本)
→ 阶段6：能沉淀能力(Skill/模板/评测集)
```

Demo 通常只覆盖前两个阶段，工程工作在后面四个。

---

## 十一、AI 原生组织四层

1. **Context Layer** — 汇聚完成任务所需的信息
2. **Pipeline Layer** — 任务在组织中的流转（角色/阶段/输入/输出/交付标准）
3. **Skill Layer** — 组织做事方法的沉淀
4. **Agent Governance Layer** — Agent 作为持续运行的执行单元被管理

> 操作系统作为组织总线，人提供 Context，Agent 按 Pipeline 调用 Skill/Tool，结果写回记录系统。

### 业务恢复能力

不同业务容错要求差异大：
- 线上软件业务：恢复能力强（日志/版本/Git）
- 线下/资金/医疗/对外沟通：恢复成本高 → 需要执行前预览、分级授权、沙箱、回滚

---

## 十二、人才需求四维度

1. **基础素质** — 聪明、乐观、皮实、自省
2. **专业能力** — P5功能 → P6模块 → P7产品 → P8产品线 → P9创造业务
3. **业务能力** — 客户、行业、商业链路、共性需求
4. **组织能力** — 推动项目、处理冲突、获得资源、管理预期

### Agent 产品经理 vs 工程师

- **Agent 产品经理**：场景理解、Pipeline 设计、Skill/Tool 定义、评估体系
- **Agent 工程师**：Harness 工程、Tool 开发、Skill 构建、评测自动化

---

## 核心脉络

> 企业怎样让 Agent **长期、稳定地完成有价值的任务**

三条汇合线：
- **架构线**：Loop → Harness → Tool → Skill → Context → Memory → 调度 → 治理
- **业务线**：围绕真实任务设计 Pipeline，明确输入/输出/责任人/交付标准/异常
- **组织线**：重新划分人与 Agent 的职责，调整岗位边界/协作/评价/人才要求

> 先找到值得解决的业务问题 → 搭建可持续交付的系统 → 沉淀为 Tool/Skill/Pipeline/评测集 → 形成组织可复用的生产能力
