# 轻量化业务应用：四步渐进式验证框架

> **一句话**：AI 业务方案向真实环境落地的方法论——用最小工程成本完成核心能力与业务价值验证。通过传统项目与 AI 开发痛点对比，确立四步渐进式验证框架 + 业务执行内核结构模型，避免"过早复杂化导致开发停滞"和"错误前提被快速放大"两大陷阱。

## 一、AI 项目落地困境与传统验证逻辑

**两个核心痛点：**

1. **过度复杂化导致开发停滞**：开发者过早将需求扩展为复杂技术方案（如直接开发 App），未在最开始定义清楚技术可行性、需求共识与价值目标，导致问题耦合无法定位，陷入开发僵局
2. **错误前提被快速放大**：AI 工具大幅降低"想法→编码"的成本，若最初始的前提定义错误，会更快扩散成完整系统，开发进度被卡在证据积累不足上

**传统验证逻辑依然适用：** Demo、POC、原型、MVP 的核心是用最低成本在不同阶段确认特定问题（关键能力、用户路径、需求共识、核心价值），避免直接进入高成本生产环境。

## 二、四步渐进式验证框架

| 步骤 | 目标 | 关键动作 | 退出标准 |
|---|---|---|---|
| **1. 核心能力的最小化验证** | 验证影响准确率和有效性的功能 | 在真实业务流程中抽离核心能力，人工串联验证 | 预先定义的评价标准通过测试 |
| **2. 核心流程的可执行化** | 能力从人工拼凑转为 Agent 可自主运行 | 封装为 Skill/Tool（Agent 工作单元）或 Workflow（程序工作流） | 人工介入下基于明确输入边界可独立完成任务 |
| **3. 轻量应用封装** | 用户能在本地持续跑起并日常操作 | 补充状态管理与用户界面，引入自动化与单机运行能力 | 具备日常操作体验 |
| **4. 真实业务闭环验证** | 端到端跑通并修正设计缺陷 | 接入更多真实场景与上下游节点，验证业务结果与异常处理 | 真实场景跑通，前期设计缺陷被修正 |

## 三、业务执行内核结构模型

### Workflow / Task / Node 三级结构

- **Workflow**：承载端到端目标（SOP 的流程语义）
- **Task**：独立责任单元，含对象输入输出与验收标准
- **Node**：具体运行步骤；支持子流程压缩以增强可维护性

### 三类节点执行主体（含职责迁移关系）

| 主体 | 定位 | 适用内容 |
|---|---|---|
| **人（Human Node）** | 初始任务与兜底决策 | 尽可能减少非必要的语义性评价分配 |
| **大语言模型（LM Node）** | 语义理解、判断与不确定性内容 | 动态修改与用户交互 |
| **程序（Program Node）** | 内部确定性规则与外部连接器 | 需稳定输出的格式处理与状态动作 |

### 执行载体与渐进式固化

- **混合运行模式**：程序 Runtime 控制稳定主干，Agent+Skill+Tool 动态承载未消化的复杂度
- **渐进固化原则**：随业务推进，将确定的规则逐步迁移固化至程序，释放 Agent 处理新不确定性

### 通用运行支撑层（最小化即可）

- **状态存储**：记录业务事实、执行状态与证据；早期可用轻量文件或数据库
- **用户入口**：对话、表单、CLI 等形式供用户查看状态与确认结果；无需追求统一形态

### 业务内核公式

> **一个 AI 应用的业务内核 = Workflow（流程语义）+ 核心提示词（决策语义）+ 业务知识（数据语义）+ 具体行动（行动语义）**

## 四、案例实战：简历投递

1. **现状诊断与目标设计**：针对岗位匹配难复用、投递进度难追踪，重新设计目标流程，明确人机分工——AI 负责数据处理、程序负责数据采集、用户负责核对与决策
2. **核心能力验证**：选取"整理可追溯的岗位匹配判断"与"严格基于经历准备简历材料"两项核心能力，在代表性样本范围内验证成功率与失败兜底策略
3. **可执行结构与轻量封装**：目标 SOP 转化为 Workflow 与 Task 结构；多维表格或简易 Web 页面作为状态存储与用户入口；实现单岗位闭环可操作性
4. **真实闭环与价值评估**：进入真实投递场景采集数据、核对状态、提交反馈，循环中逐步消化复杂度；最终依据"是否稳定辅助替代原有人工环节 + 成本是否接受"决定是否进入下一阶段工程化

## 五、本体数据来源与回流机制

- **咨询阶段沉淀业务语义**：AI 辅助业务咨询过程中，通过录音转写合并事实文档，沉淀有证据支撑的业务理解与建模语义
- **运行阶段抽取执行规则**：真实业务运行中，通过日志与人工修正记录，沉淀判断规则与异常处理标准——为后续构建复杂本体提供高质量数据来源

## 战略分析

**1. 与知识库现有脉络的呼应——这是"AI 项目工程化"的方法论层：**

| 本文概念 | 知识库已有对应 |
|---|---|
| Task 独立责任单元（输入输出+验收标准） | AgentDesk 任务卡（task-card/v2 含 acceptance criteria） |
| Workflow 承载端到端目标 | AgentDesk tasks.yaml 编排 / Hermes Skill |
| 渐进固化（规则从 LM 迁移到 Program） | J-Space"fast/full/loop 分档"的工程化版本 |
| 人机分工（Human/LM/Program） | Buzz 四角色分工（人控主节奏 + Agent 干活） |
| 最小化验证 → 真实闭环 | AgentDesk 四步验证、传统 Demo→POC→MVP |

**2. 最有价值的洞察是"渐进式固化"：** 确定规则从 Agent 逐步迁移到程序——这与 AgentDesk 的"Automated 模式在 Standard 跑通后才启用"同构，也是所有 Agent 系统从"能跑"到"稳定"的必经路径。方法论上它是反过来的：先让 Agent 消化不确定性，把确定的部分抽出来程序化，释放 Agent 能力给新问题。

**3. 业务内核公式的实用性：** `Workflow + 核心提示词 + 业务知识 + 具体行动` 四语义拆解——正好是设计 Hermes Skill 的检查清单：流程语义（Skill 步骤）、决策语义（提示词）、数据语义（业务知识/参考文件）、行动语义（工具调用）。任何新 Skill 可以用这四格自检完整性。

**4. 对用户落地建议：** 如果要做"轻量化业务应用"，最小路径是：挑一个真实高频业务 → 抽 1-2 个核心能力人工验证（步骤 1）→ 封装为 Hermes Skill + 轻量状态文件（步骤 2-3）→ 真实场景跑闭环。不要在步骤 1 之前写任何 App 代码。
