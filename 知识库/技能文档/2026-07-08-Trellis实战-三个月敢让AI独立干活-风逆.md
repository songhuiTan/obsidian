## 概述

AI 编码并非模型不够强，而是**缺了一层脚手架**。每次开新会话都要重新解释技术栈，规则散落在各处，经验无法沉淀——这是当前 AI 编程最大的浪费。

风逆用了三个月 Trellis 后给出的判断。文章不是介绍 Trellis 是什么（另有之前的架构拆解），而是以实战视角复盘：试过的三类方案对比、三层架构的真实体验、3 好 2 坏案例、团队推广落地经验。

## 踩过的三种方案

| 方案 | 代表 | 解决 | 问题 |
|------|------|------|------|
| **流程强化型** | Superpowers（170K⭐） | 单次任务流程约束 | 太重（改文案也要确认三轮）、上下文吃紧、无跨会话记忆 |
| **规格沉淀型** | Spec Kit / OpenSpec | 规范文档化 | 写了不代表 AI 会读、无流程闭环、缺少需求澄清环节 |
| **多 Agent 编排型** | oh-my-claudecode（29 agents） | 复杂任务分工 | 太复杂（29 agents/35 skills/20 hooks/11事件）、绑定特定平台、简单任务过度编排 |

核心差距：三类方案缺的都是同一个东西——**跨会话记忆**。

## Trellis 三层架构实战

### 第一层：Spec 规范层

`./trellis/spec/` 目录按模块分文件，与手写 CLAUDE.md 的三个关键区别：

| 对比维度 | CLAUDE.md / .cursorrules | Trellis Spec |
|---------|--------------------------|-------------|
| 加载方式 | 全量塞入上下文 | **按需加载**，做后端只注入后端规范 |
| 注入方式 | 手动提醒"先读一下" | **自动注入**（Hook 平台在会话启动时注入） |
| 维护方式 | 手动更新 | **自更新**，任务结束后自动检查有无新最佳实践 |

### 第二层：Task 任务层

每个 Task 是一个物理目录，包含完整上下文：

- **prd.md** 明确写：目标、scope 内/外、验收标准——需求从聊天记录搬到了文件里
- **上下文边界明确**：实现阶段读什么、检查阶段对照什么
- **任务生命周期**：Planning → In Progress → Check → Finish → Archived

### 第三层：Workspace 记忆层

**最核心的一层。** 每次会话结束后写 workspace journal；第二天开新会话，AI 先读 journal。

效果：以前开新会话前 20 分钟都花在"让 AI 回忆起来"，现在 AI 读 journal 直接续上思路。

团队场景：踩过的坑、总结的规范写进 spec → 提交 Git → 所有人 AI 受益。**写一次，全队 AI 都学会了。**

## 实战案例：3 好 2 坏

### ✅ GOOD 01：老项目接入，规范从零到有

三年 SaaS 项目接入 Trellis：不自己写 spec，先让 AI 扫描代码库从真实代码提取模式，生成第一版 spec，团队花半天 Review 删掉"想当然"的规则。

效果：之前 Review 指出 5-6 个"不符合规范"的问题 → 接入后通常只有 1-2 个。

### ✅ GOOD 02：团队推广，规范不再靠口口相传

8 人团队，Claude Code / Cursor / Codex 各用各的。`./trellis/spec/` 目录提交到 Git，所有人拉代码即获最新规范。

Review 转变：以前跟新人解释"为什么这么写"→ 现在指 spec 某一条。

### ✅ GOOD 03：修复反复 Bug，治标到治本

SessionStart hook 崩溃 bug（子进程用系统 Python 3.9 vs 用户 3.11）。Trellis break-loop 流程：修 bug → 根因分析 → 沉淀成 spec → 加 check 清单。同样坑不再踩第二次。

### ❌ BAD 01：一开始就想写完整的 spec

花两天填 20+ 模板文件，结果一半是脑补的"理想规范"，跟实际代码对不上。AI 按 spec 写的东西与项目风格不搭。

**正确姿势：** 从真实代码提取，不要预先设计整个体系。空 spec 比没有 spec 危害更大。

### ❌ BAD 02：所有任务都套 Trellis 完整流程

改文案/调样式/加配置也走完整流程——5 分钟变 15 分钟。Trellis 有三种模式（简单对话 / Inline 小任务 / 完整任务），小改动直接 inline。

## 典型场景用法

| 场景 | 策略 |
|------|------|
| **从零新项目** | 先跑起来，边做边补 spec；第 1 周写核心栈 spec（2-3 个文件） |
| **接入老项目** | AI 扫描代码库生成第一版 → 团队 Review → 小需求试点 |
| **交付产品功能** | 跨层次功能，完整闭环：scope → spec → implement → check → update-spec |
| **重构老模块** | 先列"行为不变清单"加 characterization tests → 一次只抽一个职责 → 重构完更新 spec |
| **减少重复 Review** | 收集近期 PR 评论 → 归类重复模式 → 每条规则配 good/bad 示例写进 spec |

## 个人 vs 团队

| 维度 | 个人使用 | 团队使用 |
|------|---------|---------|
| 最大价值 | 会话记忆，不用重复解释 | 规范共享，一人总结全队受益 |
| 核心投入 | workspace journals | spec 库持续维护 |
| 起步成本 | 低，跑两个任务就上手 | 中，需团队达成共识 |
| 见效时间 | 当天感受到 | 1-2 周后 |

## 关键洞察

- **AI 编程的下半场，比的是谁的 AI 更懂你的项目。** 模型能力的差距在缩小，真正拉开差距的是"让 AI 稳定地、持续地、按你的标准输出高质量代码"
- **体感曲线：** 第 1 周变慢 → 第 2 周持平 → 第 3 周开始变快 → 第 4 周明显提速
- 模型是发动机，Trellis 是方向盘+刹车+导航——**它不会让车的马力变大，但能让你敢把油门踩下去**
- Trellis 官方支持 16 个平台，但体验最好的仍然是 Claude Code（Hook 系统最完善）
- AGPL-3.0 协议：用于开发自有项目没问题，但基于 Trellis 做商业产品需评估

## 战略分析

### 与现有体系的对照

| 维度 | Trellis（风逆实战） | 当前知识库已有 |
|------|-------------------|--------------|
| 三层架构 | Spec + Task + Workspace | 已有架构拆解（AI海森 07-07） |
| **新增实战价值** | 3种替代方案对比 + 3好2坏案例 + 团队推广经验 | 无 |
| Spec 策略 | **从代码中提取**，不要预先设计 | 无此实践建议 |
| 任务模式选择 | 三种模式：对话/Inline/完整，小改动不该走完整流程 | 无 |
| 个人 vs 团队 | 双轨策略，workspace journals 是个人核心资产 | 无 |
| 体感曲线 | 第 1 周变慢 → 第 4 周明显提速 | 无 |

### 对当前体系的启示

1. **workspace journal 模式**：Trellis 最核心的设计是每次会话结束后写 journal，第二天 AI 先读再继续。这个"文件即记忆"的模式比完全依赖上下文窗口更可靠——Hermes 的 cronjob + 记忆系统可以借鉴。

2. **Spec 从代码提取而非手动设计**：老项目接入的正确方法是让 AI 扫描代码库生成第一版 spec，而不是人脑补。这个原则适用于任何知识沉淀场景——包括 Hermes Skill 的编写。

3. **三层模式选择**：不是所有任务都值得走完整流程。简单对话 / Inline 小任务 / 完整 Trellis 任务三种模式的分级，可以映射到 Hermes 的"快速问答 / 简单技能 / 复杂工作流"分级。

4. **团队推广经验**：一人总结全队受益是 Trellis 最大的团队价值。当前 Hermes 的 SKILL.md 也是文件化共享的，但缺少自动注入和跨平台统一管理。

### 与 Superpowers 的对比

已在 `Trellis-团队级Agent-Harness框架-拆解vs-Superpowers.md` 中有完整的四维对比。本文补充的关键差异是：**跨会话记忆**——Superpowers 解决的是"单次任务怎么做"，Trellis 解决的是"跨会话怎么积累"。
