# 两个skills把产品经理从PRD中解脱出来

作者分享了两款自制的产品经理 Skill：**PM-Make（产品定型）** 和 **PRD-Make（PRD 写作）**。核心设计理念是：**极致的把 Agent 的作业过程强行分成多个小步骤，最大化利用 LLM 的注意力。**

## PM-Make：把模糊需求变成产品定型文档

适用于产品设计初期：有大概想法、边界不清楚、直接写 PRD 容易越写越散。

### 关键设计

1. **强制初始化作业空间** — 接到需求后先创建 6 个文档：
   - `shaping/00-intake.md`
   - `shaping/01-product-shaping.md`
   - `shaping/02-jtbd.md`
   - `shaping/03-scope.md`
   - `shaping/04-pages-and-flows.md`
   - `shaping/05-open-questions.md`

2. **有信息就填，没信息就留 `[待确认]`** — 刻意让 LLM 不要瞎编。LLM 最大的毛病是太会写了，会把不确定的信息写得很像真的，混进大量未经确认的假设。

3. **分轮澄清，每轮只抛 3-5 个问题** — 一次不能抛太多，需求早期自己也没想清楚，一堆问题反倒制造压力。

4. **答完直接更新文档** — 2-3 轮澄清后生成最终 `06-shaped-brief.md`。

### 产出定型摘要包含

产品定位、目标用户、核心场景、用户当前替代方案、核心价值、MVP 范围、核心流程、页面结构、关键业务规则、仍待确认的问题。

### 定型文档的两个用途

1. **PRD 的基础**
2. **Coding Agent 的提示词** — 作者验证：直接拿 PRD 丢给 Codex 输出稀烂（功能模块又多又细，相互关联影响，Agent 注意力崩溃）。用定型文档做 Vibe-Coding 提示词反而**一稿过**。

> 这个定型文档做 Vibe-Coding 的提示词已经验证完全没问题，我自从使用它作为产品开发需求开始，所有产品都是一稿过。

## PRD-Make：写 PRD，但不让 AI 一次写完

核心策略：**先制定写作模块计划，再按顺序一个一个写完。**

### 两层约束确保模块化

1. 每写完一个模块，更新 `_module-plan.md` 的状态
2. 用户确认后，更新 `_append-log.md` 的确认状态

每写完一个模块就停下来让用户确认、修改或补充，再继续下一个。过程慢一点，但确保 LLM 每轮注意力聚焦在一个板块上，吃满每次请求的 `max_tokens`。

## 作者观点摘录

- 产品经理使用 AI，不应该只聚焦在"生成"这两个字上，更多应该是在理解了原理后的 **"约束添加"**。
- 当 LLM 被塞进 Agent 循环：既要看整体效能提升，又要钻到每一个"断点"里找风险和机会。
- **Skills 是毋容置疑的下一代产品**，就像过去的 PC 应用要有一个移动端 App 一样。
- Agent 的底层虽然是"Loop + Tools"，但它是 **"带脑子的循环"** — "带脑子"改变了规则，循环把"一生二、二生三、三生万物"卷进来了。
- AI 改变的是用户完成任务的方式，它不是大数据、区块链那样的单点技术。
- **如果你不是真的懂 AI，就无法判断哪些任务可以被 AI 改写、哪些体验应该被重构、哪些产品会被 AI 原生产品替代。**

## 获取方式

两个 Skills（PM-Make 和 PRD-Make）打包放在"AI学习行动圈"知识星球。
