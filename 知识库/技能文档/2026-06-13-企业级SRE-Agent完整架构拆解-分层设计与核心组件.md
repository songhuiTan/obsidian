# 第3篇：企业级 SRE Agent 完整架构拆解：分层设计与核心组件

> 六层架构（接入→编排→执行→能力→记忆→可观测），来自真实生产线迭代。

## 一、架构分层的出发点

传统 AI 服务架构经验无法覆盖 Agent 运行态的复杂问题：

- 一次对话调七八个工具，每个可能挂掉
- 用户一条消息，Agent 可能要推理 40 步
- 推理延迟不可控（2s～40s）
- 前端要实时看到 Agent 在想什么、调什么工具
- Token 成本直接可见
- 多 Agent 协作上下文传递容易爆炸
- MCP 协议让工具动态增减

## 二、整体六层架构

### 1. 接入层（用户交互层）

核心原则：**Agent 和通道解耦**。通道只负责"把话送进来、把回复送回去"，Agent 本身是一个独立实体挂在编排层。

同一个 Agent 服务前端 SSE、企微长连接、告警 Webhook、AgentHub。来源打上 `source` 标签（web/wecom/alert/agenthub），不参与决策，仅用于可观测和 Token 核算。

企微是群聊场景按群 ID 隔离，前端是个人会话按 session_id 隔离——不加分层记忆系统会被搞死。

### 2. 编排层（Graph 编排引擎）

三块组件：GraphOrchestrator → FlowEngine → Router

**Router 是核心**：不让每个请求都从头推理一遍。方案是两张协同：

- **场景绑定表**：关键词快速命中（"巡检""健康度"直接落对应场景），70% 请求毫秒级完成路由
- **意图分类 Agent**：未命中才走 LLM 分类，只输出场景标签立刻结束

**HITL Gate 挂载点**：敏感操作在路由层就判断要不要插入人工确认，不是执行到一半弹窗。

FlowEngine 通过 Conditional Edge 分发到执行层——走 Solo、Scenario 还是 Playbook 由 Router 判定。

### 3. 执行层：Solo / Scenario / Playbook 三档引擎

#### Solo（单 Agent 执行）
一个 Agent、一个 LLM、几个 Skill 和工具。占平台 60%+ 流量。集群排障/日志分析/指标查询全是 Solo。关键优势是**快**，8~15 步出结果。最新架构增加了 Solo 模式下 subagent（用完即丢）处理大数据量场景。

#### Scenario（多 Agent 协作）
按场景定义一组角色 Agent（告警接入 Agent、根因推理 Agent、执行建议 Agent）。基于任务下发，每个 Agent 平级接收任务。

**核心挑战是上下文传递**：不全文传递对话历史。做法是**结构化传递**——上游输出 JSON 结构体（问题类型、关键发现、置信度、待确认项），下游只读结构体做推理。自然语言兜底保留。同时有输出围栏做强校验。

#### Playbook（人工审核流）
为敏感操作设计。流程是 DAG，每步要么自动执行要么人工确认。确认节点挂在路由层 HITL Gate。全部执行记录落库可追溯。

**原则**：先 dry-run，再人工确认，再可回滚执行，全过程可追溯。

### 4. 能力层：工具、Skill 与知识库

#### MCP 工具
所有连外部系统的工具走 MCP 协议（K8s 集群/监控/CMDB/CI/CD/工单）。`tools/list` + 懒加载让新增工具只需改 YAML 配置文件 + 入库，不改代码不重启。走 `streamable-http` 运输层。

#### Skill 包
工具是"能调但不知道怎么调"——Skill = 工具组合 + 使用说明书：

- 解决什么场景的问题
- 包含哪些工具
- 每个工具的推荐参数和调用时机
- 标准排障链路（决策树）

Agent 按需加载 Skill（`load_skill`），不占 Token。新增工具只需新增 Skill 描述，不改 Agent 配置。

#### 知识库
定位是**检索增强**不是主记忆。SRE 知识分散/散/乱/旧，直接灌向量库效果差。策略是先做**知识萃取**——原始文档经 LLM 结构化处理再入库：去噪、结构化（"问题-原因-解决方案"）、加标签。

### 5. 记忆层：L1-L4 多模态记忆系统

- **L1 会话缓存**：当前对话完整上下文，跟随请求生命周期，回答完释放
- **L2 语义向量**：历史对话关键片段向量化入 Qdrant，语义检索
- **L3 快照存储**：对话结束后结构化摘要落库（问题、结论、工具链、Token），支持按时间/场景回溯
- **L4 短期记忆**：对话中短期上下文管理——哪些保留、哪些切掉、优先级排序；多 Agent 长任务场景

核心原则：**按需注入**，不是全量塞 prompt。

### 6. 可观测层（竖切面）

#### 三层 Trace（Langfuse）
- Session Trace：每次用户对话
- Generation：Session 里每次 LLM 调用
- Span：Generation 里每次工具调用

映射到前端 SSE 事件流，能算清每一分钱花在哪。

#### Token 看板
按 Agent/场景/时间段分组。每周拉一次，用量翻倍立刻定位到是哪个 Skill prompt 太长、哪个工具返回没截断、哪类问题推理步骤暴增。

#### 结构化日志
每条日志带固定字段：request_id、source、module、caller。request_id 能串起从接入层到工具调用的完整链路。

## 三、为什么是六层

- **编排层和执行层必须拆**：编排负责"判"（什么问题、走哪条路），执行负责"做"（调工具、做推理）
- **记忆层必须独立**：L1-L4 四层记忆不独立成层，长对话必然炸 Token
- **能力层必须独立**：工具/Skill/知识库跟 Agent 绑死，扩展性为零
- **可观测层必须画在图上**：不画出来团队做着做着就不做了
