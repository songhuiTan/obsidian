## 核心论点

> 生产级多 Agent 不是"多个模型协作"的问题，而是"分布式任务系统 + 云原生运行时 + 可治理执行链路"三者合一的问题。

很多多 Agent 系统能演示，不能上线——因为把多 Agent 做成了：
1. 规划、执行、审查全在一个进程内存里
2. 没有状态机，只有函数调用链
3. 共享上下文 → 记忆污染 + 上下文爆炸
4. 高风险工具直接暴露给模型
5. 服务重启/Pod漂移/消息重复后无法恢复

---

## 一、多 Agent 解决什么问题

### 适合场景
- 任务需规划+执行+校验+审批四种角色
- 工具域多（搜索/数据库/监控/工单/代码仓库/审批系统）
- 任务生命周期长，有同步+异步步骤
- 结果触发真实业务动作
- 系统必须支持回放、审计、人工介入、失败恢复

### 不适合场景
- 简单问答或文案生成
- 工具只有一两个且只读
- 单 Agent 状态治理都没做完
- 业务目标未稳定，频繁改角色和流程

## 二、原理：本质不是对话，是任务状态流转

### 四个核心对象
| 对象 | 说明 |
|------|------|
| **Task** | 完整业务任务，状态机的载体 |
| **Step** | 任务中的具体执行步骤，由不同 Agent 承担 |
| **Agent Role** | 规划者/执行者/审查者/协调者等角色定义 |
| **Event** | 状态变化、工具结果、审批回调和异常事件 |

### 多 Agent 比单 Agent 多出的三层复杂度

| 复杂度 | 说明 |
|--------|------|
| **协作复杂度** | 并行探测/结果汇总/冲突裁决/上下文裁剪/失败转人工 |
| **状态复杂度** | 某步骤失败/某角色超时/某工具不可用/某审批未通过/异步回调丢失 |
| **治理复杂度** | 权限/成本/并发/风险/合规 五个边界 |

## 三、架构：四层运行时

```
用户入口 → Agent Gateway
           ↓
     Control Plane  (控制面：做什么、谁来做)
           ↓
     Execution Plane (执行面：怎么跑起来)
           ↓
     State Plane    (状态面：知道自己运行到哪)
           ↓
     Governance Plane (治理面：系统不会失控)
```

### 控制面 — 做什么、谁来做
任务分类/角色分配/执行计划生成/风险级别识别/是否触发审批/模型和工具策略路由

### 执行面 — 怎么跑起来
模型调用/工具执行/多 Agent 任务接力/并发步骤调度/异步任务消费/失败重试与超时收敛

### 状态面 — 系统是否知道自己运行到哪
任务状态机/步骤状态/检查点/事件日志/会话快照/中间结果引用

> 多 Agent 不能依赖内存态。实例漂移/Pod 重建/消费者重平衡时，纯内存状态必然丢失。

### 治理面 — 系统会不会失控
身份与租户隔离/配额与预算/限流熔断降级/审计与回放/工具白名单/高风险动作审批

## 四、状态机设计

### 状态迁移图
```
CREATED → PLANNING → EXECUTING → SUCCEEDED
                           ↓            ↑
                    WAITING_APPROVAL → EXECUTING
                           ↓
                       FAILED
                    TOOL_RETRYING → EXECUTING / FAILED
                    PARTIAL_SUCCESS → ASYNC_CONTINUING → SUCCEEDED / FAILED
                    MANUAL_RECOVERING
```

### 双层存储
- **MySQL/PostgreSQL**：任务真相源
- **Redis**：热点会话状态、短期上下文、流式输出缓存

## 五、工程落地关键

### 5.1 Tool Gateway
工具调用不直接暴露给模型，而是通过 Gateway 统一：权限/参数 Schema/审计/熔断/限流/脱敏/超时

### 5.2 Outbox 模式
状态更新和事件投递必须一致——解决两种不一致：
- 任务状态已写库但消息没发出去
- 消息发出去了但任务状态还没落库

### 5.3 Lease + 幂等
多副本 Worker 下必须补：Lease 抢占/任务版本号/事件唯一键/外部动作执行去重表

### 5.4 编排器职责
> 编排器最重要的职责不是代替 Agent 思考，而是把 Agent 的局部结果推进成全局可恢复的业务状态。

## 六、高并发瓶颈与治理

### 四类瓶颈

| 瓶颈 | 治理方式 |
|------|----------|
| **模型调用** | 模型分级路由/Prompt 裁剪/语义缓存/步数上限/结果缓存/高低配混跑 |
| **工具调用** | Tool Gateway 限流/工具级熔断降级/连接池隔离/大结果分页流式 |
| **状态写入** | 真相源与缓存分层/检查点增量写入/大对象落对象存储/状态表分片 |
| **异步执行** | 优先级队列/任务过期时间/租户级并发配额/Lease 抢占/指数退避/死信队列 |

### 三层并发控制
```go
type ConcurrencyPolicy struct {
    MaxTasksPerTenant  int
    MaxStepsPerTask    int
    MaxParallelTools   int
    MaxAsyncWorkers    int
    MaxTokensPerTask   int
}
```

### 水平扩容最容易忽视的两点
- **上下文粘性**：会话状态必须外置，不能只在 Pod 内存
- **多副本竞争**：重复消费/顺序错乱/状态覆盖/补偿重入 都需要治理

## 七、云原生落地

### 工作负载拆分
1. `agent-gateway` — 入口流量、认证、限流、SSE 会话
2. `agent-orchestrator` — 控制面，规划+状态推进
3. `agent-worker` — 执行面，工具调用+异步任务
4. `tool-gateway` — 统一工具协议、权限、审计
5. `event-dispatcher` — Outbox 扫描与事件投递

### Kubernetes 上必须补的三类治理

**弹性治理：** 根据队列堆积和任务延迟做 HPA，不同优先级 Worker 独立伸缩策略
**隔离治理：** 高风险工具 Worker 独立部署，读写分池，租户凭证隔离
**发布治理：** 蓝绿/金丝雀发布，Prompt 模板灰度，Tool Schema 版本兼容

### KEDA 基于消息堆积弹性伸缩
多 Agent 瓶颈经常是"任务积压"不是"算力跑满"，建议用 Kafka lag 做伸缩触发器而非 CPU。

## 八、可靠性设计

### 三层超时
请求总超时 → 单步执行超时 → 工具调用超时

### 重试策略
| 失败类型 | 是否适合重试 | 策略 |
|----------|-------------|------|
| 上游 429/瞬时 5xx | ✅ | 指数退避 |
| 工具网络超时 | ✅ | 需幂等+上限保护 |
| 模型输出格式错误 | ⚠️ | 先修复提示，限次数 |
| 参数校验失败 | ❌ | 需修正输入 |
| 权限拒绝 | ❌ | 重试无意义 |
| 高风险动作失败 | ⚠️ | 需审批+补偿+人工介入 |

### 审计至少记录
`task_id` / `trace_id` / `tenant_id` / `agent_role` / `prompt_version` / `model_name` / `tool_name` / `tool_request_summary` / `tool_response_summary` / `approval_ticket` / `status_transition`

## 九、预算治理

三层预算：租户日预算 → 用户会话预算 → 单任务步数和 Token 上限

超限策略：降级到低成本模型 / 缩减工具范围 / 只返回建议不执行 / 直接转人工

## 十、生产落地检查清单

| 领域 | 关键问题 |
|------|----------|
| **架构** | 是否区分四层运行时？是否有任务/步骤状态机？是否有高风险审批链路？ |
| **工程** | 是否有三层超时？是否实现幂等/Lease/Checkpoint/Outbox？是否有三层并发限制？ |
| **云原生** | 是否拆分工作负载？是否有弹性伸缩和积压告警？是否有配置灰度和版本回滚？ |
| **治理** | 是否有预算和配额？是否有工具白名单和权限边界？是否支持审计回放和人工接管？ |

## 演进路径

| 阶段 | 目标 |
|------|------|
| ① 单 Agent 验证期 | 跑通核心问答+工具调用，建立基础 Trace 和日志 |
| ② 状态化改造期 | 引入任务表/步骤表，会话状态外置，补齐超时/重试/幂等 |
| ③ 多 Agent 编排期 | 拆分角色，引入 Planner/Reviewer/Action，引入 Outbox/MQ/Worker Pool |
| ④ 治理平台期 | 多租户隔离，工具网关统一协议，审计回放，预算治理，灰度发布 |
