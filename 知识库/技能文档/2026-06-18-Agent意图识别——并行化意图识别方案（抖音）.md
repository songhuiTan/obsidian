## 核心观点

Agent 意图识别的正确做法是**并行化意图识别**——不依赖单一全能模型，而是由多个领域专家（agent）并行审题，各自从自己的专业视角判断用户意图。

核心思想：**把复杂的歧义阅读理解题，拆解为多维度的独立填空题。**

## 单次调用大模型的问题

1. **多意图遗漏** — 用户消息包含多个独立动作（如"查数据+发邮件"），单标签容易遗漏
2. **歧义难消解** — 用户意图摇摆时，单次推理无法及时修正方向
3. **安全风险高** — 语义模型可能漏判危险操作，引发生产事故

## 并行化意图识别方案

### 四大专家角色

| 专家 | 职责 |
|------|------|
| **规则专家** (Rule Expert) | 扫描核心关键词，做初步意图分类 |
| **上下文专家** (Context Expert) | 回溯对话历史，修正或补全意图 |
| **工具专家** (Tool Expert) | 匹配可用的执行工具，判断可行的动作路径 |
| **安全专家** (Safety Expert) | 做风险校验，拦截不安全操作 |

### 方案优势

- **并发执行** → 响应速度快
- **专才判断** → 各自领域精准度高
- **安全兜底** → 安全专家独立校验，不依赖语义模型的"自觉"

## 三个核心原则（面试回答框架）

```
并行 > 串行     —— 多专家并行审题，避免单点瓶颈
专才 > 全能     —— 单一全能模型不如多个专业模型各司其职
安全 > 功能     —— 安全专家作为独立闸门，不可省略
```

## 评论区热点

| 角度 | 观点 |
|------|------|
| **Token 消耗** | "上下文不共享，token消耗严重"、"四个提示词，无敌了" |
| **本质等价** | "别人写一个提示词，你写4个。在我看来是一样的" |
| **架构权衡** | 评论区共识：方案思路正确，但需要结合实际场景做工程优化（token 预算、上下文窗口、延迟要求）|

## 分析

这个方案本质上是在**ReAct 范式**的意图识别阶段引入**多 Agent 并行**（Multi-Agent Parallel Reasoning），与当前主流思路一致：

- 与 Anthropic 的 **Multi-agent orchestration** 理念相通（各 Agent 各司其职，并行处理）
- 与 Claude Code 的 **Sandwich 架构**类似（多种 checker/policy 并行校验）
- 实际工程中需要权衡：并行度 vs token 开销，建议结合 **意图缓存** + **分层过滤**（先粗筛再精判）来控制成本
