## 概述

腾讯技术工程对**自进化 Agent（Self-Evolving Agent）**赛道的系统调研：聚合 14 篇前沿论文，按"是否更新模型权重"和"是否依赖人工数据"两个维度划成三大技术路线。

**核心问题：如何让 Agent 在没有人工干预的情况下，把交互的副产物转化为下一次更强的能力？**

自进化 Agent 的核心诉求三件事：**能存**（沉淀成功模式/失败教训/可迁移技能）、**能用**（新任务中检索/调用/内化）、**能进化**（经验可更新、合并、淘汰）。

## 三大技术路线

| 路线 | 更新权重 | 依赖人工数据 | 代表工作 | 比喻 |
|------|---------|------------|---------|------|
| **第一类：经验/Skill 存储型** | ❌ | ❌（用训练数据） | AutoSkill、EvoSkill、MemSkill、CoEvoSkills、SE-Agent、Hermes | 配一本"工作笔记"，模型不动 |
| **第二类：RL 训练型** | ✅ | ❌ | EvolveR、SAGE、SkillRL、SKILL0、SkillOS、AgentEvolver | 把经验通过 RL 写进权重 |
| **第三类：0 数据自学型** | ✅ | ✅（不用） | Agent0、Tool-R0、Absolute Zero | 不要老师，Agent 互相出题互考 |

## 第一类：经验/Skill 存储型（不更新权重）

核心：把经验沉淀为可检索/可复用的"技能（Skill）"，本体 LLM 冻结。

### 代表工作

| 工作 | 核心机制 | 关键数据 |
|------|---------|---------|
| **AutoSkill** (2603.01145) | 双环结构：在线服务（查询重写+混合检索+技能注入）+ 技能进化循环（提取/Add/Merge/Discard/版本化合并） | WildChat-1M，**无性能指标**（只看了 skill 数量）——评估缺位是这类通病 |
| **EvoSkill** (2603.02766) | 三 Agent 分工（Executor 执行留档 / Proposer 反思根因 / SkillBuilder 落地）+ **Pareto 精英池**（新 Skill 至少一维严格优于才入库） | OfficeQA 60.6%→67.9%（+7.3pp）；SealQA 学到的 skill 跨任务到 BrowseComp +5.3pp |
| **MemSkill** (2602.02474) | 只进化操作 Memory 的 Skill；Controller 用 MLP + RL 训练（少见），Executor/Designer 冻结 | Controller/Skill 跨模型迁移有效（LLaMA→Qwen、LoCoMo→LongMemEval） |
| **CoEvoSkills** (2604.01687v2) | **Generator + Verifier 双子星**：Skill 生成同步带单元测试，sandbox 验证，两阶段（Surrogate 廉价验证 + Oracle 真实 LLM 端到端） | **Self-evo > Cross-model transfer**：Opus 4.6 self-evo 30.6%→71.1%（+40.5），把 Skill 迁给弱模型绝对值明显更低 |
| **SE-Agent** (2508.02085, NeurIPS 2025) | **多策略轨迹生成 + 跨轨迹重组**（Crossover 交叉 / Transfer 迁移 / Restructure 重构）——横向总结 vs 其他工作的纵向总结 | SWE-Bench Verified 最高 +55% 相对改善；与底层模型正交 |

**第一类总结：** 看似不训练其实仍要训练数据（核心点1）；核心是"存下经验"（核心点2）；**总结这一步被严重低估**——几乎所有工作都把 Skill 总结交给冻结 LLM，针对总结优化的几乎没有（核心点3，空白）；纵向 vs 横向总结之分（核心点4）。

## 第二类：RL 训练型（更新权重）⭐重点

### 代表工作

| 工作 | 核心机制 | 关键数据 |
|------|---------|---------|
| **EvolveR** (2510.16079) | 离线提炼策略原则入库 + 在线检索指导行动，反哺蒸馏 | NQ/HotpotQA/TriviaQA/PopQA |
| **SAGE** (2512.17102) | **Sequential Rollout**：一次跑一串相似任务，前序技能后序直接用，模型被迫学会"生成+复用技能"；Skill-integrated Reward | AppWorld |
| **SkillRL** (2602.08234) ⭐ | 强模型（o3）蒸馏 Skill，弱模型（Qwen2.5-7B）RL 学会使用；成功轨迹提炼+失败教训合成，压缩比 10-20× | ALFWorld 89.9% vs 77.6%（+12.3%）；WebShop +6.6%；Search-QA +8.6%；Skill 库 55→100 |
| **SKILL0** (2604.02268) ⭐ | 把 Skill 从推理时外挂上下文**内化到模型参数**；三阶段渐进课程（6 条→3 条→0 条），零样本执行每步 <0.5K tokens | 继承 SkillRL 的 SkillBank |
| **SkillOS** (2605.06614) ⭐⭐ | **训练专门 Curator 学会增/改/删 SkillRepo**，Executor 完全冻结；长周期间接奖励学习 | **结论1：训练过的 Qwen3-8B 总结者 > 冻结的 Gemini-2.5-Pro**；结论2：不动解题者性能也能涨 |
| **AgentEvolver** (2511.10395) ⭐ | **完全自主三环**：自出题（Self-Questioning 四步）、自解题、自总结，全链路无需人工标注 | 出题解题同模型，RL 后双重提升 |

### 四篇代表工作对比（三角色视角）

| 论文 | 出题者 | 解题者（训练？） | 总结者（训练？） |
|------|--------|----------------|----------------|
| SkillRL | — | Qwen2.5-7B ✅ | OpenAI o3 ❌ |
| SKILL0 | — | Qwen2.5-VL-3B/7B ✅ | o3（继承）❌ |
| SkillOS | Gemini-2.5-Pro（离线分组❌） | Executor 冻结 ❌ | **Qwen3-8B Curator ✅** |
| AgentEvolver | LLM 自身 ✅ | Qwen2.5-7B/14B ✅ | Qwen-MAX API ❌ |

**范式演进脉络：** SkillRL（强模型提炼→弱模型学会）→ SKILL0（内化进参数）→ SkillOS（冻结执行者→训练 Curator 管理技能）→ AgentEvolver（全链路自主）。

## 第三类：0 数据自学型

| 工作 | 机制 | 评估 |
|------|------|------|
| **Agent0** (2511.16043) | Curriculum Agent（RL 出题，reward=答题不确定性+工具频率）+ Executor Agent（RL 解题） | GSM8K、AIME 等数学 |
| **Tool-R0** (2602.21320) | 类似 Agent0 但做 general tool；Generator 格式/合法性/难度 reward + Solver 格式/准确性 reward | ToolAlpaca、SealTool、NexusRaven |
| **Absolute Zero** (2505.03335) | 单模型同时出题解题，**代码执行器作为唯一验证来源**（[输入,代码,输出] 三元组删一个让模型猜）——判分外包给绝对客观环境 | 代码 HumanEval/MBPP/LCB；数学 AIME/AMC/MATH-500 等 |

**第三类总结：** 全靠出题 Agent 自己（核心点1）；准确率判断多靠对照 sliver answer 是隐患（核心点2）；**最好有自动化判断标准**——Absolute Zero 的代码执行器是范本（核心点3）；出题难度 reward shaping 是核心难点（核心点4）；评估很混乱、benchmark 不重叠（核心点5）。

## 关键洞察：被忽视的"总结者"

**总结者是被严重低估的关键模块。** 14 篇工作中只有 SAGE（半个）和 **SkillOS（唯一完整训练）** 针对总结者本身做训练。SkillOS 证明：训练后的 8B Curator 优于冻结的 Gemini-2.5-Pro Curator。

**二维空间：** 总结者训练（纵轴）× 题目自动生成（横轴）——**右上方空白象限（既自动生成题目、又训练总结者）目前没有一篇工作覆盖**，这是最显眼的研究空白。

**另一个开放问题：** 横向总结（SE-Agent 多轨迹采样）与纵向总结（历史对话）在第二类工作中没有融合——"横向+纵向融合"会不会带来更稳健的 Skill 库？

## 战略分析

### 与现有体系的对照

| 维度 | 腾讯调研的进化路线 | 当前 Hermes 体系 |
|------|------------------|----------------|
| 经验存储 | AutoSkill/EvoSkill 式 Skill 库进化 | Skill 体系（SKILL.md）+ 记忆系统 |
| 总结者 | SkillOS 证明训练总结者 > 冻结大模型 | 尚无自动 Skill 总结/进化 |
| 自我进化 | AgentEvolver 自出题自解题 | 无 |
| 验证闭环 | CoEvoSkills 单元测试+Oracle | skill_view 加载，无自动验证 |
| 记忆进化 | MemSkill 操作 Memory 的 Skill 自进化 | TencentDB Memory（人工/半自动） |

### 高价值启示

1. **"总结者被低估"对 Skill 工程有直接指导意义**。SkillOS 结论"训练过的小模型总结者 > 冻结的大模型总结者"意味着：与其用强模型蒸馏 Skill 给 Hermes，不如让 Hermes 自己在使用中总结 Skill——Self-evo > Cross-model transfer（CoEvoSkills 已验证）。

2. **CoEvoSkills 的"测试驱动 Skill 进化"** 和知识库已归档的 Skill Quality Gate、SkillCorpus 是同一主线：Skill 不能靠 LLM 自觉，要有验证闭环（单元测试 + 真实任务 Oracle）。

3. **Hermes 出现在第一类代表工作里**（表格明确列了 Hermes）——说明腾讯调研团队把 Hermes 视为经验/Skill 存储型的代表之一，这与知识库中对 Hermes Skill 体系的认知一致。

4. **研究空白 = 机会**：完全自主 + 训总结者的交叉路径没人做。对社区/团队来说，这是可以在 Hermes/OpenClaw 生态上探索的方向。

5. **Absolute Zero 的"代码执行器当判分器"** 与 rgraph 的确定性内核、SkillCorpus 的沙箱实测建议一致——**客观执行环境是自进化可信度的基石**。

### 局限与判断

- 调研是论文综述，各工作的实际效果需要复现验证（部分论文无性能指标，如 AutoSkill）
- sliver answer（自生成答案对照）的可靠性是第三类工作的隐患
- 对工程落地最直接的借鉴：Skill 进化闭环（总结→验证→入库）比"模型变强"更可操作
