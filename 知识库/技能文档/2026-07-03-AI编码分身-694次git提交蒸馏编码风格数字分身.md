## 文章概要

作者从 18 个核心项目、694 次 git 提交中蒸馏出自己的编码风格数字分身，固化为可复用的 Claude Code Skill。通过「去业务化」提纯，从 594 行（51% 通用能力）优化到 517 行（77% 通用能力），任何前端开发者都能参考复用。

---

## 核心理念：编码风格是能力，不是业务手册

### 第一版错误：塞业务知识

- 594 行塞满业务领域（邀约、财务、CRM 等）
- 问题：别人用不了、占 token、业务一周一变

### 去业务化：去掉什么 vs 留下什么

| 去掉（业务特定） | 留下（通用能力） |
|:---|:---|
| 8 大业务领域 | Commit Message 风格（86% 中文，85% 带 Conventional Commits） |
| 具体接口链路 | 命名风格（文件 kebab-case，变量 camelCase） |
| 域名迁移规则 | 注释习惯（解释 WHY，不解释 WHAT） |
| 业务踩坑 | 架构偏好（接口层独立、优先复用、配置驱动） |
| | 决策逻辑（技术选型原则、重构触发条件） |

## 三路采集（怎么蒸馏编码 DNA）

### 第一路：Git 自动采集（覆盖「怎么做」）

- 最近 50 次 commit 概览 + commit 消息 + 文件变更频率
- 自动提取：技术栈偏好、命名/缩进/注释指纹、分层习惯、提交粒度

### 第二路：项目文档（覆盖「怎么想」）

- docs/、README、设计文档记录需求到代码的转化

### 第三路：个人反思（覆盖「为什么」）

- git 记不了决策 WHY
- 结构化问卷：最满意的技术决策、最大的坑、写代码最在意的 3 件事

> 单靠 git 大概还原 60% 的你。加上文档和反思，才能高保真。

## 六层编码 DNA 架构

```
SKILL.md
├── 表达层（Expression DNA）
│   ├── 代码命名风格（三重验证标记）
│   ├── 注释风格（WHY 不写 WHAT）
│   ├── commit message 风格
│   └── 代码排版规则
├── 架构层（Architecture Patterns）
│   ├── 标准项目结构
│   ├── 分层原则
│   ├── 复用策略
│   └── 通用开发模式
├── 决策层（Decision Heuristics）
│   ├── 技术选型原则
│   ├── 重构触发条件
│   └── 调试方法
├── 反模式层（Anti-patterns）
│   ├── 绝对不会做的事
│   ├── 踩过的坑 & 教训
│   ├── 技术债务处理原则
│   └── 批评者视角：我做得不好的地方
├── 诚实边界（Limitations）
│   ├── 不擅长的领域
│   └── 无法替代的判断
└── Correction 层（纠正层）
    ├── 纠正触发规则
    ├── 已记录的纠正表格
    └── 即时生效机制
```

### 三重验证（参考 nuwa-skill）

每条规则同时满足三条才标 ⭐⭐⭐：
1. 跨 2+ 项目出现过
2. 能预测新场景
3. 有具体案例

等级：⭐⭐⭐ 必须遵守 / ⭐⭐ 建议遵守 / ⭐ 可选参考

## 关键方法

1. 圈出业务特定内容 → 抽象为通用模式
2. 套 skill-engineering 模板（评估、门禁、版本）
3. Baseline + Darwin + Correction 组成进化闭环
4. 参考 colleague-skill（Correction、增量合并）和 nuwa-skill（三重验证、达尔文）
5. **能力 vs 知识**：风格是编程能力，不是领域百科
