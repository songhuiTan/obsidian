## 核心论点

> 没有评测体系的 Agent 团队，是在用客户做实验。

三个故事：
1. 客服 Agent 只看响应速度（3min→15s）→ 第三周满意度跌到比上线前还差
2. Claude Code：有评测体系后，模型升级决策从"几周"压缩到"几天"
3. 客服 Agent 准确率 62%，换模型 → 65%；修检索策略 → **84%**

---

## 一、Agent 为什么比传统软件难评测

| 特性 | 影响 |
|------|------|
| 非确定性 | 同样输入不同输出，pass/fail 不再适用 |
| 多轮决策 | 错误跨步骤级联放大 |
| 工具调用 | 行为依赖外部世界，不能只看文本输出 |
| 长链路 | 几十轮+几十次工具调用，评测维度多 |
| 能力复合 | 任务能力/对话质量/安全/成本常需 trade-off |

---

## 二、评测的四层对象（不是只评测模型）

评测的是"模型 + Prompt + 工具 + 工作流"的组合：

| 层 | 作用 | 典型问题 |
|----|------|----------|
| 模型层 | 底层大模型能力上限 | 推理不足、知识过期 |
| Prompt 层 | 任务翻译成指令 | 指令歧义、边界未覆盖 |
| 工具层 | Agent 可调用的外部工具 | 检索不准、参数错误、工具缺失 |
| 工作流层 | 多步骤任务编排 | 分支错误、异常处理缺失 |

> 模型层往往不是瓶颈。换模型提升 3%，修检索策略提升 22%。

---

## 三、评测核心概念链路

```
Task（测试用例）→ Trial（单次尝试）→ Transcript（执行轨迹）
→ Outcome（最终结果）→ Grader（评分器）→ Suite（套件）→ Harness（框架）
```

## 四、两套框架结合

### Anthropic 官方框架（方法论 — "怎么评测"）

**Grader 三件套：**

| 类型 | 特点 |
|------|------|
| 代码型（规则） | 快、确定、便宜，对合法变体不灵活 |
| 模型型（LLM Judge） | 灵活，但有位置/长度/自我偏好偏差 |
| 人工（Human） | 金标准，贵，用于校准/争议/高风险 |

**组合策略：** 加权 / 全过（安全） / 混合（关键硬过+其他加权）

**pass@k vs pass^k：**
- pass@k：k 次中至少一次成功（k=10 趋近 100%）
- pass^k：k 次全部成功（k=10 趋近 0%）
- 生产系统更关心 pass^k

**工程坑：**
- 多 Trial → 统计 pass rate 而非 single-shot
- 环境隔离 → Claude Code 踩过的坑：模型通过 git 历史获取"不公平优势"
- 可重放 → 不能复现的 badcase 等于没有

### 阿里工程化体系（平台 — "怎么持续评测"）

| 模块 | 说明 |
|------|------|
| 指标分级 P0/P1/P2 | 门禁/版本对比/长期观察，不分在一起看平均值 |
| Scorer 优先级 | 规则 > LLM > 人工 |
| 分层筛查 | 粗筛(90%) → 精判(8%) → 人工复核(2%) |
| 根因定位 5 步链路 | 证据汇总→范围收敛→分模块诊断→责任判定→结构化落盘 |
| 反馈三条生产线 | 回归用例线 / 训练数据线 / 配置知识库修订线 |
| 离线门禁 × 线上灰度 | 离线提升但线上恶化 → 回滚 |

**版本对比必须带统计：** 置信区间 + 显著性判断 + 最小可感知变化阈值

**人工评分路由逻辑（不只是阈值触发）：**
- 自动评分不确定时（边界分数/低置信度/reason 含糊/Judge 分歧）
- 新东西上线（模型/Prompt/工具 Schema/业务活动）
- 规则与 LLM Judge 结论冲突时

## 五、五个评测维度

| 维度 | 对应上线问题 | 关键指标 |
|------|-------------|----------|
| 任务完成率 | 用户问题有没有被解决 | 端到端通过率 |
| 回答质量 | 答案对不对、好不好 | 准确性/相关性/可操作性 |
| 鲁棒性 | 极端场景会不会崩 | 对抗输入通过率、多轮一致性 |
| 响应速度 | 用户等不等得了 | P50/P99 延迟、**TTFT（首字延迟）** |
| 安全性 | 会不会出大事 | 内容/信息/行为安全 |

TTFT 经验：0.5s 开始打字 vs 3s 无反馈，体感天差地别。

## 六、评分器选择原则

**瀑布模型：**

```
规则（硬条件：工具/状态/字段/禁用动作）
  → LLM Judge（语义/策略合理性）
    → 人工复核（高风险/低置信/冲突样本）
```

> 不要让 LLM Judge 做硬条件判断。规则一行代码能搞定的事，没必要让模型猜。

### LLM Judge 三个系统偏差及缓解

| 偏差 | 现象 | 缓解 |
|------|------|------|
| 位置偏差 | 前排答案更容易赢 | 打乱顺序做两次取平均 |
| 长度偏差 | 更长答案更容易高分 | Rubric 写明"简洁且完整" |
| 自我偏好偏差 | 同系列模型评自己更宽容 | 不同供应商交叉验证 |

## 七、评测集构建

**四类来源：**

| 来源 | 作用 | 做法 |
|------|------|------|
| 专家设计 | 定标准 | 手写核心业务路径期望行为 |
| LLM 扩展 | 扩覆盖 | 规则定结构骨架 + LLM 生成自然语言变体（1条→10-50条） |
| 线上数据 | 反映实际分布 | 从会话/工单中筛选 |
| Badcase 回流 | 收集典型失败 | 线上失败沉淀回评测集 |

**每个 Skill 四阶段组织：** 触发 → 核心逻辑 → 产物质量 → 异常容错

**推荐起步路径：** 先 50-200 条 golden set（覆盖核心路径+高风险边界）

---

## 八、能力评测 vs 回归评测

| | 能力评测（攻） | 回归评测（守） |
|--|--------------|--------------|
| 问什么 | "能做什么？" | "还能做以前能做的事吗？" |
| 通过率 | 低，瞄准挣扎的 Task | 接近 100% |
| 生命周期 | 通过率高了→毕业成回归套件 | 持续运行 |

两者必须同时跑——能力评测攻坚时，回归评测确保改动不引入新问题。

## 九、Badcase 根因定位 5 步链路

1. **证据汇总** — 按 traceId 汇总完整链路日志
2. **范围收敛** — 问题现象×功能模块映射表（答非所问→意图识别/Query改写/知识筛选）
3. **分模块诊断** — 逐模块读 input/output/Prompt/工具返回/异常日志
4. **责任判定** — 优先用严重模块结论直接定责，规则引擎匹配确定模式，LLM 兜底复杂链路
5. **结构化落盘** — 问题分类/现象/枚举/责任层+模块/置信度/修复建议

**根因标签绑定解决角色：**

| 分类 | 示例 | 解决角色 |
|------|------|----------|
| 语义理解 | 意图识别错误 | 算法优化 |
| 知识召回 | 检索不相关 | 运营配置/算法 |
| 工具覆盖与执行 | 关键工具未调用 | 工程修复 |
| 风险防控 | 安全护栏误判/漏判 | 规则配置 |
| 模型指令遵循 | 证据使用错误 | Prompt 优化 |
| 外部系统 | API 超时 | 工程修复 |

## 十、反馈闭环

一条 Badcase 至少生产三类反馈：
1. **回归用例线** — 同类问题不再出现
2. **训练数据线** — 正确模式→SFT，错误模式→RLHF 负例
3. **配置/知识库修订线** — 知识缺陷→补充，规则缺陷→变更

**入库标准：** 失败可复现 / 期望行为明确 / 根因标签清楚 / 样本有代表性 / 已完成脱敏

## 十一、五步可上手评测流程

| 步骤 | 核心任务 | 对应章节 |
|------|----------|----------|
| ① 定义评测目标 | 客服/代码/数据分析各有重点 | 五维度 |
| ② 构建评测集 | 正常60%+边界25%+对抗15% | 评测集构建 |
| ③ 自动化评测 | 规则+LLM Judge，可重复跑 | 评分器选择 / pass@k |
| ④ 人工抽检 | 每周50-100条，重点查高置信通过case | 人工评分路由 |
| ⑤ 持续监控+反馈 | badcase自动回流 | 反馈闭环 |

---

## 落地路径

| 时间 | 目标 |
|------|------|
| **本周** | 50 条用例最小评测集，人工评分，建基线 |
| **本月** | 接入 LLM Judge 做粗筛，人工复核分歧样本 |
| **本季度** | 补齐数据集 + 搭 Harness + 接入 CI 门禁 |
| **持续** | badcase 沉淀回评测集，评测结果转修复工单 |

> 一个覆盖 3 个维度、100 条测试用例的"粗糙"评测框架，远好过永远停留在设计阶段的"完美"评测框架。
> **评测越早开始，修复成本越低。**
