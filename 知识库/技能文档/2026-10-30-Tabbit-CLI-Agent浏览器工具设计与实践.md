## 1. 背景：三个设计起点

| 起点 | 含义 |
|---|---|
| **规划仍交给用户选择的 Agent** | Tabbit 不做模型循环，不自建 agent |
| **复用浏览器里已有的登录状态** | 不搞新 session、不要求重新登录，直接操作用户真实浏览器 |
| **浏览器程序在本机执行** | 不再额外叠加一层模型推理 |

Agent 接入后要面对的麻烦：按钮会移动、提交可能延迟、连接可能在操作完成前中断。工具要做三件事——**找到正确的控件、核对结果、中断后查明已完成的操作**。

### 三件套分工

```
Playwright  →  操作层：定位器、自动等待、可操作性检查、断言
浏览器      →  访问控制：进程内附着任务所属页面，不开放调试端口，后台运行
Runtime Service → 执行生命周期：跨命令保持执行状态，为每次提交记录回执
```

**为什么选 CLI + Skill 而不是 MCP / 自建 loop**：
- CLI 提供程序提交、结果查询、故障诊断的执行入口
- Skill 说明如何使用这些入口，以及**何时观察、验证、恢复**
- 结果：规划仍由用户选的 Agent 负责，Tabbit 无需维护模型调用循环，还能白嫖编码 Agent 已有的命令执行与编程能力

## 2. 操作层：复用并适配 Playwright

### 2.1 为什么是 Playwright + CDP + JavaScript

- Chromium 上 Playwright / Puppeteer / ChromeDriver **底层都是 CDP**
- Playwright 在协议之上提供定位器、等待、frame 处理、错误诊断——直接复用成熟语义，不让 Agent 再学一套
- 试过 Chromium 的 **Actor 路径**，但要达到需要的操作语义仍需重新实现定位、可操作性检查、frame 处理、错误诊断 → **放弃**
- 选 JavaScript 是为了让操作、异步协调、断言、结果处理**在同一个运行时完成**（`page.evaluate()` 的函数使用同语言，但跑在页面执行上下文）

### 2.2 三种互补操作路径（同一段 JS 里可混用）

| 路径 | 用途 |
|---|---|
| **定位器（locator）** | 操作有名称的控件 |
| **原生指针 / 键盘输入** | 操作视觉目标 |
| **页面内 JavaScript** | 数据提取与计算 |

可以混用：先截图找到对话框 → 再用定位器点其中的按钮；或脚本选出符合条件的行 → 定位器逐行更新。

> ⚠️ **重要警告**：在 `page.evaluate()` 里调用元素的 `click()` **会绕过 Playwright 的可操作性检查**。只能有意为之，**不应成为「控件被遮挡」或「匹配不唯一」时的通用补救手段**。

### 2.4 动作之前：定位与就绪（受控实验，全文最硬的一节）

测了页面让一次预期点击失效的**三种方式**：移动按钮、复制它的标签、用遮罩层盖住它。

| 场景 | 坐标点击 | 定位器点击 |
|---|---|---|
| **按钮被移走 + 原位放诱饵** | 点中**诱饵**（坐标保留旧位置） | 点中**目标**（定位器针对当前文档解析） |
| **标签重复** | — | 严格模式**拒绝执行**；把查询限定到预期区域后恢复正常 |
| **持续遮罩覆盖** | `click({force:true})` 正常返回，计数器显示「目标：0，遮罩层：1」**（误点遮罩）** | 普通点击**超时**，计数器「目标：0，遮罩层：0」→ **没发输入，避免了误点** |

**延迟绑定（late binding）** 是核心：定位器保存的是**查询**而不是元素或坐标，执行时刻才解析。这是它相对坐标点击的根本优势。

**测试规模**：四种场景各 48 对测试页面 = 共 **192 对 / 384 次初次尝试 / 32 次限定范围后的恢复**。判定依据是**对计数器和状态的直接回读**，不是模型自评。

### 2.5 动作之后：断言与判定依据

提供 `expect`，让 Agent **在程序里明确写出操作后的预期结果**。

> 点击正常返回，并不意味着保存或提交已经成功。

`expect` 的页面断言会在限定时间内**自动重试检查**，条件满足才继续，否则抛错。这样 Agent 可以依据验证结果判断是否完成，减少固定等待和反复回模型查页面。

**实验设计（很值得抄）**：让点击先把页面状态改成 `Saving`，受控延迟后再改成 `Saved` 或 `Failed`——两种情况下**点击都正常返回**。加上等待 `Saved` 的断言后：**24 次成功保存全部通过 / 24 次失败保存全部未通过**。

> 这就是「如何验证你的验证器有效」的标准做法：**先构造一个「表面成功、实质失败」的场景**。

### 2.6 错误诊断与恢复

案例：`getByRole('textbox', {name: 'Address *'})` 匹配到多个控件而停止 → Agent 检查页面发现 Email 已填好、地址仍为空 → 保留已填字段、加 `exact: true`、填完提交成功。

**33 条轨迹中 38 次严格模式失败的后续处理分布**：
- 12 次加上精确匹配
- 8 次其它查询修正
- 11 次按位置选择
- 7 次其它处理

**错误截断策略**（§2.3 的适配）：保留**长错误的首尾两端**，同时保留**出错的调用**和**最后报告的阻塞原因**（例如拦截了按钮点击的遮罩层）。这样 Agent 能对症处理：改定位器 / 处理遮挡 / 先检查之前操作的效果。

> 直接可迁移：**错误信息必须保留「首尾 + 出错调用 + 最终阻塞原因」四元组**，只截中间。

## 3. 浏览器侧：访问边界与后台执行

### 3.1 合成浏览器（synthetic browser）

Playwright 期望连接一个**完整浏览器**，但一个任务只应看到**属于自己的页面**。

做法：
- 暴露一个「浏览器形态」的 CDP 端点，**只暴露任务自己的页面**
- 浏览器通过 Chromium DevTools 机制**在进程内附着**页面
- 运行时服务通过**私有传输通道**与浏览器通信，**不监听任何调试端口**

路由示例：Playwright 发 `tabbit-page-1` → 路由器解析为目标页面 → 去掉合成 `sessionId` → 通过该页面 DevTools 客户端发 `{"id":2,"method":"Page.enable"}`。跨进程 iframe 保留真实子会话 `oopif-1`。对不属于该任务的目标发起附着 → 返回 `-32000: Unknown targetId`。

### 3.2 页面归属必须跟着变化走（完全中介原则）

> 只在任务开始时过滤一次标签页，形成不了持久的边界。

三种变化路径：
- frame 可能被移到**独立渲染进程**
- 弹窗可能**继承上下文**
- 已有 frame 也可能**提交一个新文档**

**弹窗五步案例**：
1. 任务页面（或其 frame）打开弹窗，Tabbit 接管并记录**打开者**
2. 弹窗最初是空白文档；若打开者是扩展，可能继承扩展的安全主体 → **一律拒绝会破坏合法流程**
3. 弹窗导航到目标地址，此时由**目标地址**决定是否允许顶层自动化
4. 导航可能**复用同一个 frame host**，DevTools 不一定重新执行最初的附着检查 → 因此**在新文档提交之前还要再检查一次目标地址**
5. 目标地址受限 → **解除附着并释放归属，用户的标签页保持打开**

> **完全中介原则（complete mediation）**：访问检查要覆盖**所有路径**，并在**权限条件变化后重新执行**。
> 「页面曾经获准访问，并不意味着它导航后的文档也能继续被操作。」

**新增 `newCDPSession(page)` = 多了一条控制路径**：Tabbit 为它创建**独立的受限客户端**、重新检查归属、用同样的 frame 附着策略。独立 DevTools 附着隔离协议订阅，但两个客户端操作同一页面，**效果是共享的**。

**边界声明**：任务归属限制的是**页面控制范围**，不是安全沙箱——任务仍跑在用户现有 profile 里，Cookie 和已登录账号共享；对**页面内容中的 prompt injection**，敏感操作仍需 Agent 宿主和用户授权。

### 3.3 后台执行

> 拦截一条显式的激活命令只覆盖了其中一条路径。

焦点模拟让后台页面获得所需的文档焦点状态，**同时不切换用户的前台标签页**。

## 4. 程序执行与结果反馈

核心循环：**观察 → 执行 → 核对**

| 环节 | 做什么 | 例子 |
|---|---|---|
| **观察** | 读页面内容 / 截图 / 上一段程序结果，确定下一步 | 预订前先确认日历当前显示的月份 |
| **执行** | 用程序完成已明确的步骤 | 翻到目标月份、选日期、设人数 |
| **核对** | 用断言或业务记录确认结果 | 确认日期、人数、预订结果 |

**关键洞察**：三个环节**不要求分别调用一次模型**。状态检查和预期结果明确时，程序可以连续执行并核对；只有需要理解新页面或作新业务判断时，才把观察交回模型。

### 4.1 以程序为执行单元（本文最值钱的公式）

Agent 通过 shell **heredoc** 把多行 JavaScript 一次提交：

```bash
tabbit-cli <<'JS'
  ...多行代码...
JS
```

`<<'JS'` 给标记加单引号，避免 shell 展开代码中的变量和命令替换。

**成本模型**——对于 n 次模型请求：

```
输入 = Σₖ₌₁ⁿ (S + Hₖ + Oₖ)

S  = 每次请求都重复的固定指令
Hₖ = 保留的历史
Oₖ = 新的观察
```

> **压缩观察只减少 `Oₖ`；省掉一次模型轮次，则连同那一轮的 `S` 和 `Hₖ` 一起省掉。**

这是「为什么要批量执行」的数学证明。省一轮 = 省掉整轮的固定指令 + 全部历史，远大于省一次观察。

**实测**：日期选择器任务，一次提交连续完成翻月→检查月份→选日期→人数从 1 到 5→预订，回执报告 **366 ms**。

**富表单任务**：一段程序填富文本编辑器、国家、出生日期、联系方式、上传文件，回读隐藏 email 字段返回 `form.checkValidity(): true`；下一段提交并读成功提示。**六次尝试全部成功，输入少 65.3%，累计耗时少 49.3%**。

### 4.2 数据处理与结果选择

字母方格题：读取 **3,864,805 字符**的词典 → 程序在页面内枚举相邻不重复路径、检查候选词、按长度与字母排序 → **返回压缩 JSON 只有 319 字节**（四个八字母单词 + 路径 + 词典来源）。

> **词典本身留在执行环境，不必进入模型上下文。**

反面数据（诚实且有价值）：另一次内部对比提高了内联结果上限，资源读取次数 92 → 14，**总输入却只下降 1.5%**。
→ 结论：**减少读取次数 ≠ 减少 token**。真正省的是「先计算再返回」。

### 4.3 回执（receipt）

运行时为每次程序提交保存的结构化记录。CLI 以 JSON 返回摘要，也可查询历史回执。

状态机：`queued` / `running` → `succeeded` / `failed` / `interrupted`

```bash
tabbit-cli receipt --task inspect --request-id inspect-01
```

**幂等语义**：只要原任务中的回执仍可用，重复提交同一 `request_id` 会**返回已有回执，不会再次执行程序**；修改后的程序必须用新的 `request_id`。

**两个字段的语义陷阱（原文特意强调）**：
- `status: succeeded` = **程序正常结束**，不代表保存/下单等业务操作成功
- `mutationState: possible` = **不能排除副作用**，不意味着检测到了修改

**延迟提交探测**：程序在网站 POST 完成前就返回，随后出现的 HTTP 504 直到**下一次回执**才返回给 Agent。→ **跨程序调用保留页面上的请求诊断**，并在下一次回执中返回新发现的问题。观察弹窗和导航时也要**先装监听再触发动作**，否则漏掉执行期间的事件。

### 4.4 Skill 设计（最有借鉴价值的一节）

- 主 Skill **13,137 字符**；两份 Markdown 参考文档合计 **40,613 字符**，**任务需要时才读取**
- Skill 不再复述 Playwright API 参考，只讲**任务边界、返回结果、恢复方法**，并用**完整可运行程序**展示观察/执行/验证

**A/B 实测（关键数据）**：

| Skill 版本 | 使用并发的运行占比 |
|---|---|
| 篇幅更长、以文字说明为主 | **4%** |
| 更短、把**可运行示例放在显眼位置** | **63%** |

> **示例的位置决定行为，文字的长度不决定行为。** 这条我直接采纳到 skill 编写规范里。

缓存效率：75 对内部对比中，缓存 token 占 Tabbit 输入 **91.9%**，占 Codex Chrome Control **91.2%** → **保持常用指令稳定以复用缓存**。

恢复提示要**随运行结果返回**：定位有歧义时列出匹配控件；程序仍在运行时提示查同一请求；修改结果不确定时提示核对应用状态。Skill 还要求 Agent 在程序里**明确写出停止条件**。

## 5. 运行时生命周期与故障恢复

问题根源：**CLI、Agent 宿主、浏览器三者运行时间不一致**。CLI 退出时页面操作可能仍在继续；Agent 没收到回复时操作可能已完成。

### 5.1 由浏览器托管运行时

踩过的坑：复用 Codex 浏览器客户端能连上 Tabbit，但页面对象和变量依赖 **Codex 宿主的持久 JavaScript 内核** —— 换 Agent 内核就不存在了，桥接层只能执行彼此独立的调用，**无法保留跨调用变量**。且**有些 Agent 会在命令结束时终止子进程**。

> 结论：**要服务多个 Agent 的浏览器工具，持久状态不宜依赖某个宿主的专有内核或进程管理方式。**

→ Tabbit 由**浏览器启动并托管**运行时服务，CLI 只负责提交程序和查询结果。
→ 每个任务独立 Worker，Worker 可被终止而**不关闭它的标签页**；**最多 8 个活动任务**；显式关闭浏览器才结束运行时。

### 5.2 为可恢复而设计（避坑范本）

**核心原则：保留结果，避免重复执行。**

- CLI 超时但浏览器里程序仍在跑 → **查询原请求回执**继续等待或取回结果，**不要重新提交**
- 恢复流程本身也会丢结果：`finish` 在回复前请求重启运行时 → 重启关闭了回复通道 → 调用方收到连接失败。修复：**先写完响应，再允许重启**

**「已完成部分」的恢复**：表格汇总等待页面超时，但「下一页」已点成功、页面停在第三页 → Agent 检查当前位置继续收集，**补回遗漏的第二页**，得到正确总计（而不是从错误起始页重跑）。

**最危险场景——提交订单**：

> 假设点击后没收到确认，服务器可能已经创建了订单，**直接重试就可能重复下单**。

处理：在支持的中断修改和传输丢失场景返回 **`OUTCOME_UNKNOWN`，不自动重放**。Agent 应先查回执 → 核对订单记录 → 应用支持**幂等键**时复用原键 → 否则只有确认上次修改未生效且不会再生效，才重复提交。

## 6. 评测：分别衡量接口与 Agent 行为

### 6.1 完整配对对比

25 道固定答案题 × 3 次重复 × 每种集成方式 = **75 次配对尝试**，同模型同推理设置，**不用重试结果替换计分**。

| 指标 | 结果 |
|---|---|
| **总输入** | **低 47.2%** |
| 未缓存输入 | 低 51.0% |
| 配对输入比值 | 几何均值 **0.641**，按任务聚类 95% CI **[0.503, 0.819]** |
| **工具调用次数** | 只少 **6.7%**（汇总比值 0.933，配对几何 0.917，**区间跨过 1**） |
| 每次调用输入 | 少 **43.5%**（约 **41.2K vs 72.9K** token） |
| 正确率（多数票） | **17/25 vs 15/25**，差异不显著 |
| 耗时 | 区间**跨过 1**（不显著） |
| 输出消耗 | **更高** |

> **诚实结论**：Tabbit 的优势主要是**输入消耗较低**，不是更准也不是更快。§4.1 富表单的耗时改善只适用于那个具体流程。

**方法论亮点**：工具调用次数 ≠ 模型请求次数，所以这种拆分**无法把差异归因到 Skill 大小 / 保留历史 / 观察内容**。→ 作者主动划出归因边界，这是好研究的标志。

### 6.2 衡量设计想要改变的行为

集成对比是综合效果；要分离单个设计选择的作用需要**受控测试**，要了解 Agent 怎么用这些机制需要**分析执行轨迹**。

初始化一致性：第一次 `goto`/`navigate` 之前的工具调用次数，**Tabbit 中位数 2 vs Chrome Control 3**（含初始化、探索、浏览器操作；75 条 Tabbit / 73 条 Chrome 轨迹包含导航调用，另 2 条 Chrome 轨迹未计入）。

### 附录里的统计学诚实

- 完整测试组 225 次尝试，单次上限 1,800 秒
- 答案匿名化乱序后由**两个模型家族各评两次**
- 跨家族评分只覆盖 225 次中的 **222 次** → **事先设定的正确率判定门槛没有通过** → **正确率数字仅作描述用途**
- 受控测试：文档不变 / 原位替换 / 移动 / 替换+移动；标签 16 个唯一 + 32 个重复；遮挡 24 无遮挡 + 24 持续遮挡，点击超时 500ms；保存 24 延迟成功 + 24 延迟失败，延迟 120/180/240ms，断言期限 700ms
- **注意**：测试页面模拟的是**内存中的应用状态**，不是持久化服务器提交
- 1,067 条轨迹中 550 条出现 `expect`，但**包括指令和工具输出中的出现，不代表实际执行断言次数**

## 7. 经验总结与下一步

**保留与放手的分界**：
- 保留 Playwright 的**定位、等待、输入行为**
- 浏览器侧精力集中在**页面访问 + 运行时管理**
- 程序负责连续执行已知步骤并检查结果，出现新业务判断再交回 Agent

**中断处理三问**：程序是否仍在运行？哪些修改已经生效？如何继续？

**性能评测四指标**（缺一不可）：输入消耗、错误操作、虚假成功、恢复结果。

**下一步**：
- 把常用网站上验证过的操作说明、程序、结果检查方法存为 **Playbook**，相关任务时按需加载
- **WebMCP** 由网站直接声明结构化工具（查订单、加商品）→ 与 Playbook 配合
- 已有页面操作经验和网站提供的业务接口**都需要持续验证并随网站变化维护**

## 8. 直接可迁移到我这套体系的做法

| 做法 | 落地方式 |
|---|---|
| **错误信息四元组** | 截断长错误时保留「首尾 + 出错调用 + 最终阻塞原因」 |
| **示例位置 > 文字长度** | skill 里把**可运行示例放显眼位置**（4% → 63% 的行为差） |
| **省轮次 >> 压观察** | 已知步骤批量执行，`S`+`Hₖ` 才是大头；公式 `Σ(S+Hₖ+Oₖ)` 可直接用来解释批量操作的价值 |
| **先构造「表面成功实质失败」再验证验证器** | 测断言能力时先造延迟失败场景（24/24 通过 + 24/24 拦截） |
| **`OUTCOME_UNKNOWN` 不自动重放** | 任何有副作用的操作（下单、提交、发消息）中断后先查回执再决定，幂等键优先 |
| **请求幂等语义** | 同一 `request_id` 重复提交返回已有结果，不重复执行 |
| **完全中介** | 权限/范围检查要覆盖 frame 迁移、弹窗继承、文档提交，而非只在入口检查一次 |
| **持久状态别挂宿主** | 跨会话状态放在独立托管的运行时，不依赖某个 agent 的进程生命周期 |

### 与本地浏览器工具对照

我这边 `browser_exec` 的现状对照这份设计：
- ✅ 有 `js()` 直接跑页面 JS、`wait_for_load()`、`capture_screenshot()`——对应它「三种操作路径」
- ✅ 有 `cdp()` 原生协议口——对应它的底层通道
- ⚠️ **缺** §2.4 的定位器延迟绑定与可操作性检查（`click_at_xy` 是坐标点击，正是它实验里点中诱饵的那条路）
- ⚠️ **缺** §2.5 的 `expect` 式断言 + 自动重试
- ⚠️ **缺** §4.3 的回执/幂等（同一动作重复提交没有 request_id 保护）
- ⚠️ 实践上应按它 §4.1 的结论：**多步已确定的操作合并成一次 `browser_exec` 调用**，把 `S + Hₖ` 省掉，而不是每步一调用
