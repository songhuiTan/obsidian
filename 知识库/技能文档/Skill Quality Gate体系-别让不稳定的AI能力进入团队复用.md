## 核心观点

Skill Quality Gate 的核心价值，不是证明 AI 很聪明，而是**防止不稳定、不安全、不可回归的 Skill 被规模化使用**。

AI Skill 的错误，很多时候是"看起来没错"——真正危险的不是 AI 完全不会做，而是它做得像对的，让测试产生"已经覆盖过了"的错觉。

---

## Review vs Gate

| 维度 | Skill Review | Skill Quality Gate |
|------|-------------|-------------------|
| 问的是 | 这个 Skill 写得是否合理？ | 这个 Skill 现在能不能放行？ |
| 侧重 | 设计质量（像代码评审） | 准入条件（给出通过/警告/阻断） |
| 举例 | Prompt 写得很完整，有角色有步骤 | 执行样例集发现 10 个样例漏 4 个异常流 |

**Skill Review 是必要条件。Skill Quality Gate 才是准入条件。**

---

## Gate 要拦的 6 类问题

| # | 问题类型 | 说明 |
|---|---------|------|
| 1 | **结构不可控** | 今天 Markdown 明天 JSON，接入质量平台后无法解析 |
| 2 | **能力不达标** | 只会正常流，Diff 分析只看文件名，接口测试只正向参数 |
| 3 | **稳定性不足** | 同一段支付代码 Diff，一次高风险、一次低风险、一次无法判断 |
| 4 | **幻觉和过度推断** | 需求没写优惠券却生成优惠券规则，测试记录没结果却总结"全部通过" |
| 5 | **安全和权限越界** | 从读取代码→修改用例→关闭缺陷→触发流水线，能力越强越要限制 |
| 6 | **成本和运行不可观测** | 没有版本号、trace、输入输出摘要，质量下降后无法定位 |

---

## 6 个 Gate 详解

### Gate 1：元信息 Gate
确认它是不是一个**可管理资产**。不能只是一段散落在文档里的 Prompt。
- 解决什么问题？适合/不适合什么场景？
- 输入/输出是什么？依赖哪些工具？
- 谁维护？当前版本？最近改了啥？评测样例在哪？

> 最怕的不是 Skill 写得不好，而是没人知道它为什么这么写、谁改过、改完有没有回归。

### Gate 2：结构 Gate
检查输出能不能被**后续系统消费**。测试工程场景里，很多输出要被系统继续处理。
- 测试用例生成 → 入库
- 风险分析 → 质量报告
- 自动化修复 → 创建 PR

**固定字段示例**：用例标题、前置条件、测试步骤、预期结果、优先级、覆盖类型、关联需求点、风险说明

### Gate 3：样例 Gate
**没有样例集，就没有回归能力**。至少要有：
- 黄金样例 ✔️
- 边界样例 ✔️
- 异常样例 ✔️
- 对抗样例 ✔️

> 不能只证明 Skill 在顺风场景能用。

### Gate 4：行为 Gate
检查输出有没有**抓住测试重点**。不只看格式，看是否覆盖了关键质量点。

例：订单取消需求的关键点 —— 订单状态变化、库存回滚、优惠券返还、支付退款、消息通知、重复取消、超时取消、权限校验。

### Gate 5：稳定性 Gate
**同一个问题不能每次给出完全不同的判断**。对同一样例执行多次，观察：
- 输出格式是否稳定
- 核心测试点是否稳定
- 风险等级是否稳定

### Gate 6：安全与权限 Gate
**不要让 Skill 做它不该做的事**。大多数测试 Skill 初期应停留在"只读类"和"建议类"：
- ❌ 默认自动：关闭缺陷、修改用例、删除数据、合并脚本、触发生产流水线
- ✅ 需要人工确认：有风险的写操作

## 最小可落地方案

```
skill-quality-gate-demo/
├── skill.md              # Skill 说明和正文
├── metadata.yaml         # 名称、版本、负责人、适用场景
├── cases/                # 样例输入
├── expected/             # 每个样例必须命中的关键点
├── gate.md               # 门禁规则和执行结果
└── changelog.md          # 变更记录
```

**第一版只需三类检查：**
1. **结构检查** — 元信息完整？输出格式符合？字段缺失？
2. **行为检查** — 关键测试点命中？出现明显幻觉和遗漏？
3. **安全检查** — 对抗样例验证：被诱导偏离、泄露敏感信息、建议越权动作？

Skill 变更后必答三个问题：
- 这次改动解决了什么问题？
- 有没有影响原来通过的样例？
- 有没有新增对应的回归样例？

## 风险分级

| 级别 | 适用 | Gate 要求 |
|------|------|----------|
| 🟢 个人辅助类 | 帮工程师整理测试思路 | 轻量 Gate，检查边界和输出格式 |
| 🟡 团队复用类 | 统一生成测试用例 | 样例集 + 结构 Gate + 行为 Gate |
| 🟠 决策辅助类 | 风险等级、测试优先级判断 | 必须增加稳定性 Gate |
| 🔴 执行类 | 自动修改/触发操作 | 必须有权限 Gate + 人工确认 |

---

## 核心金句

- "Skill Review 解决的是'这个 Skill 设计得怎么样'；Skill Quality Gate 解决的是'这个 Skill 现在能不能放行'；下一步的 Skill CI/CD，解决的是'怎么让这些 Gate 自动执行'。"
- "AI 输出不能只靠人凭感觉判断。有了 Gate，AI 能力才能被回归、被比较、被追踪、被持续改进。"
- "没有 Gate，Skill 只能停留在个人试用。有了 Gate，Skill 才能进入团队复用。"

**结尾留给测试的 5 个问题：**
1. 它的答案能不能被信任？
2. 它的结论有没有依据？
3. 它的输出能不能回归？
4. 它的行为有没有边界？
5. 它的错误会不会被规模化放大？
