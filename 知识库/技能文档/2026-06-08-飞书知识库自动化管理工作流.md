# 飞书知识库自动化管理工作流

文章中涉及到的工具安装地址：

[https://www.kimi.com/features/webbridge](https://www.kimi.com/features/webbridge)
[https://github.com/Panniantong/Agent-Reach](https://github.com/Panniantong/Agent-Reach)
[https://open.feishu.cn/document/home/index](https://open.feishu.cn/document/home/index)

文章中有很多专业性的安装提示，如果非专业人员不建议手动安装，**全部交给 Codex 安装**。

你只需要把工具的地址告诉 Codex。

## 一、整体工具组合

我实际用的是这 4 类工具：

```text
Codex：负责调度、写脚本、读写本地文件、执行任务
Kimi WebBridge：负责操作真实浏览器和登录态网页
Agent Reach：负责搜索网页、读取文章、采集公开内容
飞书 API 机器人：负责批量创建页面、写入内容、维护目录
```

可以理解成：

```text
Codex 是总控
浏览器工具负责看页面
搜索工具负责找资料
飞书 API 负责写入系统
本地 Markdown 负责留痕和备份
```

不要把所有事情都交给一个工具。每个工具只做自己最擅长的部分。

## 二、Kimi WebBridge

Kimi WebBridge 的作用是让 AI 使用你的真实浏览器。

它适合处理这些场景：

- 网页需要登录后才能看。
- 页面内容 API 拿不到，只能从浏览器看。
- 需要确认页面排版、图片、按钮、表单。
- 需要截图或保存网页状态。
- 需要对比两个网页的目录结构。

### 1. 安装

安装命令：

```bash
curl -fsSL https://cdn.kimi.com/webbridge/install.sh | bash
```

安装完成后，需要同时满足两件事：

```text
1. 本地 daemon 已启动
2. 浏览器扩展已安装并连接
```

浏览器扩展安装页：

```text
https://www.kimi.com/zh-cn/features/webbridge
```

### 2. 检查状态

先检查状态：

```bash
~/.kimi-webbridge/bin/kimi-webbridge status
```

健康状态应该类似：

```json
{
  "running": true,
  "extension_connected": true,
  "port": 10086
}
```

如果 `running` 是 `false`，启动服务：

```bash
~/.kimi-webbridge/bin/kimi-webbridge start
```

如果 `extension_connected` 是 `false`，通常是浏览器扩展没有连接。打开浏览器，确认扩展已启用，再重新检查。

常用维护命令：

```bash
~/.kimi-webbridge/bin/kimi-webbridge start
~/.kimi-webbridge/bin/kimi-webbridge stop
~/.kimi-webbridge/bin/kimi-webbridge restart
~/.kimi-webbridge/bin/kimi-webbridge logs -n 100
```

### 3. 基本调用方式

Kimi WebBridge 默认监听：

```text
http://127.0.0.1:10086
```

打开网页：

```bash
curl -s -X POST http://127.0.0.1:10086/command \
  -H 'Content-Type: application/json' \
  -d '{"action":"navigate","args":{"url":"https://example.com","newTab":true},"session":"demo"}'
```

读取当前页面结构：

```bash
curl -s -X POST http://127.0.0.1:10086/command \
  -H 'Content-Type: application/json' \
  -d '{"action":"snapshot","args":{},"session":"demo"}'
```

截图：

```bash
curl -s -X POST http://127.0.0.1:10086/command \
  -H 'Content-Type: application/json' \
  -d '{"action":"screenshot","args":{"format":"png"},"session":"demo"}'
```

查找已经打开的标签页：

```bash
curl -s -X POST http://127.0.0.1:10086/command \
  -H 'Content-Type: application/json' \
  -d '{"action":"find_tab","args":{"url":"https://example.com","active":true},"session":"demo"}'
```

### 4. 我怎么用它

我主要让它做 4 件事：

```text
1. 打开需要登录态的飞书页面
2. 读取页面目录和可见文本
3. 截图确认图文页面是否正常
4. 对照外部资料库和自己的页面结构
```

它不适合承担全部批量导入任务。批量创建页面、批量写入正文，还是交给飞书 API 更稳。

### 5. 给 Codex 的提示词

```text
请使用 Kimi WebBridge 打开这个链接，并读取当前页面的目录结构。
先检查 WebBridge 状态。
如果页面需要登录态，不要改动页面内容，只读取可见标题、目录和正文摘要。
输出：
1. 页面标题
2. 一级目录
3. 二级目录
4. 需要进一步打开的页面
5. 无法读取或需要人工确认的位置
```

```text
请使用 Kimi WebBridge 对比这两个飞书知识库页面。
不要迁移内容，只分析结构差异。
输出：
1. 对方目录结构
2. 我方目录结构
3. 我方缺少的栏目
4. 值得参考的页面类型
5. 不建议照搬的部分
```

```text
请使用 Kimi WebBridge 检查这个页面是否包含二维码、微信号、课程推广、打赏或外部引流。
只输出可疑位置，不要删除任何内容。
输出字段：
- 页面标题
- 可疑内容类型
- 大概位置
- 原因
- 是否需要人工复核
```

## 三、Agent Reach

Agent Reach 这里指的是让 AI 使用搜索和网页读取工具。

我实际使用的是 Agent Reach 这类工具集合。它的作用是让 AI 不只依赖浏览器，还能通过搜索引擎、网页读取器、公众号采集、GitHub 搜索等方式拿到资料。

适合处理：

- 搜索公开网页。
- 读取普通网页正文。
- 搜索技术资料和代码上下文。
- 读取微信公众号文章。
- 获取公开资料的 Markdown 文本。
- 在导入前先做价值判断。

### 1. 检查环境

检查 Agent Reach 可用渠道：

```bash
agent-reach doctor
```

如果使用 MCP 工具，可以查看 MCP 服务：

```bash
mcporter_list_servers()
```

### 2. 网页搜索

用 Exa 搜索网页：

```bash
mcporter call 'exa.web_search_exa(query: "搜索关键词", numResults: 5)'
```

搜索技术或代码上下文：

```bash
mcporter call 'exa.get_code_context_exa(query: "code question", tokensNum: 3000)'
```

### 3. 读取普通网页

用 Jina Reader 读取网页：

```bash
curl -s "https://r.jina.ai/https://example.com/article"
```

这个方式适合读取普通网页、博客、文档页。

### 4. 读取微信公众号文章

微信公众号文章不适合直接用普通网页读取，经常会遇到验证或空内容。

可以先搜索：

```bash
mcporter call 'exa.web_search_exa(query: "关键词", numResults: 5, includeDomains: ["mp.weixin.qq.com"])'
```

再抓取正文：

```bash
mcporter call 'exa.crawling_exa(urls: ["https://mp.weixin.qq.com/s/ARTICLE_ID"], maxCharacters: 10000)'
```

### 5. 我怎么用它

我的使用顺序一般是：

```text
1. 先搜索主题
2. 读取网页正文
3. 保存原始 Markdown
4. 让模型判断资料价值
5. 有价值的再进入整理流程
6. 图片、二维码、外部引流单独标记
```

这样做的好处是，不需要一开始打开大量网页，也不需要让浏览器一个页面一个页面地截图。

### 6. 给 Codex 的提示词

```text
请使用 Agent Reach 搜索这个主题的公开资料。
要求：
1. 优先找教程、官方文档、案例复盘。
2. 不要只给链接，要判断每条资料适合解决什么问题。
3. 输出标题、链接、内容类型、适合人群、是否值得导入。
4. 对广告页、课程销售页、纯引流页标记为不建议导入。

主题：
【填写主题】
```

```text
请读取下面这些网页，并整理为资料评估表。
不要改写正文，不要写入飞书。
输出字段：
- 标题
- URL
- 摘要
- 适合栏目
- 内容价值：高/中/低
- 风险内容：二维码/课程/社群/打赏/外链/无
- 建议动作：导入/跳过/人工复核

链接：
【粘贴链接列表】
```

```text
请采集这篇微信公众号文章。
先用 Agent Reach 的微信公众号采集路线。
如果普通网页读取失败，不要反复重试，切换到公众号文章专用读取方式。
采集结果保存为本地 Markdown。
输出：
1. 是否采集成功
2. 正文字数
3. 是否包含图片
4. 是否包含二维码或外部引流
5. 本地保存路径
```

## 四、飞书 API 机器人

飞书 API 机器人负责把整理好的内容写入飞书。

浏览器适合"看"，API 适合"批量写"。

我用飞书 API 机器人处理：

- 获取 tenant access token。
- 获取知识空间列表。
- 读取知识库目录。
- 创建知识库节点。
- 创建新版文档。
- 写入文档块。
- 上传或挂载图片。
- 更新同步记录。

### 1. 创建飞书自建应用

进入飞书开放平台，创建企业自建应用。

需要准备：

```text
App ID
App Secret
机器人能力
知识库相关权限
文档读写权限
```

注意：

- App Secret 不要写进公开文档。
- 不要把 token 发到聊天窗口。
- 凭证只放本地配置文件或服务器环境变量。

本地配置文件示例：

```text
FEISHU_APP_ID=cli_xxx
FEISHU_APP_SECRET=xxx
```

### 2. 授权机器人访问知识库

只创建应用还不够，还要让机器人有目标知识库的访问权限。

常见做法：

```text
1. 开启应用机器人能力
2. 发布或启用应用
3. 把机器人加入对应群或空间
4. 给机器人授予知识库访问权限
5. 用 API 读取知识空间列表做验证
```

验证成功后，再做写入测试。

### 3. API 基础流程

典型流程：

```text
1. 用 App ID 和 App Secret 获取 tenant access token
2. 获取知识空间列表
3. 找到目标 space_id
4. 获取目标知识库子节点
5. 创建新版文档
6. 写入文档块
7. 创建或挂载知识库节点
8. 记录同步结果
```

### 4. 最小验证流程

第一次不要直接全量写入。

先跑最小测试：

```text
1. 读取知识空间列表
2. 读取目标知识库目录
3. 创建一个临时测试页面
4. 写入一段测试文本
5. 浏览器打开确认
6. 删除或归档测试页面
```

只有最小测试成功，才开始批量同步。

### 5. 批量写入原则

批量写入时遵守这几个规则：

```text
先读后写
先小批量后全量
先创建目录再写页面
每一批都生成同步记录
失败页面单独记录，不要无限重试
```

### 6. 给 Codex 的提示词

```text
请读取本地飞书应用配置文件，但不要输出任何 App Secret 或 token。
先做只读验证：
1. 获取 tenant access token
2. 获取知识空间列表
3. 找到目标知识库
4. 读取一级目录
只输出验证结果、知识库名称、目录数量和是否具备继续写入的条件。
```

```text
请用飞书 API 创建一个测试页面。
要求：
1. 只创建 1 个页面
2. 页面标题包含"API 测试"
3. 写入一段简单文本
4. 成功后输出页面链接或节点信息
5. 不要创建其他页面
6. 不要输出密钥和 token
```

```text
请根据这个 Markdown 文件批量同步到飞书知识库。
要求：
1. 先输出导入计划，不要立刻写入
2. 说明会创建哪些目录和页面
3. 标记可能失败的图片或附件
4. 我确认后再执行写入
5. 写入后更新同步记录

Markdown 路径：
【填写本地路径】
```

```text
请读取当前飞书知识库目录，并和本地导入计划对比。
输出：
1. 已存在页面
2. 需要新增页面
3. 可能重复页面
4. 标题不一致页面
5. 不建议自动覆盖的页面
```

## 五、Codex 的调度方式

Codex 不只是聊天工具，它在这个流程里负责调度其他工具。

我通常这样安排任务：

```text
搜索资料：Agent Reach
读取登录页：Kimi WebBridge
批量处理文件：Codex 本地脚本
写入飞书：飞书 API
大批量判断：外部或自部署大模型
人工确认：只看不确定结果
```

### 1. 每次任务先让 Codex 读规则

提示词：

```text
请进入项目目录，先阅读项目规则文件。
后续所有飞书操作必须遵守：
1. 不输出任何密钥和 token
2. 写入前先做只读检查
3. 批量操作前先输出计划
4. 操作完成后更新同步记录
```

### 2. 让 Codex 先规划再执行

提示词：

```text
下面是一个资料导入任务。
你先不要操作，先输出执行方案。
方案里说明：
1. 哪些内容用浏览器读取
2. 哪些内容用 Agent Reach 采集
3. 哪些内容用飞书 API 写入
4. 哪些内容需要人工确认
5. 如何减少 token 消耗
```

### 3. 让 Codex 减少上下文浪费

提示词：

```text
这次任务请减少进度读取和长文本输出。
原则：
1. 不要把全文贴到聊天里
2. 大文件保存到本地
3. 只汇报统计、异常和需要我决策的点
4. 能用脚本处理的不要逐页读给我
5. 不确定内容输出到报告文件
```

### 4. 让 Codex 做人工复核清单

提示词：

```text
请把模型筛选结果整理成人工复核清单。
不要直接删除内容。
输出字段：
- 页面路径
- 问题类型
- 可疑片段
- 建议处理
- 是否必须人工确认
- 优先级
```

## 六、推荐工作流

完整流程可以这样跑：

```text
1. Agent Reach 搜索公开资料
2. 保存原始网页或 Markdown
3. 大模型初筛资料价值和风险
4. Kimi WebBridge 检查需要登录态或排版确认的页面
5. Codex 生成导入计划
6. 飞书 API 小批量测试写入
7. 飞书 API 批量创建页面
8. Codex 生成同步记录
9. 人工抽检可疑页面
```

不要一开始就全自动。

比较稳的方式是：

```text
先让工具收集
再让模型筛选
再让 API 写入
最后人工抽检
```

## 七、常见问题

### 1. Kimi WebBridge 和 Agent Reach 有什么区别？

Kimi WebBridge 用你的真实浏览器，适合登录态页面和页面操作。

Agent Reach 更像搜索和阅读工具，适合找公开资料、读网页正文、采集文章。

### 2. 为什么不用浏览器全量抓？

浏览器适合确认页面，不适合大规模批处理。

全量抓取、批量判断、批量写入最好交给脚本、API 和模型。

### 3. 飞书页面为什么不用手动复制？

少量页面可以手动复制。

但几百篇资料、图片、目录、同步记录靠手工会很难维护。API 的价值是可重复、可记录、可回滚。

### 4. 大模型能不能直接决定删什么？

不建议。

模型适合做初筛和标记，不适合直接删除。尤其是二维码、课程推广、外部链接、授权说明这些内容，最好输出清单后人工确认。

### 5. 最容易出问题的地方是什么？

主要有 5 个：

```text
1. 浏览器扩展没连接
2. 飞书机器人没有知识库权限
3. API token 或权限不足
4. 图片和附件批量写入失败
5. 模型误判内容价值或风险
```

所以每一步都要先小批量测试。

## 八、最小复现版本

如果想复现这套方法，可以按这个顺序做：

```text
1. 安装 Kimi WebBridge
2. 确认浏览器扩展连接成功
3. 安装或配置 Agent Reach
4. 用 Agent Reach 搜 3 条资料
5. 用网页读取工具保存 1 篇文章
6. 在飞书开放平台创建自建应用
7. 开启机器人能力并授权知识库
8. 用 API 创建 1 个测试页面
9. 让 Codex 把本地 Markdown 写入测试页面
10. 写一条同步记录
```

只要这 10 步跑通，就说明"搜索、读取、整理、写入、记录"这条链路已经打通。
