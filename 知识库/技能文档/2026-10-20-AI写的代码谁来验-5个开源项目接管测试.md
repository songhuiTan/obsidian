# AI 写的代码谁来验？5 个开源项目接管测试

> 公众号：aivibe ｜ 2026-10-20 08:25
> 原文：[AI 写的代码谁来验? 5 个开源项目接管测试](https://mp.weixin.qq.com/s/fSfJqS5lOYnzZHSCg3NSsA)

## 概述

Cursor / Claude Code 已经能在几分钟内写出一个能跑的登录页，但"验证"这一环仍然靠人工点一遍——而且点完还得自己记住每个边界情况。这篇文章选了 5 个本地运行、不需要把代码交给第三方的开源项目，覆盖从"AI 应用自身的质量"到"接口契约"再到"测试资产版本化"的完整链条：promptfoo（LLM 评测与红队）、midscene（自然语言写 E2E）、keploy（真实流量录制成用例）、hurl（纯文本 HTTP 断言）、bruno（Git 原生 API 客户端）。

> 今日金句：AI 负责把代码写出来，你需要的不是相信它，是一套能替你不相信它的工作流。

## 核心亮点：5 个项目的分工与边界

以下 Star 数、License 为 **归档日（2026-10-20）GitHub API 实测**，非文章口径；文章有一处许可证写错，已在表中标注。

| # | 项目 | 实测 Star | 语言 / License | 一句话定位 | 关键限制 |
|---|------|-----------|----------------|-----------|---------|
| 1 | [promptfoo/promptfoo](https://github.com/promptfoo/promptfoo) | 26,185 ⭐（2,522 forks） | TypeScript / MIT | LLM 评测 + 红队 + 多模型横向对比 + CI 集成 | 按 token 计费，跑量大成本真实；只管 prompt/模型行为，不替代业务单测；**已归 OpenAI**（2023-04 建库，仍在维护） |
| 2 | [web-infra-dev/midscene](https://github.com/web-infra-dev/midscene) | 15,334 ⭐（1,201 forks） | TypeScript / MIT | 视觉 GUI Agent 写 E2E：`aiAct` / `aiWaitFor` / `aiAssert` | 每次跑都烧 token；视觉相同元素易点错；只验"看得见"的部分 |
| 3 | [keploy/keploy](https://github.com/keploy/keploy) | 18,658 ⭐（2,420 forks） | Go / **Apache-2.0**（文章误写 AGPL-3.0） | eBPF 抓真实流量 → 自动生成测试 + mock，`record` / `test` | eBPF 依赖 Linux 内核，macOS/Windows 需虚拟化绕行（最常见翻车点）；录不到没跑过的分支 |
| 4 | [Orange-OpenSource/hurl](https://github.com/Orange-OpenSource/hurl) | 19,263 ⭐（750 forks） | Rust / **Apache-2.0**（文章误写 AGPL-3.0） | 纯文本 `.hurl` 跑 HTTP 断言，底层 libcurl | 只管 HTTP 层，DB/业务逻辑不碰；无 GUI；不生成用例（与 keploy 互补） |
| 5 | [usebruno/bruno](https://github.com/usebruno/bruno) | 47,759 ⭐（3,015 forks） | JavaScript / MIT | Git 原生 API 客户端，Bru 纯文本集合，永久离线 | 永远不做云同步（设计承诺）；插件广度不及 Postman；迁移需转 Bru 格式 |

### 细节补充

**promptfoo** — 六件事覆盖 AI 应用完整质量流程：自动化评测、红队与漏洞扫描、并排对比（OpenAI / Anthropic / Azure / Bedrock / Ollama）、进 CI/CD、code review 时扫 LLM 安全合规、结果共享团队。安装四条路：npm / brew / pip / npx 免装。官网首屏 "Ship agents, not vulnerabilities"。评测 100% 本地跑，prompt 不出机器。

**midscene** — 主张写在 README 最上面："See interfaces like a human. E2E testing in natural language." 两种用法：YAML 用例（每 case 下 `aiAct` 做什么 / `aiWaitFor` 等什么 / `aiAssert` 断言什么），或塞进已有 Playwright 测试（`new PlaywrightAgent`）。原理是"看屏幕、对看到的东西做动作、检查可见结果"，用截图避开发庞大 DOM 树给模型。覆盖 web / 移动端 / 桌面（scrcpy + yume-chan 控制安卓）。成本实测：AppControlBench 上 Doubao Seed 2.1 Turbo 完成 60 题中的 58 题，总花费 0.59 美元。自托管模型支持清单含 Qwen3.x、Doubao-Seed-2.1、DeepSeek V4 Flash、GLM-4.6V、UI-TARS，但小模型准确率明显下降。

**keploy** — 跑 `keploy record` 把日常真实 API/集成流程自动录成测试和 mock，`keploy test` 回放验证。底层 eBPF 在网络层抓流量，无代码、语言无关、不装 SDK。捕获对象含 API 调用、数据库查询、流式事件。口号"90% 测试覆盖率"，且自己用自己测（公开覆盖率徽章）。官网首页："AI writes code, Keploy catches what breaks"。

**hurl** — 一个文件里先 GET 首页用 xpath 从 meta 抓 CSRF token，紧接着 POST 登录时用 `{{csrf_token}}` 引用上一步的值——跨请求串值是它最顺手的地方。断言按数据类型分开：HTML 用 XPath、JSON 用 JSONPath，可查响应头/状态码，正则校验（`jsonpath "$.id" matches /\d{4}/`）。适合 REST / SOAP / GraphQL。工程细节：`--parallel` 每文件独立 worker、`--jobs` 控并行数、`--test` 测试模式（不出响应体只给汇总）、`--json` 导 HAR 近似格式。Powered by curl，支持 IPv6 / HTTP/3。

**bruno** — 集合直接存成文件系统文件夹，用 Bru 纯文本标记语言保存请求。接口用例天生就是代码，可用 Git 协作。明确原则："Bruno 是纯离线的，永远不会有云同步的计划"。官网："The Git-native API client"。桌面 IDE 为主体，有 VS Code 插件，README 支持 20+ 语言含简体中文。

## 这 5 个在链条上的位置

不是五个平行的替代品，而是一条从"写完"到"上线"的链：

```
promptfoo ── AI 应用自身的质量（prompt / 模型行为 / 红队）
midscene  ── AI 应用自身的质量（界面视觉）
    ↓
keploy    ── 网络层：真实流量 → 用例（回归防护）
    ↓
hurl      ── 契约层：最轻的纯文本 HTTP 断言，diff 可评审
    ↑
bruno     ── 地基：让上面这些用例以代码形式存进 Git
```

作者给的选型口诀：
- 做 AI Agent / RAG → 先上 **promptfoo** 跑评测和红队
- 给网页 / App 写端到端 → **midscene**
- 服务有数据库和外部依赖、改一次怕炸一次 → **keploy**
- 团队只有 HTTP 接口、要进 CI 的契约断言 → **hurl** 最省事
- 不想把接口数据交给第三方 → **bruno** + Git 管理集合

## 关键洞察

- **"AI 写得越快，这条验证链越值钱"** —— 这是全文的核心论点，也是当前 Agent 落地的真实瓶颈：生成能力已经过剩，验证能力才是稀缺资源。
- **5 个项目没有一个在宣称"帮你写测试"**。promptfoo 测的是 prompt 行为，midscene 靠视觉理解界面，keploy 靠录真实流量，hurl 靠你自己写契约，bruno 只是存。**"写用例"这件事始终是人的活**，工具只负责执行和回归。
- **keploy 的覆盖率天花板是自己的软肋**：录的是已经发生的流量，没人在生产路径上走过的分支永远测不到。所以它防的是"改了就炸"，不是"本来就漏"。
- **本地化 / 数据不出机器是一条反复出现的产品原则**：promptfoo 强调评测 100% 本地、bruno 承诺永不做云同步。在 Agent 时代，"不把代码和数据交给第三方"正在从卖点变成基线要求。

## 战略分析

**这篇文章对我的工具链相关度：中等偏高，但主要是"缺什么"而不是"换什么"。** 目前我这套体系（Hermes Agent + Obsidian 知识库 + TencentDB Memory + 一套 skill 库）在"生成"侧很厚——skill 越攒越多、cron 在跑、归档在流水线化；但在"验证"侧几乎是零：没有任何自动化回归、没有对已装 skill 的质量门禁、没有任何形式的"改动了这个会不会炸"的检测。文章揭的正是这个洞。

分项判断：

| 项目 | 对我是否有实际价值 | 判断依据 |
|------|-------------------|---------|
| promptfoo | **最高优先** | 我有多个 skill 依赖 LLM 输出（归档清洗、战略分析、产品经理人格）。现在质量全靠我每次现判，没有固定测试集。promptfoo 的 declarative config + CI 集成正好能给 skill 的 prompt 建回归基线。本地跑、MIT、归 OpenAI 后仍开源——风险是后续开源策略变动 |
| midscene | 中等 | 我的 `dogfood` / `computer-use` skill 已经在做浏览器操作验证，但都是手写断言。midscene 的自然语言 `aiAssert` 是更轻的写法，且能进 Playwright。不过每跑一次烧 token，不适合高频 CI |
| keploy | 低（当前） | 依赖 eBPF/Linux，macOS 上要绕虚拟化，收益对不上成本。而且我没有长期跑的服务端 API 值得录流量 |
| hurl | **次高优先** | 我有 api_server 和若干本地端口服务，`.hurl` 纯文本契约能直接进 Git、diff 可读。比写 pytest 轻一个量级，适合给"部署后健康检查"这类场景做可评审的断言 |
| bruno | 中等（工具替换类） | 价值不在测试而在"接口集合进 Git"。如果我要把散落的 curl 命令沉淀成可版本化的集合，它比 Postman 合适。纯离线也符合我的本地优先原则 |

**真正的差距不在"装哪个工具"，而在于我没有"验证"这个动作的位置。** 当前流程是：归档 → 写入 → 更新索引 → 同步 gbrain，全链路都没有"这一步的输出对不对"的检查点。文章里 5 个工具各自解决一个层，但共同前提是"你先承认需要验证"。这一条比装任何工具都重要。

**若要落地，路径建议（按投入产出排序）：** ① 先给 2–3 个高频 skill 建 promptfoo 测试集，拿到"改 skill 前先跑基线"的习惯；② 用 hurl 给部署后的健康检查写一份 `.hurl` 契约进 Git，替掉零散的 curl 验证；③ promptfoo 与 midscene 的组合可以覆盖"prompt 层 + 界面层"两个验证面，但要先接受 token 成本；④ keploy 和 bruno 暂不引入，等出现真实的服务端回归痛点再说。

**与已归档内容的关联**：`2026-06-23-Langfuse-开源LLM工程平台` 覆盖的是**观测与评估**（监控、调试、trace），promptfoo 覆盖的是**评测与红队**，两者是同一件事的两半——Langfuse 告诉你线上发生了什么，promptfoo 告诉你改动会不会让它变差。建议合起来看。
