## 事件背景

code2rich 在过去一段时间做了三件看似不相关的事：fork 了 Multica 并改造其 Agent 管理和运行链路；做了 AgentWaker，用目录、配置和技能文件描述一个 Agent 的身份；给自己做了两个内容运营助手（微信公众号 + 小红书）。三个项目背后的核心问题是同一个：

> 当 Agent 从一次性的聊天窗口走出来以后，怎样让它拥有稳定身份、明确边界、真实运行环境，以及可以复查的交付结果？

## 核心观点 / 作者态度

### 1. Agent 需要源代码式的角色管理

身份、技能、权限、环境和记忆不能永远散落在聊天记录里。它们需要目录、schema、版本和校验器。

### 2. 角色定义和任务运行应该分层

AgentWaker 管角色契约，Multica 管工作区、任务、运行时和状态。两边通过明确的源同步协议连接。

### 3. 自动化是否可信，要看证据而不是演示

代码提交、校验结果、daemon 状态、草稿回读、作品 ID、平台指标，这些都比一句"任务已完成"更重要。

### 4. 先确保内容真实、动作有授权、结果能核验，再优化标题和选题

不要只追求夸张的指标——Agent 很容易学会制造看起来漂亮的报告，而不是改善真实工作。

## Multica 改造：角色供应链的五阶段

code2rich 对 Multica 的 fork 涉及 28 个提交、108 个文件、约 1.08 万行新增。五项改造构成一条"角色供应链"：

**1. 角色源**：AgentWaker 是本地目录。工作区只记录目录属于哪个 daemon、绝对路径和同步策略，不猜测本地路径，不越界读取文件。

**2. 扫描**：daemon 只识别契约（PROFILE.yaml、角色指令、技能、能力依赖、配置文件），返回结构化脱敏清单，不是把整个仓库打包上传。

**3. 快照与计划**：服务端保存不可变快照，与上一个已应用版本比较。差异检测 + 来源追踪 + 回滚空间。

**4. 运行时物化**：分别创建/更新 Agent、角色技能、共享能力和绑定关系。像信息采集、视觉生成等通用能力只维护一份，角色声明自己的权限和使用方式。

**5. 配置支线（.env）**：`env/.env` 参与同步，但扫描预览只显示变量名和状态；服务端解密保存；冲突时手工人肉值优先。秘密管理是主链，不是附件。

**6. 运行与入口**：Agent Runs 页面记录执行记录；接入微信 ClawBot / iLink 作为任务入口。

## AgentWaker：角色源代码

一个正式角色是一个有契约的目录：

- `PROFILE.yaml` — 机器可读身份与路由
- `agent-soul/` — 身份、工作方式、工具、记忆边界
- 角色技能目录 — 定义怎样做事
- `capabilities.yaml` — 声明共享能力依赖
- `env/` 和 `mcp/` — 真实运行配置

截至文章写作时，仓库有 **14 个正式角色** 和 **2 个共享能力**，全量验证通过。

## 两个运营助手的真实结果

### 微信公众号助手

- 目标：可靠进入草稿，不擅自发布、群发或删除
- 实现：调研 → 成稿 → 即页预览 → 草稿写入 → 回读验证
- 真实案例：《Agent 技术栈全景图》含 6 张图、6 个图注、6 个二级标题

### 小红书助手

- 生成标题、正文和 5-7 张图卡 → 发布检查 → 获得授权后调用本机 `xhs` CLI 发布 → 读取作品指标
- 真实数据：《Vibe Coding 做完的页面，怎么发给别人直接打开看？》发布于 7 月 15 日，77 浏览、6 赞、5 收藏、2 分享、2 评论

> "这些数字很小，我反而愿意把它们放出来。它们不是'增长案例'，只能证明一件事：这条链路真的从角色、选题和图片走到了平台发布，并且可以再读回来。"

## 即页（jpage.cn）的角色

即页在系统中承担"发布前的中间层"：长文先生成一个自包含 HTML 预览，确认后再进入微信草稿。让"生成内容"和"写入平台"不必绑死在一个动作里。

## 战略分析

**与 Hermes Agent 体系的高度相关性：**

这篇文章与 Hermes Agent 的架构理念有惊人的共鸣。code2rich 遇到的问题——角色定义散落、技能、工具、环境变量、长期记忆和交付标准分散在不同地方——正是 Hermes 通过 skill 系统和 CLAUDE.md/AGENTS.md 解决的问题。

**对照与差距：**

| 维度 | code2rich 方案 | Hermes Agent |
|------|---------------|-------------|
| 角色定义 | AgentWaker 目录（PROFILE.yaml + agent-soul/） | CLAUDE.md / AGENTS.md + skills/ 目录 |
| 技能管理 | 角色技能目录 + capabilities.yaml 共享能力 | skills/ 目录 + skill_manage |
| 运行时 | Multica（任务调度 + daemon + Codex/Claude Code） | Hermes CLI + gateway + 子代理 |
| 秘密管理 | env/.env 加密同步 + 服务端解析 | 环境变量 + config.yaml |
| 外部入口 | 微信 ClawBot / iLink | WeChat 平台接入已支持 |
| 校验器 | AgentWaker 验证器（路径/schema/MCP/env/集成全量） | Hermes skill Lint/Verify 机制 |
| 快照/回滚 | Multica 不可变快照 + 差异检测 | 无内建回滚机制 |

**最值得借鉴的点：**

1. **验证器文化** — "角色一多，最危险的不是少写一段漂亮文案，而是某个角色的路径错了、MCP 文件变成空文本、环境变量引用不存在。" code2rich 做了全量验证器（角色模板、schema、MCP、语言边界、运行时存储、secret 检查）。Hermes 的 skill 系统同样面临可验证性问题——一个 skill 有 5 个依赖文件但引用了不存在的路径，只在运行时才报错。借鉴方向：skill 注册时做静态验证。

2. **共享能力注册表** — "像信息采集、视觉生成这样的通用能力只维护一份，角色再声明自己的权限和使用方式"——这对应 Hermes 的 skill 依赖管理，但 Hermes 目前没有"能力声明"的显式机制（skills/ 里的每个 skill 是独立文件，没有 dependencies.yaml）。

3. **.env 作为主链** — 秘密管理不是补丁，是主链。Hermes 的 config.yaml 已经承担了部分职责，但 env 的脱敏、加密同步、冲突优先级可以借鉴其思路。

4. **源—快照—应用—运行—证据**五步链 — 这个闭环比"写 Prompt → 执行 → 结束"更完整。Hermes 目前有运行时和工具调用，但缺少"角色源定义→差异检测→原子应用"这一层的工程化。

**整合可能性：中高。** AgentWaker 的角色目录结构与 Hermes 的 skills/ 体系可以桥接。值得注意的是，code2rich 用的上游 Multica 和 AgentWaker 都是 GitHub 开源项目（MIT），可以直接参考其 PROFILE.yaml schema 和校验器实现。
