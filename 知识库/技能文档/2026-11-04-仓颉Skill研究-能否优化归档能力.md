# 仓颉 Skill 研究：能否优化归档能力

> 结论先行：**借它的流水线机制，不借它的产物形态。**
> 四个机制值得抄（断点续跑、覆盖审计、四分流、负例测试），核心架构不能抄（它产 SKILL，我产归档文档）。

## 一、为什么研究这个

用户看到仓颉 Skill 3.0 的宣传后提出：「能不能优化你的归档能力」。

诚实的前提：**仓颉解决的是「蒸馏」问题，我解决的是「归档」问题，两者目标不同。**

| 维度 | 仓颉 Skill | 我的归档 |
|---|---|---|
| 输入 | 一本书/一部长视频 | 一篇公众号文章/一个 GitHub 仓库 |
| 输出 | 一组可调用的 SKILL.md | 一篇可查阅的分析文档 |
| 成功标准 | 真实问题被 skill 解决 | 三个月后还能看懂当时看到什么 |
| 内容性质 | 方法论（**收敛**、稳定） | 时间切片（**发散**、带立场） |
| 重复调用 | 是（同一 skill 用多次） | 否（一篇归档看一次） |

**关键判断：把文章强行蒸馏成 skill，会丢掉文章的时间属性和作者立场——而这两样恰是知识库最值钱的部分。**

## 二、实测发现的真问题（比"缺方法"更严重）

扫描 374 篇归档的格式合规率（同时含 `## 战略分析` + `## 归档日志`）：

| 月份 | 合规率 | 备注 |
|---|---|---|
| 2026-05 | 13% (2/15) | |
| 2026-06 | **5% (6/112)** | **重灾区，106 篇缺战略分析** |
| 2026-07 | 42% (33/78) | |
| 2026-08 | 86% (25/29) | |
| 2026-09 | 91% (21/23) | |
| 2026-10 | 67% (18/27) | **回退** |
| 2026-11 | 100% (5/5) | |

另外 **77 篇文件名无日期前缀**（`no-date` 组，0% 合规）。

### 根因

`kb-archive-article` skill 里写着「REQUIRED on every archive」，但**没有硬性校验门**——执行时靠自觉，规范就退化成了愿望。

这与仓颉的根本洞察同构：

> **现有读书方法论都是为人类读者蒸馏，不是为 agent 执行者蒸馏。**
> 关键字段不同（故事/金句 vs trigger/可执行步骤），失败模式不同（读完就忘 vs trigger 不准），成功标准不同（读者"有收获" vs 真实问题被解决）。

我的归档规范同理：**清单是给人看的合规，不是给 agent 执行的门。**

## 三、可借的四个机制

### 1. `PIPELINE_STATE.md` — 断点续跑

仓颉把「当前阶段 + 进度」写进文件，中断后读文件续跑，不从头重来。

**我的痛点**：归档 PluginRSI 时达到工具调用上限，上下文被压缩，进度全靠摘要传递——摘要丢了就全丢。

**改造**：批量归档时每步落 `/tmp/kb_progress.json`，状态在磁盘不在上下文。

### 2. `coverage-audit.md` — 覆盖审计

仓颉的链路：`关键任务 → 原文位置 → 候选 → decision → 最终去向`，并且有一条硬规则：

> 重要机制即使只出现一次，也要有候选与明确去向；有未解释遗漏时补读，**不虚报零遗漏**。

**我的痛点**：「战略分析」全靠临场发挥，热点容易漏。上次归档 Auto-Ontology 时，发现三处文章偏差纯属直觉好。

### 3. 四分流 — `verified / reference / needs_review / rejected`

仓颉明确禁止为了凑数量把没依据的内容包装成方法论。特别值得抄的是 **`needs_review`（待核查）** 这个状态——它的规矩是：

> 重要但待核查的内容不能静默消失；没有完成参考映射也不能声称"知识已保留"。

**映射到我这边**：文章口径 vs 实测数据的冲突，应该有固定字段记录，而不是靠每次临场判断。

### 4. 负例（诱饵）测试 — `should_not_trigger` 容错为零

仓颉的硬规则：**没有诱饵测试的 skill 一律打回。**

> 因为只测 positive case，skill 总会看起来"很好"，但实际部署后会乱激活。

**映射到我这边**：应该建 6-8 个「不该这样归档」的回归用例：
- 抖音无效分享码（应报错，不该瞎猜）
- 图片引用路径错（`img_001.png` 写成 `./images/`）
- 计数不一致（导航行数 ≠ 文件数）
- 微信图片懒加载未触发（少图）
- 文章口径未核实（应标 needs_review 而非当事实写）

## 四、不能照搬的部分

仓颉的 RIA-TV++ 有七个阶段（Adler 理解 → 5 agent 并行提取 → 三重验证 → 晋级门 → RIA++ 能力卡 → Zettelkasten 链接 → 压力测试 → 编译交付）。

**对我全是杀鸡用牛刀**：

- **5 agent 并行提取**：一篇文章的方法论单元通常 ≤5 个，不值得开 5 个 sub-agent
- **晋升门**：我没有"要不要变成独立 skill"的问题，归档就是归档
- **编译与安装**：我的产物是 Markdown，不是可加载的 skill 包
- **压力测试的触发精度**：归档文档不参与 skill 触发路由

**唯一整体值得抄的是「单一事实源 + 确定性编译」这个思想**——仓颉的 single 和 pack 从同一份 Bundle 编译，引用同一组 capability_id。

映射过来：**`技能文档/` 是唯一事实源，`README.md` 和 `快速导航.md` 应该从文件系统自动推导，而不是手工 +1。**

我现在的做法就是手工改计数，这正是 2026-10 合规率回退 67% 的直接原因。

## 五、执行状态（用户已决定暂缓）

用户 2026-11-04 明确指示：「先不动吧」。

### 搁置的方案（随时可启动）

**A. skill 加硬性校验门**（不依赖外部，最优先）
```
归档完成后必须跑 validate：
- 战略分析 + 归档日志 存在
- 图片引用集合 == 磁盘文件集合
- 导航行数 == 文件数 == README 计数
不通过 → 不许报完成
```

**B. 归档日志加固定字段**（借四分流）
```markdown
## 归档日志
- 2026-11-04 归档
- 格式: A
- 核实: GitHub API 实测 star 1921（文章口径 1.9K）
- 缺口: README 未标注性能数据 → needs_review
- 遗留: 论文地址未核实 → 下次补
```

**C. 中途状态落盘**（借 PIPELINE_STATE）
批量归档每步写 `/tmp/kb_progress.json`。

### 需外部条件的方案

**D. 视频画面蒸馏**——`video-downloader` 2.1 能做：
- 输入视频 → 平台字幕优先 / 云端 ASR 兜底 → 选关键帧或切片
- 三种视觉模式：`keyframes`（最省）、`full-video`（完整，10 分钟分块）、`agent-clips`（推荐，先按字幕选片段再发视觉模型）
- 输出 `multimodal_transcript.md`（带时间戳纯文本），**仓颉侧不改**，只吃文本

**本机实测缺口**：
- ✅ `ffmpeg` = `/opt/homebrew/bin/ffmpeg`
- ❌ `yt-dlp` 未安装
- ❌ `LONGCAT_API_KEY` 未配置
- ❌ `ARK_API_KEY` 未配置
- ❌ `SILICONFLOW_API_KEY` 未配置

**这是知识库真正的天花板**——归档了大量视频教程内容，但那条链路目前靠截图和手工处理。

## 六、历史遗留（无法用工具修复）

**2026-06 那 106 篇缺战略分析** + **77 篇无日期前缀** 是历史数据问题，不是 skill 能补的。

补的话要逐篇重读重写。建议的处理方式：**标注清楚，不假装合规**——以后翻到 6 月篇目时知道那批是"摘录"不是"分析"。

## 战略分析

### 对现有工作流的判断

仓颉最有价值的不是它的七阶段流水线，而是**它把"质量"从形容词变成了可执行的门**：

- 「不能虚报零遗漏」→ 强制写 `coverage-audit.md`
- 「没有诱饵测试一律打回」→ 强制写 `should_not_trigger`
- 「重要但待核查的内容不能静默消失」→ 强制写 `needs-review.md`

这些都是**用文件的存在性作为质量证据**，而不是靠 agent 自评"我做得很仔细"。

我的归档 skill 恰恰缺这一层：清单写得很全，但清单本身不被检查。

### 与现有工具链的对照

| 能力 | 仓颉 | 我的现状 | 差距 |
|---|---|---|---|
| 断点续跑 | PIPELINE_STATE.md | 靠上下文摘要 | **有缺口** |
| 覆盖审计 | coverage-audit.md | 无（靠临场） | **有缺口** |
| 待核查状态 | needs_review.md | 无固定字段 | **有缺口** |
| 负例回归 | should_not_trigger | 无 | **有缺口** |
| 单一事实源 | Bundle → 编译 | 手工改计数 | **有缺口** |
| 视频画面蒸馏 | 配合 video-downloader 2.1 | 截图+手工 | **有缺口，缺 Key** |
| 文章归档 | 不是它的目标 | 已成熟（92% 近三月合规） | **我的强项** |
| 图片处理 | 不涉及 | 懒加载+逐张下载 | **我的强项** |
| 多源合并归档 | 不涉及 | 有专门流程 | **我的强项** |

### 结论

**不要在归档能力上全面对标仓颉——它的目标是另一个问题。**
真正该抄的是「质量门作为文件存在性」这一个思想，落成 A/B/C 三条就够用，成本很低。

D（视频链路）才是真正的能力跃迁，但需要先解决 Key 和 yt-dlp。
