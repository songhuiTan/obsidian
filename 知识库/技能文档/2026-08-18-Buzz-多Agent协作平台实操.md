# Buzz：多 Agent 协作平台实操全流程

> **一句话**：Jack Dorsey 公司 Block 开源的多 Agent 协作平台（GitHub 快 3 万星），把人和多个 Agent 放进同一个"群聊"里协作、上下文共享。作者用 Claude Code、Codex、Kimi、DeepSeek 四 Agent 完成一个真实项目，完整记录了接入方法、两次翻车、跑顺的流程和角色设定模板。

## 核心：Buzz 是什么？

- **来源**：Jack Dorsey 的公司 Block，2026 年 7 月下旬免费开源，GitHub 快 3 万星
- **形态**：长得像 Slack（国外版企业微信），只是群里的"同事"换成了 Agent
- **最大不同**：Agent 在这里地位和人一样——有自己的名字和身份，拉进频道 = 拉同事进群，也能 @ 别人（包括 @ 另一个 Agent）

**用之前要知道的三件事：**

1. **频道就是项目群**：做什么项目开一个频道，把项目要用的 Agent 和人拉进去
2. **频道消息所有成员可见**（Agent 也在内）：任务背景说一遍，每个 Agent 都知道了，不用挨个讲
3. **Agent 要被 @ 到才会干活**：没点名的 Agent 不会抢答，安静待着不花 token；被 @ 才去读消息开始动手

## CLI / Harness / 模型三者关系

- **CLI**：Agent 的运行载体（Claude Code、Codex、Kimi 等）
- **Harness**：Agent 的"工作方式"（官方自带 Buzz harness，也可用 Claude Code harness）
- **模型**：真正负责思考和回答的部分
- **关键**：Harness 和模型**可自由搭配**——比如用 Claude Code Harness 驱动 Kimi、DeepSeek 模型

## 接入步骤

1. **下载 Buzz**：GitHub 搜 Buzz，安装时选一个 harness（可直接用官方自带）
2. **接入 Agent**：Settings → Agents → Add runtimes；预设常见 agent，也可搜索；右下角 Setup guide 有详细教程
3. **自定义 Harness 与模型**：Agent 创建页设置信息；Harness 选已连接的；想用其他模型选 Custom model 填 API key；保存
4. **测试接入**：新建测试频道，加入 Agent，@ 它，能正确回复即成功

**⚠️ 常见坑：Agent 回复只出现在自己会话、频道看不到** → 在 Agent Instruction 加"回复发布规则"（最高优先级）：

> 你在会话中直接输出的文字，频道成员一律看不到。唯一有效的回复方式是执行 `buzz messages send`。每次处理完频道消息，最后一步必须执行：`buzz messages send --channel <频道UUID> --reply-to <触发消息的event_id> --content '<回复内容>'`。频道UUID和event_id必须从当前触发事件的Context中读取，禁止写死、禁止沿用历史值、禁止猜测。执行后检查命令返回结果：失败则重试一次，仍失败就把错误信息作为回复内容再次尝试发送报告。未成功执行 send 就等于没有回复。长内容（代码、文档、数据）以文件交付，频道里只发一句摘要和文件位置。

## 先设定角色，再开始干活（不能偷懒）

第一次让 Agent 自行协调分工 → 行不通，两个原因：
1. Agent 和人一样**很难自知**——认领的任务和实际能力对不上
2. Agent 会把前一个 Agent 的输出**默认当成正确答案**，方向偏了就一路偏下去

**作者的四角色设定（可直接参考）：**

| Agent | 角色 | 设定要点 |
|---|---|---|
| Claude | 项目经理兼产品经理 | 综合/推理最强：写需求文档、盯进度、做验收；验收时逐条对照需求文档给核对结果和证据 |
| Kimi | 前端工程师 | 只负责页面/图表/交互；严格按契约中的数据格式和接口约定开发，不猜测不自行修改约定；交付文件+接口调用说明 |
| ChatGPT（Codex 原生 Harness） | 数据与后端工程师 | 数据清洗、指标计算、前后端整合；发现原始数据异常先报告再处理，不静默修复 |
| DeepSeek | 经验沉淀员 | 平时不干活，任务验收完成后通读频道所有消息输出复盘：哪里卡住/什么有效可复用/下次注意什么，每条写成可执行的一句话 |

成本考量：判断和规划类的活给贵的强模型，简单机械的活给便宜模型。

## 第一次实战：两次翻车

- **翻车 1：让 Claude 当总指挥** → 整个频道停滞，所有成员等 Claude 发话，Claude 有时忘了用 @ 触发，对话断掉，最后人挨个催。**协调 Agent 站在指挥链上，它就是瓶颈**（管理失灵在 Agent 团队一样存在）
- **翻车 2：自动接力** → 每个 Agent 干完自动叫下一个 → 前端还没预览确认，后端就开工，返工成本高。**全自动接力等于把人踢出了流程**

> 结论：流程还没成熟到可以完全放手的程度，**该人确认的节点，就得停下来等人**。

## 最后跑顺的流程

取消 Agent 协调，主节奏由人控制，Claude 定位改成"问询台"（碰到问题直接问它，它不打断正在干活的成员）。

1. **开工前先测试**：@ 每个 Agent，确认都能收到消息、回复能进频道
2. **背景介绍 + 自我介绍**：先交代任务背景发相关文档，再让每个 Agent 自我介绍职责——Agent 之间互相 @ 的前提是知道对方能干什么（和人上班先认识同事一个道理）
3. **按需 @ Agent**：一次只叫当前环节需要的 Agent。本项目顺序：前端先出一版风格页 → 人预览确认 → 再写全部页面 → 页面完成确认 → 同时 @ 前端和 @ 后端直接对接（接口、数据格式它们自己在频道里对齐）
4. **独立 Agent 验收代码**：让写代码的 Agent 自己测试 = 选手兼评委。让全程没参与写代码的 Claude 独立验收：①自己启动服务调接口跑一遍检查报错 ②对照需求文档逐条检查功能 ③代码层面查隐患（数据为空会不会崩、重启后数据还在不在）

**两个实用技巧：**
- 频道不支持直接传 HTML 文件 → 让 Agent 发文件的绝对路径 + 执行 `open` 命令直接浏览器打开（写进前端角色指令）
- 角色规则别写太细：给创造类工作定方向就够了，细节留给专业的 Agent（写太细页面反而死板）

## Buzz 的三个局限（如实说）

1. **角色不能按频道设置**：Agent 的角色设定在它所有频道生效 → 多任务场景：角色里只写能力和通用规则，具体分工写进频道 Canvas，任务指令里要求先读 Canvas
2. **速度不算快**：Agent 响应有几秒延迟（本地跑，机器性能和订阅额度是瓶颈）
3. **产品还很早期**：自带 Agent 突然失效、频道传不了 HTML 等小毛病；迭代飞快（实测当天更新两次）

## 什么时候用多 Agent（比工具更值得想清楚）

**适合：** ①能发挥不同 Agent 长处的任务（如前后端开发）②头脑风暴（没有标准答案的讨论，不同模型视角互相碰撞）

**不适合：** 单 Agent 能解决的事（如日常热点推送，一个脚本加自动化流程就够了）

**三个判断问题（有两个否定就别用）：**
1. 用多个 Agent，效果会比单个更好吗？
2. 能更省钱、更省 token 吗？
3. 收益能盖过你做协调的成本吗？

## 战略分析

**1. 与现有栈的关系（Hermes / AgentDesk / J-Space 三件套对照）：**

| 维度 | Buzz | AgentDesk | J-Space | Hermes 现状 |
|---|---|---|---|---|
| 形态 | Slack 式群聊平台 | Codex Skill 项目治理 | 推理时控制套件 | 单会话 + delegate_task |
| 交互 | @ 触发、频道共享上下文 | 任务卡 + 回调回执 | 账本 + 验证 | 直接对话 |
| 权威 | 频道消息流 | tasks.yaml | 工作空间账本 | 会话上下文 |
| 协调 | 人控主节奏（作者实证） | PM 租约 + 门禁 | 流程约束 | 幕僚长 |
| 缺点 | 无任务状态/验收机制 | 重、依赖 Codex API | 单模型 | 无跨 Agent 持久协作 |

Buzz 补上了"共享上下文 + 多模型同台"这层——它不做任务治理（AgentDesk 做）、不做推理控制（J-Space 做），只做**协作容器**。三者其实是同一趋势的三个切面：多 Agent 协作正在从"技术问题"变成"管理问题"。

**2. 作者踩坑史 = 多 Agent 管理铁律（对任何平台适用）：**
- 协调 Agent 是瓶颈 → 人控主节奏，Agent 只做问询台
- 全自动接力 = 把人踢出流程 → 关键节点必须停下来等人确认
- 写代码的不能自己验收 → 独立验收 Agent（"选手兼评委"偏差）
- Agent 会把前一个输出当正确答案 → 角色边界 + 验收门禁
- 这五条与 AgentDesk 的"验收≠集成、报告≠回调、独立验收"设计哲学完全同构——平台可以不同，管理原则相通

**3. 对用户的价值：**
- **最直接的启发是"经验沉淀员"角色**：DeepSeek 任务后通读全频道输出可执行复盘——这正好可以做成 Hermes 的复盘 Skill（收尾包的自然延伸）
- **"回复发布规则"模式**：把"如何正确回复"写进 Agent 指令作为最高优先级——对 Hermes 接入其他平台（微信群发）有直接借鉴意义
- 多 Agent 要不要上的三个判断问题：效果更好？省钱？收益盖过协调成本？——简单可用的决策框架
