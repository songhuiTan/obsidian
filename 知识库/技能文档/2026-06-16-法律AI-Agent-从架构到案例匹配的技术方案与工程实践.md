## 核心定位：四级漏斗

```
用户描述问题
    ↓
第一层：案情导诊 —— 判断法律问题类型、评估严重程度、行动方向
    ↓
第二层：案例匹配 —— 检索相似案例、分析判决结果、提供辩护思路
    ↓
第三层：自助工具 —— 生成法律文书、流程指引、证据清单
    ↓
第四层：律师匹配 —— 按领域/地区推荐律师
```

## 一、案例匹配：LangGraph 工作流编排

4 Stage 非线性流程，包含信息缺失回退和重试循环。

```python
from langgraph.graph import StateGraph, END

class LegalCaseState(TypedDict):
    user_input: str
    structured: Optional[dict]          # Stage 1 结构化结果
    missing_info: List[str]             # 缺失的关键信息
    tag_filtered_ids: List[str]         # 标签过滤后的候选 ID
    recall_candidates: List[dict]       # 向量召回结果
    reranked_top5: List[dict]           # 精排结果
    output: Optional[dict]              # 最终产出
    retry_count: int                    # 重试次数
    max_retries: int                    # 最大重试

workflow = StateGraph(LegalCaseState)
# ...节点注册 + 条件边：信息缺失→反问，精排不达标→放宽重试
```

## 二、Stage 1：案情结构化

Pydantic Output Parser 将口语化描述转结构化法律要素，`missing_info` 字段驱动反问节点。

---

## 三、Stage 2：多路召回

**ES 标签过滤（第一级）：** 按案由、年份、要素快速缩小候选集（千万级→万级）

**Qdrant 向量检索（第二级）：** bge-m3（1024维）做语义检索，混合权重 0.6× 向量 + 0.4× 标签匹配

**为什么先过滤再检索：** "法律关系相似" ≠ "事实描述相似"，标签过滤确保候选集在法律关系上是同类的。

**重试策略：** 案由扩大→去掉年份限制→全库检索

---

## 四、Stage 3：LLM 精排

四维评分：案由匹配度 ×0.3 + 事实相似度 ×0.3 + 争议焦点 ×0.2 + 参考价值 ×0.2

---

## 五、Guardrail 三层校验链

1. **Agent 自检** — 拦截"保证""一定""100%""肯定赢"等绝对化表述
2. **规则拦截** — 刑事/行政案件必须建议咨询律师；必须包含免责声明
3. **法条引用校验** — 精确查询校验，不用向量检索（法条原文一字不能差）

> 法律 Agent 和其他场景最大的不同是：**给错了建议，用户可能真的会输掉官司。**
> Guardrail 是代码逻辑强制追加的，不是 LLM 自觉加上的。

## 六、V2.0 五个关键升级

### 6.1 CrossEncoder 初排
V1.0（LLM看50个→TOP5）→ V2.0（LLM看20个），**成本降低60%**

| 方案 | 单次成本 | 延迟 |
|------|---------|------|
| LLM直接看50个 | $$$ | 10-20s |
| CrossEncoder 50→20 + LLM看20个 | $ | 2-3s |

选型：bge-reranker-v2-m3（中英文混写更优）或 Qwen3-Reranker（纯中文略优）

### 6.2 法条优先 + 联合推理
中国是**成文法系**，不是判例法。V1.0 只做了"事实→经验"，V2.0 补齐法条检索和联合推理。

```
V1.0: 案情结构化 → 案例检索 → 策略推荐
V2.0: 案情结构化 → ┌── 法条检索 (Law RAG)
                    ├── 案例检索 (Case RAG)
                    └── 联合推理 (Legal Reasoner)
```

输出结构：法律依据 → 相似案例参考 → 策略建议

### 6.3 法律知识图谱（Neo4j）
三元组：`法条 — [适用于] → 场景` + `法条 — [关联] → 概念` + `案例 — [依据] → 法条`

核心价值：法条变更追踪（新法替代旧法时自动溯源最新版本）

### 6.4 Case Memory（DuckDB）
跨会话案件上下文。同一用户多轮对话不再重复做结构化抽取。

### 6.5 MCP Tool Layer
接入外部数据源：企业信息(天眼查)、法院公告、律师执业信息、裁判文书网

## V1.0 → V2.0 架构演进对照

| 层级 | V1.0 | V2.0 |
|------|------|------|
| 工作流编排 | LangGraph StateGraph | + Memory 路由 |
| 结构化抽取 | LLM + Pydantic | + Case Memory 跳过 |
| 法条检索 | ES 精确查询 | Law RAG + 知识图谱(Neo4j) |
| 标签过滤 | Elasticsearch | 同上 |
| 向量检索 | Qdrant + bge-m3 | 同上 |
| 初排 | 无 | CrossEncoder (50→20) |
| 精排 | LLM看50个→TOP5 | LLM看20个→TOP5 |
| 联合推理 | 案例→策略建议 | 法条+案例+MCP工具联合推理 |
| 法条校验 | ES精确查询 | + 图谱变更追踪 |
| 跨会话记忆 | 无 | DuckDB Case Memory |
| 外部工具 | 无 | MCP Tool Layer |
| Guardrail | Condition + 规则 | + 法条版本校验 |

## 关键工程决策（7条）

1. 用 LangGraph 而不是 Chain — 流程带环（反问回退、重试放宽）
2. 先 ES 标签过滤再 Qdrant — 不是全库向量搜索
3. 裁判文书必须预处理提取 — 不用原文 Embedding（超512 token质量下降）
4. CrossEncoder 做初排，LLM只看20个 — 成本降低60%
5. 法条召回优先于案例召回 — 中国是成文法系
6. 法条引用用精确查询校验 — 不用向量检索
7. Guardrail 是代码逻辑 — 不是说一句"仅供参考"
