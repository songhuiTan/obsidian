# DeepSeek Harness 缓存优化源码拆解：旧内容不改，新内容后加

> **一句话**：叶小钗拆解 DeepSeek Harness 如何做到 99% 缓存命中率——核心就一条原则：**旧内容不改，新内容后加**（稳定内容固定在前，可变内容追加到尾部）。缓存命中与未命中价格差 30 倍，从 90% 提到 99%，输入费用再省 2/3。

## 先算个账：缓存差价 30 倍

DeepSeek 官方定价（元/百万 token）：

| 计费项 | v4-flash 空闲 | v4-flash 高峰 | v4-pro 空闲 | v4-pro 高峰 |
|---|---|---|---|---|
| 输入且缓存命中 | 0.05 | 0.10 | 0.15 | 0.30 |
| 输入且缓存未命中 | 1.50 | 3.00 | 4.50 | 9.00 |
| 输出 | 4.50 | 9.00 | 13.50 | 27.00 |

**缓存命中与未命中差价恒为 30 倍。** 实际输入单价 = 命中率 × 命中价 + 未命中比例 × 未命中价（v4-flash 高峰价）：

| 命中率 | 100 万输入 token 实际价格 | 相当于全未命中 |
|---|---|---|
| 0% | 3.000 元 | 100% |
| 90% | 0.390 元 | 13% |
| **99%** | **0.129 元** | **4.3%** |

从 90% → 99% 只多 9 个百分点，费用又少 2/3。**多轮 Agent（每轮累加发送系统提示+工具+历史）正是缓存优化的最大受益者**——Agent 每做一步都把前面的内容重发几遍，命中率直接决定账单。

## 缓存原理与规则

- **原理**：LLM 推理两阶段——prefill（对所有输入 token 做前向计算生成 KV 状态，**长上下文成本大头在这**）→ decode（逐个输出 token）。缓存把请求输入部分的 KV 状态**存到硬盘**，下个请求开头完全一致时直接加载，跳过绝大部分 prefill
- **规则**：①默认开启，无需开关 ②从请求第一个 token 开始对比（**前缀命中**）③按完整前缀单元命中（用户输入结束、模型输出结束、长文本固定间隔处保存）④公共前缀可能要到下一轮才沉淀（发 A+B 再发 A+C 后，A 才被单独保存，第三次 A+D 命中）⑤会过期（几小时到几天，构建也要几秒，尽力而为不承诺）
- **查看**：响应里的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 两字段

## Agent 很容易把缓存弄丢（四种典型）

1. **系统提示每轮变化**：时间/当前目录/权限状态/随机 ID 拼进提示词头部——最容易提前截断缓存
2. **工具列表顺序不稳定**：工具个数和 Schema 没变，但序列化顺序变了（read/bash/edit → bash/edit/read），工具说明位于历史之前就会丢缓存
3. **每轮重新整理历史消息**：重排消息、重新生成 XML/JSON、改写之前消息——多一个空格、字段顺序变化都是新 token 序列
4. **请求参数后台变化**：额度/超时自动切换模型或服务商、插件动态注入系统提示——形成新请求前缀

> 理想状态：**前面的内容尽量保持不动，新的、容易变化的内容不断往尾部追加**——会话越长，可复用前缀越长。

## DeepSeek Harness 五步实现

### 第 1 步：稳定内容和可变内容分开
插件把内容交给统一登记处（系统提示 `section()`、工具 `tools()`、可变状态 `context()`、填充值 `variable()`），Harness 组装时统一决定顺序。判断放哪看**会话运行期间会不会变化**（工作目录不变就留在系统提示里；沙箱模式/审批策略/子 Agent 权限会变就按可变处理）。

### 第 2 步：每一轮按同样规则排序
每轮重新取出内容按同一套规则组装：系统提示按登记编号、工具按名称排序。**顺序稳定才能保证 token 前缀稳定**；动态注入值（模型名/工作目录）参数名错误或取不到值，请求发出前报错。

### 第 3 步：可变状态追加到历史末尾（最关键的缓存设计）
运行时状态（沙箱/审批/权限）整理成 runtime context 快照：每轮与上一轮比较——**内容相同不重复发送；内容变了生成新消息追加到会话末尾；上一轮状态清空也追加一条清空消息**。变化只追加在尾部，前面的 system/tools/历史保持原样，下一轮就能复用长前缀。

### 第 4 步：把请求的固定部分记下来
模型名、温度、最大输出长度等调用参数连同系统提示和工具列表记进会话日志：第一次写完整记录，**后面只有内容真的变了才新增变化记录**——缓存命中率突然下降时，查日志找是哪一轮、改了什么。

### 第 5 步：每次都从同一份日志还原请求
每轮从日志取回用户消息/模型回答/工具结果，系统提示/工具/参数从 request header 取——两部分合起来即完整请求。**组装好即冻结**：发送插件可查看但不可临时改；发送前逐项核对，对不上就报错不发送。模型回复追加回日志，下一轮照旧还原。

## 自查清单（自己做 Agent 时照着检查）

1. 系统提示的各段内容要有**固定名字和固定顺序**
2. 当前时间、随机编号和环境状态**放到消息尾部**
3. 工具按名字或明确配置排序，**工具参数的字段顺序也要稳定**
4. 历史消息**只追加，少做每轮重排和改写**
5. 模型、服务商和参数发生变化时，**留下明确记录**
6. 上下文压缩时，尽量**保留前面仍可复用的内容**

## 战略分析

**1. 与用户场景直接相关（本机就是 DeepSeek）：** 当前 Hermes 用的正是 deepseek-v4-flash——多轮归档/研究任务每次都要十几轮工具调用，每轮重发系统提示+工具列表+历史消息。**缓存命中率就是实际账单**。这篇文章的六条自查清单可以直接对照 Hermes：系统提示是否每轮稳定？工具列表是否稳定排序？动态信息（时间戳等）是否在头部？

**2. 与最近归档的"上下文工程"谱系汇合：**

| 维度 | DeepSeek Harness | J-Space 账本 | Prime Agent RLM | 轻量化业务应用 |
|---|---|---|---|---|
| 核心 | 前缀稳定（旧不改新后加） | 状态显式记账 | 上下文变量化 | Workflow/Task/Node |
| 共同点 | **都是"上下文管理"的工程化**——隐式窗口 → 显式控制 |

缓存优化本质是"上下文工程"的成本维度；J-Space/RLM 是质量维度（不丢目标/可编程）。**质量与成本两面已闭合**：既管上下文内容对不对，也管上下文发送省不省钱。

**3. 值得直接采用的实践：**
- 系统提示稳定化 + 工具排序稳定化——如果 Hermes 组装请求时工具顺序有抖动，值得检查
- 动态信息（时间/环境）放尾部而非头部
- 监控 `prompt_cache_hit_tokens` 字段，建立缓存命中率基线，异常下降时查日志
- 上下文压缩策略保留前缀可复用部分（六条清单第 6 条——与"轻量化"的渐进式验证呼应）
