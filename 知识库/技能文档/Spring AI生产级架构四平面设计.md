# Spring AI 生产级进阶实战：RAG、Tool Calling、流式会话与多模型路由的架构闭环

> 以电商智能客服与售后助手为业务主线，从控制面、执行面、状态面、治理面四个层次，系统讲透 Spring AI 在企业级落地中的关键设计。

---

## 一、为什么 Spring AI 一到生产环境就变难

Demo 阶段：ChatClient → 系统 Prompt → RAG → Tool → 流式输出，足够惊艳。

线上阶段：**六个维度同时失控——**

| 维度 | 表现 |
|------|------|
| 🎯 回答正确性 | 知识过期、召回错位、上下文污染 |
| ⚠️ 工具调用风险 | 读写混用、不完整参数、未经确认触发退款/发券 |
| 📊 并发与资源 | 长连接/Embedding/向量检索/模型调用同时争抢资源 |
| 💰 成本 | 全部走强模型，上下文无限增长 |
| 🔄 状态 | 会话中间态分散多个服务，无法复盘 |
| 🔍 治理 | 无法解释回答了为什么、触发了什么、切换了哪个模型 |

> **真正的难点从来不是 API 调用，而是如何把 AI 能力纳入后端系统早已成熟的工程治理框架中。**

## 二、业务主线：电商智能客服与售后助手

| 能力 | 说明 | 风险点 |
|------|------|--------|
| 售前问答 | 商品规格、发货时效、优惠规则 | 知识过期、规则冲突 |
| 售后问答 | 退货规则、退款进度、运费承担 | 幻觉回答、政策错引 |
| 订单查询 | 订单状态、物流节点、支付状态 | 参数校验、越权访问 |
| 售后发起 | 创建退货单、退款申请、补发工单 | 幂等、确认、补偿 |
| 智能路由 | 简单问题走低成本模型，复杂问题走强模型 | 成本与稳定性平衡 |
| 流式对话 | 字符级输出、可取消、断线可恢复 | 连接风暴、状态管理 |

## 三、四平面架构（核心）

### 3.1 控制面（如何运行）
模型路由规则、Prompt 模板管理、Tool 开关与权限策略、RAG 召回策略、限流/超时/降级/灰度配置、成本预算与租户配额
→ **配置化，不硬编码，切换不发版**

### 3.2 执行面（处理请求）
会话接入 → 上下文组装 → RAG 检索 → Tool 调用 → 模型生成 → 流式输出
→ **低延迟、可并发、无状态优先**

### 3.3 状态面（不能丢的中间状态）
会话历史与摘要、Tool 调用记录、用户确认状态、幂等键与执行结果、知识版本与索引版本、长连接会话状态
→ **绝不能只靠内存，否则扩容后语义错乱**

### 3.4 治理面（系统是否可控）
每次回答引用的文档、Tool 触发上下文、模型切换原因、token/延迟/错误率、高风险动作确认与审计
→ **没有治理面，AI 系统进不了核心链路**

```
                     ┌──────────────────────────┐
                     │    控制面 Control Plane    │
                     │ Prompt/Routing/Policy/Quota│
                     └──────────┬───────────────┘
                                │
┌────────────┐          ┌──────▼────────┐
│ Client     │ SSE/HTTP │ AI Gateway    │
│ Web/App    ├─────────►│ Auth/RateLimit │
└────────────┘          │ Trace/Tenant   │
                        └──────┬────────┘
                               │
              ┌────────────────▼──────────────────────┐
              │ 执行面 Execution Plane                │
              │ Session Orchestrator                  │
              │ RAG Retriever / Tool Gateway          │
              │ Model Router / Stream Dispatcher      │
              └───────┬────────────────┬─────────────┘
                      │                │
         ┌────────────▼───┐    ┌──────▼─────────────┐
         │ 状态面 State    │    │ 治理面 Governance   │
         │ Redis/Postgres │    │ Metrics/Tracing     │
         │ Checkpoint/Sum │    │ Audit/Cost/Alert    │
         └────────────────┘    └────────────────────┘
```

## 五、生产级 RAG 知识链路设计

### 5.1 知识链路分层
```
知识源 → 文档采集 → 文本清洗 → 结构化抽取 → 语义分块 → Embedding → 索引构建 → 版本发布 → 在线检索 → 证据回填
```

知识源不仅仅是 PDF/Word，还包括商品字段、售后规则表、CMS 公告、物流 SLA、FAQ、客服 SOP 等。

### 5.2 文档版本与灰度（核心必做）
知识库至少三个状态：`draft` → `ready` → `active`
线上检索显式带 `knowledge_version`，回答可复现、升级可回滚。

### 5.3 生产级分块策略
- 优先按标题层级切 → 按段落边界 → 表格/代码/规则保持整体
- 有限重叠（如 60 token overlap）避免语义断裂
- 附带元数据支持过滤与解释

## 六、Tool Gateway 设计要点

- **区分查询型与副作用型 Tool**
- **高风险 Tool 需确认令牌 + 幂等键 + 补偿机制**
- **Tool 输出结构化**：关键字段显式映射与异常兜底
- **独立超时与隔离资源池**

---

## 七、生产陷阱与上线检查清单

### 常见陷阱
1. ❌ 把 AI 调用写进同步事务 → 事务变长、连接池被拖垮
2. ❌ 把会话历史全量塞给模型 → token 激增、首字延迟上升
3. ❌ 把 Tool 输出当成天然可信 → 下游异常被放大
4. ❌ 没有知识版本 → 回答无法复现、不敢更新
5. ❌ 用一个强模型解决所有问题 → 高成本、高延迟、低稳定性

### 上线前检查
- ✅ 控制面/执行面/状态面/治理面分离清楚
- ✅ 查询型与副作用型 Tool 区分、高风险 Tool 确认令牌+幂等键
- ✅ 知识库有版本与回滚策略
- ✅ 租户级/用户级/能力级限流 + provider 熔断降级
- ✅ 记录模型路由原因、知识版本和引用片段
- ✅ RAG 按权限过滤、Tool 校验对象归属、输出脱敏

## 八、总结

> **Spring AI 的真正价值，不是「让 Java 也能调大模型」，而是让 AI 能力沿着 Spring 生态已经验证多年的工程化路径落地。**

优先做好三件事：
1. **RAG 做成可版本化、可灰度、可审计的知识系统**，不是一次性导库工具
2. **Tool 做成有权限、有确认、有幂等、有补偿的受控能力**，不是模型直连业务接口
3. **流式会话、多模型路由、成本观测纳入治理面**，不是等流量上来再补洞
