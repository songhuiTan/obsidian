# RAG这次真死了！SAG2才是本地知识库的神，又快又准又便宜～

## 一句话概括

SAG2 把 RAG 的路线**反过来走**：建库阶段不调任何大模型、不做 Embedding、不要向量库、不要 GPU，只对原文建 BM25 关键词倒排索引；语义判断推迟到查询时，由一个专用小模型 JEV 逐轮判断"这段是不是有用证据"。结果是建库从 4.57 小时降到 2.36 秒（约 7000 倍），准确率不降反升。

---

## 一、问题：知识库的不可能三角

作者从 2024 年初裸辞 All in AI 起就在做知识库交付，踩过的坑按时间顺序是：

| 坑 | 具体表现 |
|---|---|
| **分块** | 张三负责 A 项目和 500 万预算被切成两段，线索就断了 |
| **调优** | score 调低噪音多、调高漏东西，按下葫芦浮起瓢。朋友公司组 6 人团队花半年才把准确率调到可用 |
| **维护** | 文件一改就得重新上传、重新切块、重新向量化 |
| **预处理** | 一代仍需调大模型逐段提取事项和实体，建库耗时长 |

**不可能三角**：又轻、又便宜、又准——过去最多满足两个。

## 二、技术演化：每一步都是"入库多花钱换检索准度"

| 阶段 | 方案 | 做法 | 代价 |
|---|---|---|---|
| 2020 | **RAG 原始论文**（Meta/Facebook） | 资料切小块 → 转向量 → 提问找最相似的块 | — |
| 2023+ | **FastGPT / Dify** | 把上面流程做成 UI 点点点 | 单文档问答够用，**多跳不行** |
| 之后 | **混合检索**（全文+向量+重排） | 工业标配，至今最成熟 | 多跳依然断链 |
| 2024 | **GraphRAG**（微软开源）→ LightRAG → HippoRAG 2 | 入库前让大模型抽出人名/公司/事件关系，画成大图 | **贵且重**，索引阶段大量调模型，新文件进来关系要重算 |
| 2026.04 | **LLM Wiki**（Karpaci 分享） | 大模型读原始资料编译成 wiki 页面，对 wiki 问答，结果回填 | 对个人知识整理友好，但资料多则逐篇读写的 Token 和时间上去；原文一改页面要重写 |
| 2026 初 | **NotebookLM**（Google） | 资料扔进去问答/摘要/生成播客 | 要传云端、每本有来源上限、本地 Agent 不便调用 |
| 一代 | **SAG** | 不画全局大图，只提炼事项和实体，查询时用 SQL 串线索 | 比 GraphRAG 轻，但工程上仍需逐段提取 |

### 多跳断链的经典例子

```
文档1：A公司全资收购了B公司。
文档2：张三被任命为A公司的CTO。
文档3：张三离职，加入了盘古大模型项目。

问：收购了B公司的企业，其CTO后来加入了哪个项目？
```

文档 3 里"收购""B公司""CTO"一个词都没有 → 纯向量检索线索就断了。

## 三、SAG2 的分工：BM25 粗筛 + JEV 判断

**建库阶段**：一个模型都不调。直接对原文建关键词索引，用 **BM25** 打分。

> BM25 是 90 年代的老算法，Elasticsearch 默认打分用的就是它。

**查询阶段**：靠 **JEV** 补语义。

> JEV 是前 OpenAI 研究员 **Diogo Almeida** 9 月发布的模型。它不能写文章、不能聊天——你给问题和候选内容，它只回一个判断和打分，但又快又便宜。

**循环流程**：
1. BM25 粗筛出候选段落
2. JEV 判断哪些是有用证据
3. 算法从有用段落里挑出关键词，接着往下搜
4. JEV 结合已找到的证据，判断新找到的内容
5. 重复直到收敛

### 同一个张三例子的 SAG2 走法

| 轮次 | 动作 | 命中 | 得到线索 |
|---|---|---|---|
| 1 | 搜"收购 / B公司" | 文档1 | JEV 判有用 → 挑出关键词 **A公司** |
| 2 | 搜"A公司" | 文档2 | 得知 CTO 是 **张三** |
| 3 | 搜"张三" | 文档3 | **盘古大模型项目** ✅ |

**关键变化**：一代串线索靠提前抽好的"事项和实体"；SAG2 换成**关键词和段落**——一个关键词连多个段落、一个段落含多个关键词，**这些联系直接来自原文，无需任何预处理**。

> 作者比喻：以前是图书馆开张前先请人把每本书读一遍写好卡片；现在是管理员拿着目录飞快翻，旁边站个老师傅，每递一本扫一眼就告诉你这本有没有用。

## 四、性能数据（实测）

**建库速度**（同样 11,656 段文本，M4 Pro / 64GB 内存，从空库连续重建三次取中位数）：

| | 建库耗时 | Token 消耗 |
|---|---|---|
| SAG 一代（原论文） | 4.57 小时 | 2,826 万 tokens |
| **SAG2** | **2.36 秒** | **0** |
| 差距 | **约 7,000 倍** | — |

**检索准确率**：

| 基准 | 结果 |
|---|---|
| MuSiQue（最难）Recall@5 | **80.68%**（一代 80.04%，**比 HippoRAG 2 高 15.55 个百分点**） |
| 三个多跳检索测试集 | **8 项指标全部第一** |
| EnterpriseRAG-Bench（51 万份模拟企业邮件/工单/会议记录） | 建库 **8 分 32 秒**，文档 Recall@10 **81.10%**；LightRAG / MS-GraphRAG / HippoRAG 2 这些图谱方案**都没跑完全量** |

> 作者原话："我本来以为砍掉预处理效果得退一点，结果没退反进。"

## 五、SAG Wiki 桌面端（可直接用的成品）

- **体积**：Windows 约 **13 MB**，macOS 约 **18 MB**
- **用法**：添加一个本地文件夹就是知识库，**文件不用动，改了自动增量更新**
- **配置两步**：
  1. **问答模型**（生成回答）—— 可按需自选，作者配的是 DeepSeek V4.1 Flash
  2. **决策模型**（找线索）—— 官方论文用 TypeSafe 的 Jev，是**官方固定的决策模型**，填入对应 Jev Key；有需要也可改成别的决策模型
- **格式支持**：常见格式全索引，**连音频、视频都能识别** → 设置 → 文件设置 → 其他格式

## 六、四组实测场景

### 1️⃣ 查自己的 383 篇历史公众号文章

- 问"之前蒸馏公众号文章时，到底处理了多少篇、多少字？"
- **搜两次**翻出对应文章，直接给出准确数字：**138 篇、79 万字**
- 追问"之前有哪些把视频或多模态工具通过 CLI/Skill 接进 Agent 的实测？"
- 把整个历史文章翻遍，从不同文章挑出 **LibTV、拓、Remotion** 等案例，工具/接法/标题/日期排成表格，点引用直达原文

### 2️⃣ 六度分隔：李白和爱因斯坦怎么联系起来（10 万词条维基库）

整机索引 **100,461 个文件**（10 万维基词条 + 其他目录），建库时间"上个厕所回来就搞定"。

用 Claude Code 跑两组对比：`Claude Code + DeepSeek` vs `Claude Code + DeepSeek + SAG2`，只给"李白""爱因斯坦"两个名字，要求每步必须有确凿出处、绝不瞎编。

| 组别 | 路径 | 评价 |
|---|---|---|
| 原生组 | 翻出刘慈欣作品——**《朝闻道》**（又名爱因斯坦赤道）与**《诗云》**（又名李白），在科幻作品集里同框 | 巧但属于"同名词巧合"，不是真关联 |
| **SAG2 组** | 关键词定位到学者**林庚** → 追查生平：年轻时在清华物理系痴迷爱因斯坦相对论，后来成为写出**《诗人李白》**的文学巨擘 | **从相对论连到林庚，再连回李白，两头全有原文可查** ✅ |

### 3️⃣ 26 份半导体深度研报查供应链

问题：英伟达 H100 用 SK 海力士 HBM3、MR-MUF 封装，**谁给 SK 海力士独家供应核心底层填充胶水（Underfill）？**

| 组别 | 结果 |
|---|---|
| **SAG2** | **仅 3 次工具调用**找到核心段落，一击命中 **Namics** 的供货原句 |
| 原生组 | 各文档里无头苍蝇乱翻，**第 11 次调用**才勉强蒙对 |

### 4️⃣ 代码排错：SAG Wiki v0.2.6 源码查 Jev 网络错误重试逻辑

| 组别 | 结果 | 耗时 |
|---|---|---|
| 原生组 | 抓出一堆文件逐个打开看 | 144 秒 |
| **SAG2** | 直接带回文件、行号、关键代码，明确命中 **HTTP 499 状态码重试时不增加失败计数** | **95 秒** |

> 结论：SAG2 不只适合超大规模快速检索，**数据量不大的场景也比原生模型强得多**。

## 七、作者的核心观点

> 这几年大家好像都卷进一种技术执念：模型参数越来越大，向量数据库要搞集群，系统越做越大、越贵，门槛越来越高。
>
> 但 SAG2 完全相反。它没搞重型架构，也没扯虚头巴脑的概念，反而退回到 Unix 最朴素的一句话：**一切皆文件**。
>
> 用了几十年的 BM25 倒排索引，用轻巧灵动的动态超边，把繁重的计算**推迟到真正需要的那一刻**。
>
> 用十几 MB 的体积、几秒钟的建库速度，把曾经无比困难的多跳推理能力，**平权交到了每一个普通人手里**（当然也得感谢 JEV，新技术的突破往往能带动其他技术突破）。
>
> 大道至简，少则得，多则惑。

## 八、批判性评估（归档者按）

> ⚠️ 以下是本地归档时的独立判断，非原文内容。

### ✅ 值得信的部分

1. **建库 7000 倍加速的逻辑成立**。BM25 索引是 CPU 上的字符串处理，2.36 秒建 11,656 段的倒排索引完全在合理量级；一代 4.57 小时 + 2826 万 token 的代价也符合"逐段调大模型抽实体"的成本结构。这不是营销数字，是机制差异的必然结果。
2. **"推迟计算"是真正的架构洞察**。GraphRAG 系列的根本问题就是把语义理解全部前置到索引期，导致①建库贵②文件一改就得重算③新文件进来关系要重算。SAG2 把语义判断搬到查询期，用"关键词↔段落"这种原文天然存在的结构做链接，绕开了全部三个问题。**这个思路可以迁移**：任何"预处理很贵、查询很便宜"的场景都适用。
3. **MuSiQue 80.68% vs 一代 80.04% 是可信的**。同一团队、同一基准、小幅提升，符合"砍预处理不该掉太多分"的预期。反而如果吹到 90%+ 就该警惕。
4. **EnterpriseRAG-Bench 跑完全量是真本事**。51 万份文档、图谱方案全都没跑完、SAG2 8 分半跑完，这一条比任何 Recall 数字都有说服力——**能不能跑完**本身就是工程能力的分水岭。

### ⚠️ 需要打折的部分

1. **"RAG 真死了"是标题党**。作者自己在文末说 BM25 是"老古董"、SAG2 是"返璞归真"，本质上是**对 RAG 的一次成功瘦身**，不是替代。混合检索+重排依然是工业标配，SAG2 解决的是它的多跳短板。
2. **"8 项指标全部第一"缺表格**。文中没列出是哪 8 项、对手是谁、差多少。这种概括性表述无法验证。
3. **第 22 张对比图是 AI 重绘的**。作者自己注明："终端的图不太好截，截出来也很难看，我就让 AI 根据真实结果画图展示了。" 其余终端截图同理需谨慎。
4. **JEV 是单点依赖**。官方把 JEV 定为"固定的决策模型"，这意味着 SAG2 的效果上限被 JEV 的判断力绑定。好消息是可替换（作者也提了），坏消息是替代方案的兼容性、成本、延迟都没给数据。
5. **实测都是作者自己的语料**。383 篇公众号文章、10 万维基词条、26 份研报——都是**结构良好、语义密集的长文本**。对表格密集、扫描件、代码库、对话记录这类场景的表现完全没有数据。

### 🎯 对我们知识库的参考价值

- 我们的知识库现在是 **383 篇结构化 markdown + 图片附件**，正好是 SAG2 最擅长的形态。
- 但我们的检索痛点和作者不同：我们是**"知道大概在哪篇、找不到具体段落"**，而 SAG2 解决的是**"跨文档多跳串线索"**。后者我们目前靠 gbrain 的 wikilink 图 + 语义搜索解决得还行。
- **真正值得试的点**：SAG Wiki 体积 18MB、增量更新、支持音视频——如果我们把 `assets/` 下的图片和未来要归档的视频也纳入检索，这是现有 gbrain 做不到的。
- **如果试，验证指标只能是**：同一批真实问题（不是基准题），比较"能不能找到、几次调用找到、耗时多少"。文章里那 4 组实测的**形式**（原生 vs SAG2 双组对照 + 调用次数）就是最好的设计。
