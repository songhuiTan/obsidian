## 概述

云淡风轻分享自研的 **Harness 引擎**——一套可插拔的工作流程编排工具。核心主张：**让引擎管流程，让模型管执行**。引擎负责规定步骤、执行者和走向，模型专注于执行任务。通过将流程控制权交给引擎，实现了更可靠的工作方式，内建质量保障，确保审查和测试成为必经之路。

## 核心论点

### 智能体循环的问题

AI 编程助手的核心是智能体循环（不断旋转调用工具），但裸循环存在三个根本问题：

| 问题 | 说明 |
|------|------|
| **质量门控缺失** | 模型写完代码直接结束，没有审查和测试环节 |
| **流程一致性差** | 每次执行路径不同，不可重复不可预测 |
| **适用性局限** | 通用循环无法适配特定任务的流程需求 |

### 主流产品的局限性

主流产品（Claude Code 等）通过提示词来解决问题，但**建议不等于约束**。提示词可以建议模型"请审查代码"，但模型可以选择跳过。Harness 引擎的方案是将约束内建为流程规则，而非提示词建议。

## Harness 引擎核心概念

### 执行内核与 Harness 引擎分层

| 层 | 职责 |
|----|------|
| **执行内核** | 模型调用、Tool 执行、ToolCall 循环等底层能力 |
| **Harness 引擎** | 工作流编排、阶段管理、门控、执行者分配、信号路由 |

两层各司其职，Harness 引擎在上层调度，执行内核在底层执行。

### 阶段（Phase）

阶段是工作流中的一站，每个阶段包含四个要素：

- **工作手册（Work Manual）**：本阶段要做什么、不要做什么
- **工具箱（Toolbox）**：本阶段可用的工具（只读阶段只有 Read/Grep，写入阶段才有 Write/Edit）
- **门控（Gate）**：完成本阶段后如何进入下一站
- **下一站（Next）**：完成后去哪个阶段

### 阶段状态机

调度中心，负责三件事：
- **决策阶段**：根据当前状态决定进入哪个阶段
- **决策走向**：阶段完成后选择分支路径
- **决策是否等待**：是否需要等待用户确认或其他条件

### 门控（Gate）三种模式

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| **自动放行** | 条件满足自动进入下一阶段 | 低风险、标准化流程步骤 |
| **人工放行** | 需要用户确认后才能继续 | 关键决策点、高风险操作 |
| **条件放行** | 根据执行结果自动判断，如测试覆盖率达标 | CI/CD 类流程 |

### 执行者两种模式

| 模式 | 行为 |
|------|------|
| **本机执行** | 在当前 Agent 环境中执行 |
| **委托执行** | 将任务委托给子智能体 |

### 子智能体

独立专家，有独立工作空间、可使用不同模型、完成后提交报告。适合并行分拆任务。

### 信号与双通道

| 通道 | 目标 | 内容 |
|------|------|------|
| **信号通道** | 引擎 | 执行状态、完成事件、错误 |
| **报告通道** | 用户 | 执行结果、分析结论 |

信号给引擎做调度，报告给用户做展示，互不干扰。

### 工具白名单

按阶段限定可用工具。例如：只读阶段只有 Read、Glob、Grep——确保模型不会在不该修改的阶段写入代码。

### 已确认方向

确保已经做出的决策不被后续步骤稀释。在阶段状态机中记录关键决策点，防止模型在执行过程中自行改变既定方向。

## 设计哲学

| 原则 | 说明 |
|------|------|
| **硬驱动（Hard Drive）** | 流程约束是强制的，不是可选的——门控必须通过才能继续 |
| **可插拔（Pluggable）** | 阶段、门控、执行者均可替换，不同任务绑定不同工作流 |
| **正交矩阵（Orthogonal Matrix）** | Harness 引擎与执行内核正交——改流程不改执行，改执行不改流程 |
| **零侵入（Zero Intrusion）** | 对模型层零侵入，模型不需要知道自己在哪个阶段 |

## 质量保障

质量保障内建在流程中，**审查和测试是必经之路**，而不是可选步骤。阶段完成后必须通过对应门控才能进入下一阶段，不允许跳过。

## 与 Claude Code 的根本差异

| 维度 | Claude Code（主流产品） | Harness 引擎 |
|------|------------------------|-------------|
| **流程控制权** | 模型自主决定 | 引擎控制 |
| **质量保障** | 提示词建议 | 门控强制执行 |
| **阶段可追溯** | 无显式阶段 | 阶段状态机 |
| **工具访问** | 全量开放 | 按阶段白名单限制 |
| **可替换性** | 固定工作流 | 可插拔，不同任务不同流程 |

## 实际例子

引擎通用，流程可替换。支持场景：

- **软件开发流程**：需求分析 → 设计 → 编码 → 审查 → 测试 → 发布，每个阶段有对应门控
- **深度调研流程**：信息收集 → 资料分析 → 交叉验证 → 结论生成
- **任务通过阶段状态机自动路由到对应工作流**

## 战略分析

### 与现有体系的对照

这个视频描述的 Harness 引擎设计与当前 Hermes Agent 的体系有大量交叉点：

| 维度 | 视频中的 Harness 引擎 | Hermes Agent |
|------|---------------------|-------------|
| 分层 | 执行内核 + Harness 引擎 | Agent 核心 + Skill 体系 |
| 阶段 | 阶段 + 门控 + 工具箱 | Agent 工作流的逐步执行 |
| 门控 | 自动/人工/条件三种 | 无显式 Gate 体系 |
| 工具白名单 | 按阶段限定 | config.yaml tools 注册，但无阶段级限制 |
| 子智能体 | 独立专家 + 独立空间 + 报告 | delegate_task 子代理 |
| 信号/报告双通道 | 信号给引擎，报告给用户 | stream 事件机制 |
| 可插拔 | 不同任务不同流程 | Skill 体系实现类似效果 |
| 设计哲学 | 硬驱动/正交矩阵/零侵入 | — |

### 高价值启示

1. **硬驱动 vs 建议**：当前 Hermes 的 Skill 更偏向"建议"而非"约束"。视频的核心论点是**建议不等于约束**。Skill 可以建议做测试，但模型可以选择跳过。Harness 引擎的门控体系是将约束内建为执行规则——这个思路值得引入到 Hermes 的 Skill 执行流程中。

2. **工具白名单按阶段限定**：当前 Hermes 的工具注册是全局的。如果能按阶段/任务动态限制可用工具（如只读阶段只有 Read 工具），可以大幅降低模型误操作风险。

3. **已确认方向**：确保决策不被后续步骤稀释——这是个容易被忽视但非常实用的设计。在长任务链中，模型容易在执行过程中偏离初始决策。将关键决策点"冻结"在阶段状态机中是个好模式。

4. **正交矩阵思想**：Harness 引擎与执行引擎解耦，使得改流程不需要改执行代码，改执行不需要改流程逻辑。对应到 Hermes，就是 Skill 体系（流程）与 Tool 体系（执行）的正交性。
