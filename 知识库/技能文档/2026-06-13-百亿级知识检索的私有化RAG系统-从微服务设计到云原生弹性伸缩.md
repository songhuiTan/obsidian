> 当企业知识库从"几万份文档"膨胀到"百亿级文本片段、百万级文件、千级并发请求"之后，RAG 的难点就不再是"能不能接上大模型"，而是"如何让检索、推理、治理、成本和弹性同时成立"。

很多团队第一次做私有化 RAG，往往是从一个 Demo 开始：上传文档，切块，Embedding，向量检索，拼 Prompt，再让大模型回答。这个阶段通常一两周就能跑起来，但真正进入生产之后，系统很快会遇到四类根本性问题：

1. 数据规模上来之后，索引构建和增量更新越来越慢，知识新鲜度失控。
2. 查询并发上来之后，检索链路、重排链路、推理链路的尾延迟急剧恶化。
3. 多租户和权限要求上来之后，"能搜到"变成"只能搜到自己该看的内容"。
4. 成本压力上来之后，GPU、存储、缓存、消息队列和网络都需要精细治理。

这篇文章不讨论玩具级 RAG，而是站在资深架构师视角，完整拆解一套面向企业内网、支持私有化部署、适配高并发场景、能够持续扩展的生产级 RAG 平台设计。我们会围绕以下四个目标展开：

- **技术深度增强**：讲清楚分块、Embedding、混合检索、重排、上下文编排、多级缓存、向量索引的底层原理。
- **工程化升级**：从单体 Demo 升级到微服务 + 事件驱动 + 云原生弹性伸缩体系。
- **代码生产级补全**：给出 Java、Python、SQL、Kubernetes 多栈可落地示例。
- **结构优化补充**：按"业务目标 → 架构拆解 → 核心链路 → 工程实现 → 演进治理"重构整篇文章。

## 一、先说结论：生产级私有化 RAG 到底在解决什么问题？

先看一个真实而典型的企业场景。

某大型制造集团要建设内部智能知识助手，知识源包括：

- 85 万份 PDF、Word、PPT、扫描件
- 12 年设备维修工单和 FAQ
- 近 3 亿行知识条目、日志摘要、技术规范片段
- 多组织、多地区、多语言、多权限层级

业务要求也非常明确：

- 所有数据必须留在企业内网，不允许外发
- 新文档上传后 5 分钟内可被检索
- 在线问答接口峰值 QPS 800+
- 首字延迟 P95 小于 2 秒，完整答案 P95 小于 12 秒
- 回答必须可追溯，能定位引用了哪些文档片段
- 多租户强隔离，不能出现越权召回

如果此时还沿用"单体 Python + 本地向量库 + 同步解析 + 同步推理"的思路，系统大概率会在三个地方先崩：

1. **离线构建崩**。文档解析、切块、Embedding、索引构建全都堆在一个进程里，重任务彼此抢资源，任何一个大文件都可能拖垮整条流水线。
2. **在线查询崩**。检索、重排、Prompt 组装、LLM 推理全部同步串联，任意一段抖动都会放大尾延迟。
3. **治理能力崩**。Demo 级系统默认"只追求召回"，但生产级系统必须同时满足权限过滤、审计、可观测、灰度、回滚、成本核算和版本管理。

所以，生产级私有化 RAG 的核心，不是"接一个模型"，而是建设一套完整的知识检索基础设施。

## 二、目标架构：把 RAG 拆成数据面、查询面、控制面、治理面

很多文章喜欢直接贴一张微服务架构图，但如果没有抽象层次，读者很难抓住重点。更推荐的方式，是先从职责边界定义系统。

一套成熟的私有化 RAG 平台，至少应该拆成四个平面：

### 2.1 数据面：负责知识从"原始文件"变成"可检索索引"

数据面的职责包括：

- 文档接入与元数据登记
- 文档解析与格式归一化
- 内容清洗与脱敏
- 分块与结构增强
- Embedding 向量化
- 关键词索引与倒排索引构建
- 向量索引构建与增量合并
- 版本切换与回滚

这个平面本质上是一个离线或准实时处理流水线，重点不是低延迟，而是吞吐、幂等、可恢复、可追踪。

### 2.2 查询面：负责把"用户问题"转成"高质量上下文"

查询面的职责包括：

- Query 预处理与纠错
- 多路召回：向量召回、BM25、标签过滤、规则召回
- 候选集合融合
- Cross-Encoder 重排
- 上下文压缩与去重
- Prompt 组装
- 大模型推理与流式输出

这个平面直接决定用户感知，关键指标是 P95/P99 延迟、召回质量、推理成功率和引用可解释性。

### 2.3 控制面：负责统一调度、资源编排、配置管理

控制面典型职责：

- 租户配置
- 模型路由
- 索引路由
- 配额管理
- 限流熔断
- 灰度开关
- 动态参数下发

没有控制面，系统就只能靠改配置文件或者发版来切换策略，根本支撑不了大规模生产运维。

### 2.4 治理面：负责安全、审计、可观测和成本治理

治理面至少要覆盖：

- 鉴权与租户隔离
- 文档权限映射
- 链路追踪
- 检索质量评估
- Prompt 与回答审计
- 成本归集
- 故障演练
- 数据生命周期管理

很多项目不是技术能力不够，而是治理面没有做起来，最后难以上线。

## 三、整体系统设计：为什么必须是微服务 + 事件驱动？

在百亿级知识片段场景里，"异步解耦"不是优化项，而是系统成立的前提。

### 3.1 推荐的服务拆分

下面是一套实战中更容易落地的服务划分：

| 服务 | 技术栈 | 核心职责 | 扩容方式 |
| --- | --- | --- | --- |
| API Gateway | Spring Cloud Gateway | 鉴权、路由、限流、审计入口 | 无状态水平扩展 |
| Auth Service | Spring Boot 3 | 用户、角色、租户、权限签发 | 无状态水平扩展 |
| Knowledge API | Spring Boot 3 | 文档上传、知识库管理、任务提交 | 无状态水平扩展 |
| Ingestion Orchestrator | Spring Boot 3 + Kafka | 解析任务编排、任务状态流转 | 消费组扩展 |
| Parser Worker | Python FastAPI | PDF/Office/HTML/图片 OCR 解析 | Worker 水平扩展 |
| Chunk Service | Python | 分块、结构增强、质量校验 | Worker 水平扩展 |
| Embedding Service | Python + GPU | 向量化、批处理、缓存 | GPU 节点扩展 |
| Index Service | Python/Go | 倒排索引、向量索引构建与切换 | 分片扩展 |
| Retrieval Service | Python FastAPI | 混合召回、过滤、重排 | 无状态水平扩展 |
| Chat Service | Spring WebFlux | 会话管理、SSE 推流、超时控制 | 无状态水平扩展 |
| LLM Gateway | Python FastAPI | 多模型路由、推理、降级 | GPU 池扩展 |
| Metadata DB | PostgreSQL | 元数据、任务状态、权限映射 | 主从/分库分表 |
| Cache | Redis | 热点结果、会话状态、幂等键 | 集群扩展 |
| MQ | Kafka | 异步削峰、状态事件、重试队列 | 分区扩展 |
| Vector Store | Milvus/OpenSearch | 向量索引与查询 | 分区/副本扩展 |
| Search Store | OpenSearch/ES | 倒排检索与过滤 | 分片扩展 |

### 3.2 为什么不建议"一库走天下"

一些团队会问：能不能只用一个向量数据库，别再叠加全文检索和元数据库？

答案是：小规模可以，生产场景通常不行。原因有三个：

1. 结构化元数据和租户权限天然更适合落在关系型数据库。
2. 关键词召回、前缀匹配、精确过滤、聚合统计天然更适合全文检索引擎。
3. 向量近邻搜索和索引构建策略天然更适合专门的向量引擎。

真正稳定的架构不是"所有东西放到一个地方"，而是"让不同引擎做自己擅长的事，再通过统一查询编排把结果拼起来"。

### 3.3 事件驱动为什么重要

文档入库链路中，最典型的错误是"上传完成后同步解析并同步向量化"。这样做有两个问题：

- HTTP 请求链路过长，超时和重试会把后台任务重复触发。
- 解析、OCR、Embedding、索引构建都属于重任务，必须和前台请求解耦。

推荐做法是：

1. 上传文件后只做元数据落库与对象存储保存。
2. 投递 `DOCUMENT_UPLOADED` 事件到 Kafka。
3. 解析、分块、Embedding、索引服务分别消费自己的主题。
4. 每一步产出状态事件，最终形成完整任务流水。

这样做的好处是：支持削峰填谷、支持失败重试、支持阶段性回滚、支持并行扩容、支持局部重跑。

## 四、离线链路设计：从原始文档到可检索知识的完整流水线

离线链路决定了 RAG 的"知识质量上限"。如果这个阶段做得粗糙，在线阶段无论怎么优化 Prompt 都只是补锅。

### 4.1 统一对象模型：不要让每个服务理解不同的数据结构

建议在系统内部统一使用三层对象：

- `Document`：原始文件级对象
- `Segment`：结构分段对象，例如章节、表格、代码块、标题块
- `Chunk`：最终检索对象，既可以来自一个 Segment，也可以由多个 Segment 组合

它们的职责边界是：

- `Document` 负责文件级生命周期与权限映射
- `Segment` 负责保留结构语义
- `Chunk` 负责最终检索与召回

这一步非常关键。很多系统一开始就直接把原文切成 512 tokens 的块，短期看效率高，长期看会有三个问题：

1. 无法保留标题、目录、表格、代码块等结构信息。
2. 无法做结构增强检索，例如"仅检索故障处理章节"。
3. 无法做细粒度回溯和引用解释。

### 4.2 文档解析：先解决"可读"，再解决"可检索"

生产级文档解析通常不是一个库就能搞定，而是多策略组合：

| 文档类型 | 推荐方案 | 主要风险 |
| --- | --- | --- |
| PDF 文字版 | `pypdfium2` + `pdfplumber` | 表格错位、页眉页脚污染 |
| 扫描版 PDF | OCR 服务 | 识别错误、耗时高 |
| Word/PPT | `unstructured` 或 Office 转 HTML | 格式丢失 |
| HTML/Wiki | DOM 清洗 + 结构提取 | 导航噪音 |
| Excel | Sheet 拆解 + 表头识别 | 单元格合并歧义 |
| Markdown/代码 | AST/Markdown parser | 代码块边界处理 |

在工程上，解析阶段建议输出统一 Markdown 中间格式，并保留以下附加元信息：`page_no`、`section_path`、`block_type`、`source_offset`、`language`、`acl_tags`、`doc_version`。有了这些字段，后续才能做权限过滤、精确引用、结构增强和版本回溯。

### 4.3 分块策略：切块不是长度问题，而是语义边界问题

一个成熟的分块器至少应该考虑四类边界：

1. 文档结构边界：标题、段落、列表、表格、代码块
2. 语义完整性边界：句子或论点不要被硬切断
3. 模型输入边界：避免上下文过长
4. 检索召回边界：避免 chunk 太短导致语义稀释

推荐分块策略不是固定长度，而是"结构优先 + 长度约束 + 重叠补偿"。

下面给一个更贴近生产的分块器示例：

```python
from dataclasses import dataclass
from typing import List


@dataclass
class Segment:
    text: str
    section_path: str
    block_type: str
    page_no: int


@dataclass
class Chunk:
    chunk_id: str
    text: str
    section_path: str
    page_no: int
    token_count: int
    block_types: List[str]


def build_chunks(segments: List[Segment], max_tokens: int = 420, overlap_tokens: int = 80) -> List[Chunk]:
    chunks: List[Chunk] = []
    current_segments: List[Segment] = []
    current_tokens = 0

    def estimate_tokens(text: str) -> int:
        # 生产中建议替换成与 embedding 模型一致的 tokenizer
        return max(1, len(text) // 2)

    def flush():
        nonlocal current_segments, current_tokens
        if not current_segments:
            return
        merged_text = "\n".join(s.text for s in current_segments)
        chunks.append(
            Chunk(
                chunk_id=f"chunk-{len(chunks) + 1}",
                text=merged_text,
                section_path=current_segments[0].section_path,
                page_no=current_segments[0].page_no,
                token_count=current_tokens,
                block_types=list({s.block_type for s in current_segments}),
            )
        )
        if overlap_tokens <= 0:
            current_segments = []
            current_tokens = 0
            return
        overlap: List[Segment] = []
        overlap_count = 0
        for seg in reversed(current_segments):
            token_size = estimate_tokens(seg.text)
            if overlap_count + token_size > overlap_tokens:
                break
            overlap.insert(0, seg)
            overlap_count += token_size
        current_segments = overlap
        current_tokens = overlap_count

    for segment in segments:
        token_size = estimate_tokens(segment.text)
        if token_size > max_tokens:
            # 超长块二次切分，避免单个表格/代码块拖垮上下文窗口
            text = segment.text
            start = 0
            step = max_tokens * 2
            while start < len(text):
                sub = Segment(
                    text=text[start : start + step],
                    section_path=segment.section_path,
                    block_type=segment.block_type,
                    page_no=segment.page_no,
                )
                sub_tokens = estimate_tokens(sub.text)
                if current_tokens + sub_tokens > max_tokens:
                    flush()
                current_segments.append(sub)
                current_tokens += sub_tokens
                flush()
                start += step - overlap_tokens
            continue

        if current_tokens + token_size > max_tokens:
            flush()

        current_segments.append(segment)
        current_tokens += token_size

    flush()
    return chunks
```

这段代码的关键点有三个：

- 不是直接按字符切，而是先保留结构块。
- 超长块会二次切分，避免表格和大段代码把上下文窗口吃满。
- 使用 overlap 保持上下文连续性，但 overlap 只在必要边界保留，避免召回重复过多。

### 4.4 Chunk 增强：让每个检索单元不仅"有内容"，还"有标签"

最终写入索引的 chunk，不建议只有一段文本。更合理的设计是附带增强字段：

```json
{
  "chunk_id": "doc-101#chunk-32",
  "tenant_id": 9001,
  "kb_id": 2008,
  "doc_id": 101,
  "doc_version": 12,
  "title": "液压系统故障排查流程",
  "section_path": "第三章/3.2 压力异常",
  "content": "当液压泵出口压力低于额定值时，优先检查...",
  "keywords": ["液压泵", "压力异常", "故障排查"],
  "block_types": ["paragraph", "table"],
  "acl_tags": ["dept:after-sales", "role:engineer"],
  "language": "zh",
  "published_at": "2026-03-10T08:00:00Z"
}
```

这些字段未来会直接影响：过滤条件构建、多租户隔离、重排特征构造、Prompt 中的引用格式、文档新鲜度加权。

### 4.5 索引构建：冷热分层，而不是一把梭

百亿级知识片段通常不可能全部放在高性能内存索引里。合理做法是冷热分层：

- **热层**：近期高频访问知识，放内存索引或高性能向量分片
- **温层**：常规知识，放标准向量索引
- **冷层**：长期低频知识，放磁盘索引或对象存储归档

这会带来一个很重要的架构收益：你不必为所有数据都购买最高规格 GPU 与内存。

## 五、在线链路设计：一次问答请求在系统里到底经历了什么？

RAG 的在线性能，核心看查询链路是不是足够短、足够稳、足够可控。

### 5.1 典型查询路径

生产场景下一次问答请求通常会经历下面的步骤：

```
Client
  -> Gateway
  -> Auth / Tenant Context
  -> Chat Service
     -> Query Rewrite
     -> Embedding Cache / Embedding Service
     -> Retrieval Service
        -> BM25 Recall
        -> Vector Recall
        -> Metadata Filter
        -> Candidate Fusion
        -> Rerank
        -> Context Compression
     -> Prompt Builder
     -> LLM Gateway
     -> SSE Streaming Response
     -> Async Conversation Persistence
```

这条链路上，最容易出问题的不是"大模型回答错了"，而是：

- Query 改写过度，导致原意丢失
- 候选集合不足，导致上下文缺料
- 权限过滤顺序错误，导致召回越权
- 重排太慢，拖垮整体 RT
- Prompt 拼接冗余，导致首字延迟上升

### 5.2 Query 预处理：先理解问题，再去检索

很多业务问题不是自然语言本身复杂，而是表达很口语、很缩写、很不完整。比如：

- "三号线液压泵报码 E17 怎么弄"
- "去年那版出海合规模板在哪"
- "有无售后人员点检 SOP"

如果直接拿原始 query 做向量检索，效果可能并不好。建议在查询面增加轻量 Query 理解层：

- 术语归一化：例如"报码"归一为"报警码"
- 别名映射：例如"点检 SOP"归一为"点检作业指导书"
- 拼写纠错
- 时间和组织维度提取
- 租户与业务域推断

这一步不一定要上大模型，很多企业内部术语用词固定，词典 + 规则反而更稳。

### 5.3 为什么推荐混合检索，而不是只做向量召回

只做向量召回，通常会在以下场景失分：

- 专有名词、设备编号、错误码
- 精确版本号
- 短 query
- 带过滤条件的查询

只做 BM25，又会在以下场景失分：

- 近义表达
- 长语义描述
- 问题和答案词面不重叠

所以生产级 RAG 更推荐混合召回：

- BM25 负责抓精确匹配和关键词强相关内容
- 向量检索负责抓语义相近内容
- 规则召回负责高确定性内容，比如 FAQ、工单模板、制度类答案

一个更合理的思路是"多路召回 + 融合 + 重排"，而不是押宝在单一召回模型。

### 5.4 候选融合：不要把不同召回结果简单拼接

多路召回的难点在于不同分数体系不可直接比较。

常见做法有两类：

1. 分数归一化后加权融合
2. RRF（Reciprocal Rank Fusion）按排名融合

如果你的不同召回源分数分布差异很大，RRF 往往更稳。示例代码如下：

```python
from collections import defaultdict
from typing import Dict, List


def reciprocal_rank_fusion(result_sets: Dict[str, List[str]], k: int = 60) -> List[str]:
    fused_scores = defaultdict(float)
    for _, doc_ids in result_sets.items():
        for rank, doc_id in enumerate(doc_ids, start=1):
            fused_scores[doc_id] += 1.0 / (k + rank)
    return [doc_id for doc_id, _ in sorted(fused_scores.items(), key=lambda x: x[1], reverse=True)]
```

RRF 的价值在于，它不依赖不同召回器原始分数是否可比，只要求"排名相对可信"。

### 5.5 权限过滤：先过滤还是后过滤？

这个问题看似简单，实则是生产级 RAG 最容易踩坑的地方之一。

错误做法是：

1. 先从全量知识里召回 topK
2. 再在应用层做 ACL 过滤

这样会导致两个问题：

- 召回结果大量被过滤后，实际可用候选不足
- 越权内容虽然没返回给用户，但已经进入模型上下文准备阶段，存在审计和安全风险

正确做法是：

- 能下推到检索引擎的权限过滤尽量下推
- 下推不了的复杂权限，再在应用层做二次过滤
- 在重排前就确保候选集合满足权限要求

也就是说，权限是检索条件的一部分，不是结果展示时的附加逻辑。

### 5.6 重排：为什么很多系统重排一加就变慢了？

Cross-Encoder 重排的确有效，但它的代价也非常真实：计算复杂度远高于向量召回。

因此工程上要控制三个参数：

- 初筛候选数量，例如 50 或 100
- 实际重排数量，例如截断到 20 或 30
- 输出上下文数量，例如最终只保留 5 到 8 条

下面是一个更偏生产的异步重排示例：

```python
import asyncio
from dataclasses import dataclass
from typing import List


@dataclass
class Candidate:
    chunk_id: str
    text: str
    source: str
    score: float


class AsyncRerankService:
    def __init__(self, reranker_client, concurrency: int = 8):
        self.reranker_client = reranker_client
        self.semaphore = asyncio.Semaphore(concurrency)

    async def score_one(self, query: str, candidate: Candidate) -> Candidate:
        async with self.semaphore:
            rerank_score = await self.reranker_client.score(query=query, passage=candidate.text)
            candidate.score = rerank_score
            return candidate

    async def rerank(self, query: str, candidates: List[Candidate], top_n: int = 6) -> List[Candidate]:
        limited = candidates[:24]
        tasks = [self.score_one(query, candidate) for candidate in limited]
        scored = await asyncio.gather(*tasks, return_exceptions=False)
        scored.sort(key=lambda item: item.score, reverse=True)
        return scored[:top_n]
```

这里有两个细节值得强调：

- 用 `async with semaphore` 保证异常路径也能正确释放并发许可。
- 只对有限候选做重排，不能让 rerank 成为新的系统瓶颈。

### 5.7 Prompt 组装：不是把 topK 全贴进去就叫上下文增强

Prompt 组装至少要遵守三条原则：

1. 上下文要去重，不能同一个段落多次出现。
2. 上下文要保留来源标签，便于回答引用。
3. 上下文要控制预算，不能把模型上下文窗口浪费在冗余内容上。

推荐做法是给每个片段带上来源头信息：

```
[文档1 | 售后手册V12 | 第3章/3.2 压力异常 | 第28页]
......

[文档2 | 维修工单案例库 | 案例#2025-1841]
......
```

这样可以显著提升回答可解释性，也便于前端做"引用来源跳转"。

## 六、为什么百亿级场景一定要重视索引、分片和缓存？

规模一旦上来，RAG 的瓶颈往往不在单条查询，而在系统整体资源流动。

### 6.1 向量索引的本质是"召回质量"和"资源成本"的平衡

常见的近邻索引方案，大致可以这样理解：

| 索引类型 | 特点 | 适用场景 |
| --- | --- | --- |
| Flat | 精确检索，慢 | 小规模或离线评估 |
| IVF | 聚类分桶，适合中大规模 | 常规向量检索 |
| HNSW | 高召回、低延迟、内存开销大 | 热数据高性能查询 |
| PQ/IVF-PQ | 压缩强、召回会损失 | 大规模成本敏感场景 |
| DiskANN 类磁盘索引 | 适合超大规模冷温数据 | 热温冷分层体系 |

真正的选择原则不是"哪个更先进"，而是：数据规模多大、延迟目标多严、内存预算多少、更新频率多高、是否需要在线增量构建。

### 6.2 分片不是只为扩容，更是为隔离

向量分片至少可以基于以下维度：

- 按租户分片
- 按知识库分片
- 按时间分片
- 按热度分层

很多团队一开始只按数据量分片，后面才发现最麻烦的其实是权限与热点冲突。例如一个超级租户每天访问量占全平台 40%，如果和小租户混在一个大分片里，热点抖动会影响全局。所以生产上更推荐"逻辑租户隔离 + 物理热度分层"的组合。

### 6.3 多级缓存设计：缓存的不只是答案

RAG 系统可以缓存的对象其实很多：

1. Query 归一化结果
2. Embedding 向量
3. 检索候选集
4. 重排结果
5. Prompt 模板
6. 完整回答

但并不是所有层都适合长缓存。一个更稳妥的策略是：

| 缓存对象 | TTL 建议 | 风险 |
| --- | --- | --- |
| Query 归一化结果 | 30 分钟 | 低 |
| Embedding 向量 | 1 天 | 低 |
| 检索候选集 | 5 到 15 分钟 | 中 |
| 重排结果 | 5 到 10 分钟 | 中 |
| 完整回答 | 视业务决定 | 高，可能陈旧 |

缓存命中策略必须带版本号，例如：`cache_key = tenant_id + kb_id + index_version + normalized_query`

不带 `index_version` 的缓存，最终一定会出现"知识已经更新但结果还是旧的"问题。

## 七、生产级代码示例：一条问答接口应该怎么写

这一节给出更接近生产的核心代码，而不是只能运行 Demo 的示例。

### 7.1 Java Chat Service：SSE 流式响应、超时控制与异步落库

```java
package com.example.rag.chat;

import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.http.MediaType;
import org.springframework.http.codec.ServerSentEvent;
import org.springframework.web.bind.annotation.*;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;
import reactor.core.scheduler.Schedulers;

import java.time.Duration;
import java.util.UUID;

@Slf4j
@RestController
@RequiredArgsConstructor
@RequestMapping("/api/chat")
public class ChatController {

    private final TenantContext tenantContext;
    private final QueryGuardService queryGuardService;
    private final RetrievalFacade retrievalFacade;
    private final PromptAssemblyService promptAssemblyService;
    private final LlmStreamClient llmStreamClient;
    private final ConversationRepository conversationRepository;

    @PostMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<ServerSentEvent<String>> stream(@RequestBody ChatRequest request) {
        String traceId = UUID.randomUUID().toString();
        Long tenantId = tenantContext.requireTenantId();
        Long userId = tenantContext.requireUserId();

        return queryGuardService.validate(request.query())
            .then(retrievalFacade.retrieve(
                tenantId,
                userId,
                request.knowledgeBaseId(),
                request.query(),
                request.sessionId()
            ))
            .flatMapMany(context -> {
                PromptPayload payload = promptAssemblyService.build(request, context);
                return llmStreamClient.stream(payload)
                    .timeout(Duration.ofSeconds(90))
                    .map(token -> ServerSentEvent.<String>builder()
                        .event("message")
                        .id(traceId)
                        .data(token)
                        .build()
                    )
                    .concatWithValues(
                        ServerSentEvent.<String>builder()
                            .event("done")
                            .id(traceId)
                            .data("[DONE]")
                            .build()
                    )
                    .doOnComplete(() -> persistConversationAsync(traceId, tenantId, userId, request, context, payload))
                    .doOnError(ex -> log.error("chat stream failed, traceId={}", traceId, ex));
            })
            .onErrorResume(QueryRejectedException.class, ex ->
                Flux.just(ServerSentEvent.<String>builder()
                    .event("error")
                    .id(traceId)
                    .data("请求被安全策略拒绝：" + ex.getMessage())
                    .build())
            )
            .onErrorResume(ex ->
                Flux.just(ServerSentEvent.<String>builder()
                    .event("error")
                    .id(traceId)
                    .data("系统繁忙，请稍后重试")
                    .build())
            );
    }

    private void persistConversationAsync(
        String traceId,
        Long tenantId,
        Long userId,
        ChatRequest request,
        RetrievalContext context,
        PromptPayload payload
    ) {
        Mono.fromRunnable(() -> conversationRepository.save(
                ConversationEntity.from(traceId, tenantId, userId, request, context, payload)
            ))
            .subscribeOn(Schedulers.boundedElastic())
            .doOnError(ex -> log.warn("persist conversation failed, traceId={}", traceId, ex))
            .subscribe();
    }
}
```

这段代码体现了几个生产关键点：

- 请求入口先校验，再检索，再推理，链路职责清晰。
- SSE 流中显式发送 `done` 事件，前端更容易做状态收尾。
- 会话落库异步执行，避免拖慢主链路。
- 错误分业务错误和系统错误两类处理，避免把堆栈信息直接泄给前端。

### 7.2 Retrieval Facade：统一编排混合召回和重排

```java
package com.example.rag.chat;

import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import reactor.core.publisher.Mono;

@Service
@RequiredArgsConstructor
public class RetrievalFacade {

    private final QueryNormalizeService queryNormalizeService;
    private final EmbeddingClient embeddingClient;
    private final RetrievalClient retrievalClient;
    private final AccessControlService accessControlService;

    public Mono<RetrievalContext> retrieve(
        Long tenantId,
        Long userId,
        Long knowledgeBaseId,
        String rawQuery,
        String sessionId
    ) {
        return queryNormalizeService.normalize(tenantId, rawQuery, sessionId)
            .flatMap(normalized ->
                embeddingClient.embed(tenantId, normalized.normalizedQuery())
                    .flatMap(vector -> retrievalClient.retrieve(
                        RetrievalRequest.builder()
                            .tenantId(tenantId)
                            .userId(userId)
                            .knowledgeBaseId(knowledgeBaseId)
                            .rawQuery(rawQuery)
                            .normalizedQuery(normalized.normalizedQuery())
                            .queryVector(vector.values())
                            .aclTags(accessControlService.resolveAclTags(userId))
                            .topK(60)
                            .rerankTopN(6)
                            .build()
                    ))
                    .map(result -> RetrievalContext.from(normalized, result))
            );
    }
}
```

它的意义在于：Chat Service 不需要知道检索内部到底是 BM25、向量召回还是重排，它只依赖一个统一编排结果。

### 7.3 Python Retrieval Service：多路召回、权限过滤和重排

```python
from dataclasses import dataclass
from fastapi import FastAPI
from pydantic import BaseModel
from typing import List

app = FastAPI()


class RetrievalRequest(BaseModel):
    tenant_id: int
    user_id: int
    knowledge_base_id: int
    raw_query: str
    normalized_query: str
    query_vector: List[float]
    acl_tags: List[str]
    top_k: int = 60
    rerank_top_n: int = 6


@dataclass
class RecallItem:
    chunk_id: str
    content: str
    source: str
    score: float
    acl_tags: List[str]
    doc_version: int


class RetrievalPipeline:
    def __init__(self, keyword_store, vector_store, rerank_service):
        self.keyword_store = keyword_store
        self.vector_store = vector_store
        self.rerank_service = rerank_service

    async def run(self, req: RetrievalRequest):
        keyword_hits = await self.keyword_store.search(
            tenant_id=req.tenant_id,
            knowledge_base_id=req.knowledge_base_id,
            query=req.normalized_query,
            acl_tags=req.acl_tags,
            limit=30,
        )

        vector_hits = await self.vector_store.search(
            tenant_id=req.tenant_id,
            knowledge_base_id=req.knowledge_base_id,
            vector=req.query_vector,
            acl_tags=req.acl_tags,
            limit=30,
        )

        fused_ids = reciprocal_rank_fusion({
            "keyword": [item.chunk_id for item in keyword_hits],
            "vector": [item.chunk_id for item in vector_hits],
        })

        merged = self.merge_items(fused_ids, keyword_hits, vector_hits)
        filtered = [item for item in merged if self.has_acl(item.acl_tags, req.acl_tags)]
        reranked = await self.rerank_service.rerank(req.normalized_query, filtered, req.rerank_top_n)
        return reranked

    def merge_items(self, fused_ids, keyword_hits, vector_hits):
        mapping = {item.chunk_id: item for item in keyword_hits + vector_hits}
        return [mapping[item_id] for item_id in fused_ids if item_id in mapping]

    def has_acl(self, candidate_acl_tags, request_acl_tags):
        return set(candidate_acl_tags).issubset(set(request_acl_tags))


pipeline = RetrievalPipeline(keyword_store=..., vector_store=..., rerank_service=...)


@app.post("/retrieve")
async def retrieve(req: RetrievalRequest):
    items = await pipeline.run(req)
    return {
        "items": [
            {
                "chunk_id": item.chunk_id,
                "content": item.content,
                "source": item.source,
                "score": item.score,
                "doc_version": item.doc_version,
            }
            for item in items
        ]
    }
```

这段代码重点不是语法，而是体现了三个工程原则：

- 权限标签必须作为检索条件输入，而不是结果展示时才判断。
- 多路召回要统一融合，而不是简单拼接。
- 检索服务输出的不只是文本，还要携带来源与版本信息。

### 7.4 Kafka 消费者：幂等、重试和死信

离线链路一定要解决重复消费和阶段性失败。下面给一个 Java 消费者骨架：

```java
package com.example.rag.ingestion;

import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.stereotype.Component;

@Slf4j
@Component
@RequiredArgsConstructor
public class DocumentUploadedListener {

    private final IdempotentService idempotentService;
    private final IngestionTaskService ingestionTaskService;

    @KafkaListener(topics = "document-uploaded", groupId = "parser-workers")
    public void onMessage(DocumentUploadedEvent event) {
        String idempotentKey = "document-uploaded:" + event.tenantId() + ":" + event.documentId() + ":" + event.version();
        if (!idempotentService.tryAcquire(idempotentKey, 3600)) {
            log.info("skip duplicated event, key={}", idempotentKey);
            return;
        }

        try {
            ingestionTaskService.parseAndDispatch(event);
            idempotentService.markSuccess(idempotentKey);
        } catch (RetryableIngestionException ex) {
            idempotentService.release(idempotentKey);
            throw ex;
        } catch (Exception ex) {
            ingestionTaskService.sendToDeadLetter(event, ex.getMessage());
            idempotentService.markFailed(idempotentKey, ex.getMessage());
            log.error("document ingestion failed, documentId={}", event.documentId(), ex);
        }
    }
}
```

在这种场景里，幂等键至少要包含：租户 ID、文档 ID、文档版本、任务阶段。否则重新上传新版本文档时，容易被误判成重复任务。

### 7.5 元数据表设计：索引、版本、权限一个都不能少


## 八、高并发场景的关键工程问题：不是"能跑"，而是"扛得住"

生产级架构和 Demo 最大的分水岭，是高并发下系统行为是否仍然可预测。

### 8.1 首先控制尾延迟，而不是只看平均响应时间

RAG 查询链路很长，所以平均值没有太大意义。真正要盯的是：

- Embedding 延迟 P95/P99
- 检索延迟 P95/P99
- 重排延迟 P95/P99
- LLM 首字延迟 P95/P99
- SSE 连接成功率

为什么尾延迟这么重要？因为只要链路里有一个下游 P99 崩掉，用户看到的就不是"慢一点"，而是"直接觉得系统不可用"。

### 8.2 背压机制：没有背压，流式系统迟早雪崩

高并发问答最怕的不是偶发慢，而是资源池被打穿。

必须做的治理包括：

- Gateway 层按租户限流
- Chat Service 层按用户并发数限制
- Retrieval Service 层按线程池和协程并发限制
- LLM Gateway 层按 GPU slot 限制
- 超载时优雅降级，比如关闭 query rewrite 或降低 rerank 数量

一个典型的 Java 限流示例如下：

```java
package com.example.rag.guard;

import io.github.resilience4j.ratelimiter.RateLimiter;
import io.github.resilience4j.ratelimiter.RateLimiterConfig;
import org.springframework.stereotype.Component;

import java.time.Duration;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

@Component
public class TenantRateLimiterRegistry {

    private final Map<Long, RateLimiter> limiterMap = new ConcurrentHashMap<>();

    public boolean acquire(Long tenantId) {
        RateLimiter limiter = limiterMap.computeIfAbsent(tenantId, id ->
            RateLimiter.of("tenant-" + id, RateLimiterConfig.custom()
                .limitRefreshPeriod(Duration.ofSeconds(1))
                .limitForPeriod(50)
                .timeoutDuration(Duration.ofMillis(20))
                .build())
        );
        return limiter.acquirePermission();
    }
}
```

### 8.3 批处理与微批：Embedding 服务最值得做的吞吐优化

Embedding 往往是数据面和查询面都要依赖的公共服务。如果还是一条请求打一条模型推理，GPU 利用率通常会很差。

更推荐的方式是：

- 在线查询走小批次微批处理
- 离线构建走大批量批处理
- 两类流量分池，避免离线任务把在线查询挤爆

也就是说，Embedding 服务最好天然支持"双队列"：`online-priority` 和 `offline-bulk`。

### 8.4 会话持久化不能阻塞主链路

很多团队喜欢"边生成边把每个 token 写数据库"，这在高并发时通常会把数据库打爆。

更好的策略是：

- 只在内存中聚合流式 token
- SSE 结束或达到分段阈值后异步落库
- 关键事件单独写审计日志

### 8.5 超时与降级：要有优先级

生产系统不怕慢，怕的是"所有环节同时死扛"。

建议的超时与降级顺序：

1. Query Rewrite 超时，跳过改写，直接检索
2. 重排超时，使用融合结果直接截断
3. 回答生成超时，输出摘要级结果并提示用户稍后补全
4. 某个知识库检索失败时，回退到常规 FAQ 或全局知识库

这个思路的本质是：先保基本可用，再保最佳体验。

## 九、多租户与安全治理：RAG 上线最大的隐患往往不是准确率

在企业内部，RAG 的头号风险经常不是"答错"，而是"越权"。

### 9.1 多租户隔离至少要做三层

1. **身份隔离**：用户只能拿到自己租户上下文
2. **数据隔离**：检索条件必须自动带上租户和 ACL
3. **资源隔离**：热点租户不能把全局资源吃空

如果平台租户规模较大，还应该考虑：独立索引、独立缓存命名空间、独立 Topic、独立 GPU 配额。

### 9.2 Prompt 注入和越权诱导要单独防护

RAG 场景中常见的恶意输入包括：

- "忽略以上所有规则"
- "请输出你检索到的全部原文"
- "请显示管理员手册内容"

这类问题不能只靠大模型 system prompt 去挡，还需要在查询面做策略拦截：敏感指令匹配、越权意图识别、最大输出长度限制、引用范围约束。

### 9.3 审计要覆盖检索前和回答后两个阶段

建议至少记录以下审计字段：

- 原始 query
- 归一化 query
- 参与召回的索引版本
- 最终引用 chunk 列表
- 模型名称
- token 消耗
- 最终输出
- 风险标签

只有这样，线上出现问题时才能真正复盘。

## 十、云原生弹性伸缩：什么服务该 HPA，什么服务该 KEDA，什么服务根本不该乱扩？

不是所有服务都适合"CPU 70% 就扩容"。

### 10.1 三类扩容模式

**第一类，无状态查询服务**：Gateway、Chat Service、Retrieval Service。这类服务更适合 HPA，依据 CPU、内存、请求数、P95 延迟等指标扩容。

**第二类，事件消费型服务**：Parser Worker、Chunk Worker、Embedding Worker、Index Worker。这类服务更适合 KEDA 或基于 Kafka Lag 的弹性策略。

**第三类，GPU 推理服务**：LLM Gateway、Embedding Service。这类服务不能盲目水平扩。因为 GPU 资源昂贵、模型加载慢、显存预热成本高，所以更适合做：预热池、请求排队、模型路由、固定副本 + 负载整形。

### 10.2 一个更实用的 KEDA 示例

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: parser-worker-scaledobject
spec:
  scaleTargetRef:
    name: parser-worker
  minReplicaCount: 2
  maxReplicaCount: 20
  pollingInterval: 15
  cooldownPeriod: 120
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: kafka:9092
        consumerGroup: parser-workers
        topic: document-uploaded
        lagThreshold: "200"
```

为什么这里推荐 Kafka Lag 驱动扩容？因为解析任务是典型队列型工作负载，CPU 使用率并不能真实反映任务堆积。

### 10.3 Chat Service 的 HPA 示例

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: chat-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: chat-service
  minReplicas: 3
  maxReplicas: 12
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 65
    - type: Pods
      pods:
        metric:
          name: active_sse_connections
        target:
          type: AverageValue
          averageValue: "300"
```

SSE 类服务只看 CPU 不够，必须把活跃连接数也纳入扩容依据。

### 10.4 GPU 推理服务为什么常常"扩得越快，越不稳"

原因通常有四个：

1. 模型加载太慢，Pod 启动后长时间不可用
2. 显存碎片化导致新实例不稳定
3. 请求分布不均，部分 Pod 爆满，部分 Pod 空闲
4. 扩容太晚，峰值已经打爆队列

所以更推荐的思路是：提前预热、建立推理队列、根据模型类型做路由池拆分、对长请求与短请求分池。

## 十一、Kubernetes 生产部署清单：别只写 Deployment

云原生部署不等于把容器跑起来，更关键的是把运行时治理补齐。

### 11.1 Chat Service Deployment 示例

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: chat-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: chat-service
  template:
    metadata:
      labels:
        app: chat-service
    spec:
      containers:
        - name: chat-service
          image: registry.example.com/rag/chat-service:1.0.0
          ports:
            - containerPort: 8080
          env:
            - name: JAVA_TOOL_OPTIONS
              value: "-XX:+UseContainerSupport -XX:MaxRAMPercentage=70 -Dreactor.netty.pool.maxConnections=1000"
          resources:
            requests:
              cpu: "1"
              memory: "2Gi"
            limits:
              cpu: "2"
              memory: "4Gi"
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            initialDelaySeconds: 20
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 15
```

### 11.2 Gateway 对 SSE 的关键配置

SSE 经常不是后端服务本身挂掉，而是中间层把流式响应破坏了。

Nginx 或 Ingress 侧至少要关注：

```nginx
location /api/chat/stream {
    proxy_pass http://chat-service;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
    add_header X-Accel-Buffering no;
}
```

这几项里最关键的是：关闭代理缓冲、拉长读超时、保持 HTTP/1.1 长连接语义。

### 11.3 配置中心与动态开关

RAG 系统里很多参数都需要动态调整：topK、rerankTopN、prompt 模板版本、模型路由规则、限流阈值、租户配额。所以推荐统一纳入配置中心，而不是散落在各服务环境变量里。这样线上调优不需要频繁发版。

## 十二、可观测性与评估体系：没有数据闭环，RAG 无法持续变好

很多团队上线之后，最先遇到的问题不是"系统挂了"，而是"用户觉得不好用，但工程侧不知道问题在哪"。

### 12.1 至少要有三类观测指标

**第一类，系统性能指标**：QPS、成功率、首字延迟、完整回答延迟、Kafka Lag、GPU 利用率、向量检索 RT。

**第二类，检索质量指标**：Recall@K、MRR、NDCG、引用命中率、无引用回答比例。

**第三类，业务效果指标**：问答采纳率、二次追问率、人工转接率、用户满意度。

### 12.2 检索评估要拆离线和在线

**离线评估**主要用来比较：chunk 策略、embedding 模型、召回融合策略、rerank 模型。

**在线评估**主要关注：新索引版本是否带来真实收益、新 Prompt 模板是否让回答更稳定、某类租户问题是否集中恶化。

所以一个成熟系统最好支持：查询回放、索引版本 AB Test、Prompt 版本灰度、特征和结果全链路采样。

### 12.3 OpenTelemetry 是最值得上的基础设施之一

一条问答请求跨越 Gateway、Chat Service、Retrieval Service、LLM Gateway、Redis、Kafka、向量库、全文检索引擎，如果没有统一 Trace，排障效率会非常低。

建议把以下信息挂到 span 上：`tenant_id`、`session_id`、`query_hash`、`index_version`、`model_name`、`token_usage`。

这样一条慢请求到底慢在检索、重排还是推理，几分钟内就能定位出来。

## 十三、实际落地案例：从 0 到 1，再从 1 到 100 的演进路径

对于大多数企业来说，最务实的路线不是一步到位，而是分阶段演进。

### 阶段一：先建立最小可用闭环

目标：支持文档上传、支持异步解析、支持向量召回 + 基础回答、支持引用来源展示。

此阶段的重点不是极致性能，而是把数据面和查询面打通。

### 阶段二：补齐混合检索和权限过滤

目标：加入 BM25 或全文召回、加入 ACL 下推过滤、加入重排、加入会话持久化和审计。

这个阶段通常是"效果从能用走向好用"的关键阶段。

### 阶段三：补齐弹性与治理

目标：引入 KEDA/HPA、建立缓存与版本失效体系、建立可观测和评估体系、建立降级和熔断策略。

这个阶段之后，系统才真正具备承载大规模线上流量的能力。

### 阶段四：走向多模型、多区域、多租户平台化

目标：不同模型按场景路由、不同租户独立配额、热冷知识分层、跨区域容灾。

此时，RAG 系统已经不再是某个业务的附属功能，而是一套企业级 AI 基础设施。

## 十四、常见生产故障与避坑清单

### 14.1 文档解析成功但检索为空

常见原因：元数据入库成功，但 chunk 没有入索引；索引版本未切换；查询路由到了旧索引。

解决思路：建立"元数据状态"和"索引状态"双状态机；每个阶段输出事件；发布前做索引版本健康校验。

### 14.2 新文档已经上传，但用户还是搜到旧内容

常见原因：检索缓存未带 `index_version`；Prompt 缓存未失效；文档版本切换与索引切换不同步。

解决思路：所有检索相关缓存带索引版本；新版本索引 ready 后再切流；切流后统一广播缓存失效事件。

### 14.3 GPU 没打满，但回答还是慢

常见原因：请求在上游排队；Retrieval 或 rerank 更慢；Prompt 过长；流式输出被网关缓冲。

解决思路：分段观察链路延迟；拆出首字延迟与完整时延；单独检查 SSE 代理配置。

### 14.4 重排准确率高，但整体效果没提升

常见原因：初筛候选质量太差；重排只在错误候选中挑最不差的；上下文拼接方式把有效信息冲掉了。

解决思路：先提升召回多样性；检查 chunk 粒度是否合理；检查 Prompt 是否把引用片段组织得足够清晰。

## 十五、总结：私有化 RAG 的本质，是构建一套"知识检索操作系统"

如果把这篇文章浓缩成一句话，那就是：

私有化 RAG 的核心竞争力，不在于"接了哪个大模型"，而在于你是否构建了一套可持续演进的知识检索与推理基础设施。

真正能扛住百亿级知识检索的系统，通常具备以下特征：

- 数据面和查询面彻底解耦
- 离线链路事件驱动、可重试、可回滚
- 在线链路混合检索、重排、权限过滤协同工作
- 多租户、审计、缓存、版本、限流、可观测全部成体系
- 云原生弹性扩缩建立在工作负载理解之上，而不是盲目扩 Pod

也正因为如此，生产级 RAG 的建设方式，和传统"做一个问答功能"完全不同。它更像是在企业内部搭建一层"知识操作系统"：

- **上层**对接业务应用、Copilot、智能客服、运维助手、售后助手
- **中层**沉淀统一的检索、重排、推理、审计能力
- **下层**管理文档、索引、模型、GPU、缓存和任务编排

只有这样，系统才能从一个短期 Demo，演进成真正可复用、可治理、可扩展的 AI 基础设施。

如果你正在做企业级私有化 RAG，建议优先把精力放在下面五件事上：

1. 先把数据链路做对，而不是先卷 Prompt。
2. 先把权限和版本做扎实，而不是先追求复杂 Agent 化。
3. 先把混合检索和重排做稳定，而不是盲目扩大模型。
4. 先把缓存、限流、超时、降级做出来，而不是相信高峰期自然会稳。
5. 先把评估和可观测建起来，否则系统无法持续变好。

这才是百亿级知识检索私有化 RAG 的真正工程方法论。
