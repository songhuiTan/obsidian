# gstack + Compound Engineering 组合工作流方案

> 归档时间：2026-04-06
> 框架版本：gstack (Garry Tan) + Compound Engineering Plugin (EveryInc)

---

## 一、为什么组合使用？

| 维度 | gstack 强项 | CE Plugin 强项 |
|------|------------|---------------|
| 产品决策 | CEO/Eng 视角的需求审查 | 深度代码研究 + 最佳实践检索 |
| 规划 | 快速判断"做不做" | 研究驱动的"怎么做"详细方案 |
| 设计 | 设计系统 + 多方案探索 (/design-shotgun) | Figma 同步 + 前端设计 |
| 执行 | 并行 Sprint (Conductor) | worktree 隔离 + 持续测试 |
| 代码审查 | 角色化审查（CEO/Eng/Design） | 13+ 专项 Reviewer 并行 |
| 质量验证 | 真实浏览器 QA（Playwright） | 自动化质量检查 |
| 知识积累 | 跨 session 记忆 (/learn) + 复盘 (/retro) | 结构化知识沉淀 (/compound) + 关键模式检测 |
| 部署 | 完整的 Ship 流程 | PR 生成 + 截图对比 |
| 安全 | OWASP Top 10 + STRIDE (/cso) | 安全专项 Reviewer |
| 跨模型验证 | OpenAI Codex 独立审查 (/codex) | — |

**一句话总结：gstack 管"做不做"和"测得真"，CE 管"怎么做""做得好不好"和"记住经验"。**

## 四、安装配置指南

### 4.1 安装 gstack

```bash
# 克隆到 Claude Code skills 目录
git clone --single-branch --depth 1 https://github.com/garrytan/gstack.git ~/.claude/skills/gstack

# 运行安装脚本
cd ~/.claude/skills/gstack && ./setup
```

### 4.2 安装 Compound Engineering Plugin

```bash
# 方式一：通过 Claude Code 插件系统（推荐）
# 在 Claude Code 中执行：
/plugin marketplace add https://github.com/EveryInc/compound-engineering-plugin
/plugin install compound-engineering

# 方式二：手动克隆
git clone --single-branch --depth 1 https://github.com/EveryInc/compound-engineering-plugin.git ~/.claude/skills/compound-engineering
```

**CE 插件包含 2 个 MCP 服务器：**
- **Playwright** (`pw`)：浏览器自动化，用于 E2E 测试和截图
- **Context7** (`context7`)：框架文档实时查询 HTTP 服务

> 注意：MCP 服务器可能不会自动加载，安装后需重启 Claude Code 或手动配置。

### 4.3 项目初始化配置

在项目根目录创建 `CLAUDE.md`，添加以下内容：

```markdown
## 项目工作流配置

### 框架组合
- 产品决策和 QA：使用 gstack 命令
- 技术规划和知识沉淀：使用 CE 命令

### 工作流顺序
1. 需求阶段：先 /office-hours → /plan-ceo-review → /plan-eng-review
2. 规划阶段：/workflows:plan（自动检索历史经验）
3. 开发阶段：/workflows:work（worktree 隔离）
4. 审查阶段：/workflows:review + /review
5. 测试阶段：/qa（浏览器真实测试）
6. 部署阶段：/ship 或 /land-and-deploy
7. 沉淀阶段：/workflows:compound + /retro

### 知识库位置
- 经验文档：docs/solutions/
- 计划文档：plans/
```

### 4.4 知识库目录结构

```
项目根目录/
├── docs/
│   └── solutions/          ← CE 知识沉淀目录
│       ├── build-errors/
│       ├── test-failures/
│       ├── runtime-errors/
│       ├── performance-issues/
│       ├── database-issues/
│       ├── security-issues/
│       ├── ui-bugs/
│       ├── integration-issues/
│       └── logic-errors/
├── plans/                  ← CE 计划文档目录
│   └── <feature-slug>.md
└── CLAUDE.md              ← 项目配置
```

## 五、最佳实践

### 5.1 何时用哪个框架的判断原则

```
收到需求
    │
    ├─ 是新产品方向/功能？ ──→ gstack /plan-ceo-review
    │                           │
    │                           └─ 通过？──→ CE /workflows:plan
    │
    ├─ 是技术改进/重构？ ──→ gstack /plan-eng-review
    │                         │
    │                         └─ 通过？──→ CE /workflows:plan
    │
    └─ 是 Bug 修复？ ──→ 直接 CE /workflows:plan
                           (自动检索 docs/solutions/)
```

### 5.2 快捷路径：/autoplan

gstack 的 `/autoplan` 是组合工作流的"快速通道"：
- 自动运行 CEO → 设计 → Eng 三轮审查
- 只将**品味决策**（需要人类判断的问题）呈现给你
- 适合中小型需求，省去逐步跑三个审查命令的时间

```
快速路径：   /autoplan ──→ /ce:plan ──→ /ce:work ──→ ...
完整路径：   /office-hours → /plan-ceo-review → /plan-design-review
           → /plan-eng-review → /ce:plan ──→ /ce:work ──→ ...
```

### 5.3 Compound 使用策略

**不是每次都需要 compound。** 推荐策略：

| 任务类型 | 是否 Compound | 原因 |
|---------|:------------:|------|
| 新功能开发 | ✅ | 新架构决策、踩坑经验值得沉淀 |
| 复杂 Bug 修复 | ✅ | 根因分析防止复发 |
| 性能优化 | ✅ | 优化策略和基准数据有价值 |
| 简单 Bug 修复 | ❌ | 改 typo、调 CSS 不值得沉淀 |
| 数据库迁移 | ❌ | 标准操作，无需沉淀 |
| 配置变更 | ❌ | 低复杂度 |

**折中方案：Compound Janitor**
- 每天结束时，回顾当天 session 和 git diff
- 只对有价值的任务执行 `/ce:compound`
- 避免知识库被低价值内容稀释

**自动触发机制：**
CE 的 compound 会自动在以下表述时触发：
- "搞定了" / "that worked"
- "修好了" / "it's fixed"
- "可以了" / "working now"
- "问题解决了" / "problem solved"

**关键模式检测：**
当同一类问题出现 3 次以上时，CE 自动在 `docs/solutions/patterns/critical-patterns.md` 创建关键模式条目。

### 5.4 双层记忆系统

组合使用时，你的项目拥有两层记忆：

| 记忆层 | 工具 | 存储位置 | 特点 |
|--------|------|---------|------|
| 项目偏好 | gstack `/learn` | `~/.gstack/` | 跨 session 的模式/偏好/陷阱 |
| 结构化知识 | CE `/ce:compound` | `docs/solutions/` | 可检索的解决方案知识库 |
| 团队复盘 | gstack `/retro` | Sprint 统计 | 人/速度/测试健康趋势 |
| 项目配置 | `CLAUDE.md` | 项目根目录 | Claude Code 自动加载 |

**最佳实践：** `/learn` 管偏好（"这个项目用 tabs 不是 spaces"），`/ce:compound` 管知识（"N+1 查询的根因和修复方案"）。两者互补不重复。

**多 Sprint 并行**（gstack Conductor 模式）：
```bash
# 在不同 worktree 中并行开发
/workflows:work --feature="user-auth"     # worktree 1
/workflows:work --feature="payment-api"   # worktree 2
/workflows:work --feature="dashboard-ui"  # worktree 3
```

**研究并行**（CE Plan 阶段自动）：
- `repo-research-analyst`：分析代码库模式
- `best-practices-researcher`：搜索行业最佳实践
- `framework-docs-researcher`：查找框架文档
- `learnings-researcher`：检索 docs/solutions/ 历史经验

### 5.5 审查分层策略

```
第一层：CE /ce:review（自动化专项审查）
├── kieran-rails-reviewer（代码风格）
├── dhh-rails-reviewer（架构哲学）
├── security-sentinel（安全）
├── performance-oracle（性能）
├── architecture-strategist（架构）
├── pattern-recognition-specialist（模式识别）
├── code-philosopher（代码哲学）
├── code-simplicity-reviewer（简洁性）
├── + 数据库迁移时自动启用 data-migration-expert
├── + 部署验证时自动启用 deployment-verification-agent
    │
第二层：gstack /review（Staff Engineer 视角）
├── 结构性缺陷：N+1 查询、竞态条件、信任边界
├── 自动修复明显问题，标记模糊问题
└── Greptile PR 评论智能分类（有效/已修复/误报）
    │
第三层：gstack /codex（跨模型交叉验证）
└── OpenAI Codex 独立审查，与 Claude 审查结果交叉对比
```

### 5.6 避免常见陷阱

1. **不要跳过 Plan 阶段**：CE 的 `learnings-researcher` 能在 30 秒内从 `docs/solutions/` 找到历史经验
2. **善用 /autoplan**：中小需求用 `/autoplan` 一键完成三轮审查，不必逐步跑
3. **不要省略浏览器测试**：gstack 的 `/qa` 用真实 Chromium 测试，能发现自动化测试遗漏的问题
4. **不要忽视 /retro**：定期复盘，gstack 的 `/retro` 会给出每个人的交付统计和测试健康趋势
5. **保持 CLAUDE.md 更新**：项目配置文件应该随项目演进持续更新
6. **用 /learn 管偏好**：`/learn` 能检索、修剪、导出跨 session 学习的模式和偏好
7. **注意 CE MCP 配置**：Playwright 和 Context7 服务器安装后可能需手动配置或重启

## 六、典型场景示例

### 场景 A：新功能开发

```
Day 1:
  /office-hours          → 讨论功能想法，确定 MVP 范围
  /autoplan              → 一键完成 CEO → 设计 → Eng 三轮审查
  （或分步：/plan-ceo-review → /plan-design-review → /plan-eng-review）

Day 2:
  /ce:plan               → CE 研究代理检索历史经验 + 最佳实践
                          → 生成详细实施计划 plans/user-auth.md
  /ce:work               → worktree 隔离开发，持续测试

Day 3:
  /ce:review             → 13+ 专项 Reviewer 并行审查 + Ultra-Thinking
  /review                → gstack Staff Engineer 审查
  /codex                 → OpenAI Codex 交叉验证（可选）
  /qa                    → 真实浏览器端到端测试

Day 4:
  /ship                  → 部署上线（自动调 /document-release）
  /canary                → 金丝雀验证
  /ce:compound           → 沉淀本次开发经验到 docs/solutions/
  /retro                 → 团队复盘（含个人统计和测试趋势）
```

### 场景 B：紧急 Bug 修复

```
紧急响应:
  /investigate           → gstack 系统化根因调试（不改代码先调查）
  /ce:plan               → CE 检索 docs/solutions/ 有无历史经验
  /ce:work               → 快速修复
  /ce:review             → 安全 + 正确性审查
  /land-and-deploy       → 立即部署（合并 → 等待 CI → 验证生产健康）
  /ce:compound           → 沉淀 Bug 根因和修复方案
```

### 场景 C：技术债务清理

```
规划阶段:
  /plan-eng-review       → 评估技术债务优先级
  /ce:plan               → 详细重构计划（含历史经验检索）

执行阶段:
  /careful               → gstack 谨慎模式（拦截危险命令）
  /guard                 → /careful + /freeze 全安全模式
  /ce:work               → worktree 隔离重构
  /ce:review             → 全面审查（含 data-migration-expert）
  /benchmark             → 性能基准测试对比

收尾:
  /qa                    → 全面回归测试
  /ce:compound           → 沉淀重构经验和性能数据
  /retro                 → 团队复盘
```

## 八、总结

### 核心理念

> **gstack 是锋利的手术刀，CE 是完整的知识管理系统。组合使用，既能精准决策，又能持续积累。**

### 价值金字塔

```
          ┌─────────┐
          │  永续型   │  ← CE Compound + gstack Retro
          │  Agent   │     持续沉淀，避免重复错误
          ├─────────┤
          │  质量保证  │  ← CE Review + gstack QA
          │         │     多层审查 + 真实测试
          ├─────────┤
          │  高效执行  │  ← CE Work + gstack Ship
          │         │     worktree 隔离 + 自动部署
          ├─────────┤
          │  精准决策  │  ← gstack CEO/Eng Review
          │         │     产品 + 技术双视角把关
          └─────────┘
```
