# Harness AIOps 实战：基于 LangChain 构建生产级分布式流水线诊断智能体

作者：Ray 的银河技术

## 核心矛盾

日志量大噪声多 → 不能整包丢给模型
故障诊断依赖多个外部系统 → 必须通过工具调用拿动态事实
诊断过程多阶段 → 推理 + 检索 + 校验 + 补充查询 + 风险判断
高风险动作不能直接执行 → 必须经过策略与人工审批
系统要扛住发布洪峰 → 不能拖垮 CI/CD 平台

## 系统架构

### 六层架构

1. **入口层**：身份校验、请求标准化、投递异步任务（不直接调模型）
2. **编排层**：生成诊断上下文、调用 LLM 规划、驱动工具调用、产出结构化结论（LangChain 主要用在这层）
3. **工具层**：Harness API、K8s、日志、监控、知识库（独立可测试、可限流、可审计）
4. **记忆与状态层**：Redis（会话上下文 + 缓存）+ Postgres（审计 + 任务状态持久化）
5. **模型层**：统一模型网关，统一路由、超时、重试、配额、日志脱敏
6. **治理层**：访问控制、工具白名单、参数校验、限流熔断、脱敏、审计、审批

### 控制面与执行面分离

- **控制面**：决策与约束（任务定义、允许工具集、调用次数上限、风险分级、降级策略）
- **执行面**：事实获取（访问 Harness API、K8s、日志等）

## 五阶段诊断执行流

1. **事件归一化**：统一映射为诊断任务（pipelineExecutionId, accountId, serviceId, envId 等）
2. **快速上下文构建**：只读工具拉取基础事实（但不拉原始日志全文——“日志不是上下文资产，是噪声资产”）
3. **受约束推理与工具补查**：模型思考一次 → 调用工具 → 拿到观察 → 继续推理（ReAct）
4. **结构化结论输出**：故障类型、根因、证据列表、影响范围、建议动作、风险等级、置信度
5. **结果落库与事件回传**

## 生产工程要点

### 数据流

- 原始日志不能直接进模型：去时间戳/ANSI/空行，识别错误模式（CrashLoopBackOff, OOMKilled 等），按 Stage/Step 分段，长日志做分层摘要
- 历史案例不能只存向量：必须有故障类型、组件名、环境、错误码、修复动作等元数据。检索用「向量召回 + 元数据过滤 + 规则重排」
- 诊断结果反哺知识库：新案例、误判样本、人工修复路径、无效工具调用轨迹

### 代码骨架关键原则

- 统一任务模型（DiagnosisRequest / DiagnosisConclusion Pydantic model）
- Harness 客户端封装：长连接复用、并发信号量、超时重试、429 单独处理
- 工具层预处理：标准化日志 → 提取错误信号 → 摘要
- 记忆外置化到 Redis：多 Pod 共享、异步任务延续、重启不丢
- Agent 约束：temperature 低、max_iterations 限制、要求区分事实/推断/假设
- 异步任务状态机 + 幂等消费：request_id 去重
- 高风险工具必须走审批流

### 高并发设计

- 入口异步化（先削峰再诊断）
- 工具按维度隔离（独立信号量/超时/熔断器/缓存）
- 模型调用按等级分池（快速诊断池 / 深度诊断池 / 回放评估池）
- 三层缓存（结果缓存 / 知识缓存 / 语义缓存）
- 故障降级策略（Harness API 限流 → 用缓存快照；日志超时 → 回退到元信息；主模型不可用 → 降级规则引擎）

## 失败模式总结

1. 原始日志直接喂给模型 → Token 浪费、结论漂移、成本失控
2. 只做聊天不做状态机 → 无法恢复
3. 模型持有过高权限 → 误判升级为误操作
4. 没有证据分层 → 工程师失去信任
5. 缺少评估闭环 → 无法持续优化

## 生产落地路线

1. **只读诊断 MVP**：Harness 执行详情 + 部署日志 + 历史案例知识库
2. **分布式编排与可观测**：消息队列 + Redis + Postgres + Tracing + 回放
3. **多智能体与自动处置闭环**：初筛 → 深挖 → 审批 → 评估（变更执行仍在审批流之后）

## 一句话总结

> 把智能体当成受约束的诊断系统，把工具层做成标准化事实接口，把异步编排、幂等状态机和治理能力放在模型之前，把每一次诊断结果沉淀为下一次诊断的知识资产。
