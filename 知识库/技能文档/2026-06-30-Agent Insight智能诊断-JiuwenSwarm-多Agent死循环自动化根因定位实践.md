# Agent Insight智能诊断 × JiuwenSwarm：多Agent死循环的自动化根因定位实践

> 一个跑了 600 多步、烧掉 900 万 Token、执行了十多个小时却始终「在动」的多智能体团队，为什么所有传统监控都显示绿灯？本文用 JiuwenSwarm 上一次真实的故障，讲清 Agent 故障的特殊性，以及 Agent Insight 智能诊断 Agent 的解法。

> 模型越来越聪明，Agent 却越来越难被「看懂」。当一群智能体像蜂群一样协同作战，单点报错的旧地图，已经画不出故障的全貌——我们需要一套能读懂智能体「认知」与「轨迹」的诊断引擎。

## 一、Agent故障与传统故障，本质上不是同一种东西

**传统软件故障**是确定性的：一段代码、一个空指针、一行越界访问，栈帧里写得清清楚楚，复现一次就能定位。它是**点状**的。

**Agent故障**则完全不同。一个Agent的一步行动，背后是「回忆历史 → 评估进展 → 规划下一步 → 调用工具 → 接收环境反馈」这条认知链。链上任何一环出问题，都不会立刻报错，而是被悄悄带入后续每一步，在十几轮之后才以一个面目全非的症状爆发出来。

更棘手的是，Agent故障往往**没有「崩溃」**。进程活着、工具在调、Token在涨、日志在刷，一切「健康指标」都是绿的，但任务就是**永远不收敛**。这种「一直在动，却永远到不了终点」的形态，是传统 APM、日志告警、健康检查的彻底盲区。

## 二、Agent故障诊断，要先翻过三道技术坎

学术界第一个系统研究自动故障归因的工作（Who&When，宾州州立 / 杜克）给出了一组冷峻的数字：即便用最强的方法，**识别「是哪个Agent出了错」也只有约53.5%的准确率，而精确定位「决定性错误步」只有约14.2%**。

- **第一坎·上下文太长，又不能不看。** 一次长程任务动辄数百个step、几十万Token。全量喂给LLM做推理，成本爆炸且注意力涣散；只看摘要，又会漏掉藏在细节里的真因。
- **第二坎·单步看都「没大错」，合起来才是灾难。** 死循环里的每一步，单独看可能只是一次「冗余调用」或「低效计划」。逐step检测会把它们打散成一堆低分小问题。
- **第三坎·因果会级联，根因常被症状盖住。** 第2步的一个错误规划，会引发第3步参数错、第4步工具失败……到最后报错的位置，离真正的根因可能隔着几十步。

## 三、Agent Insight智能诊断Agent的解法

Agent Insight的智能诊断能力（内部代号`AgentDebug`），核心是一条**「逐step认知错误检测 + 单点根因定位」**的流水线，由确定性Python脚本先做硬规则判错，再由智能诊断Agent补充语义判断。

### 把每一步行动，拆成五个认知维度

诊断的最小单元，是Agent的一个**「轮次」**。每个轮次被拆解为五个模块：

1. **记忆（Memory）** — 记住正确的历史上下文
2. **反思（Reflection）** — 正确评估上一步结果
3. **规划（Planning）** — 做出合理的下一步决策
4. **工具（Tool Use）** — 正确调用工具、传参
5. **环境反馈（Environment）** — 正确理解系统返回

### 判错机制：脚本确定 + LLM语义

关键原则：**凡是能从真实证据确定读出来的，绝不交给大模型猜**。

| 证据来源 | 含义 | 置信度 |
|:--|:--|:--|
| 真实工具调用 | 从raw tool call确定性提取 | 0.95 |
| 外部系统证据 | status=error、超时、上下文溢出等 | 0.95 |
| 明确标签 | 带显式动作/状态标签 | 0.85–0.9 |
| 可见文本/规则抽取 | 正则命中或可见输出推断 | 0.65–0.8 |
| LLM语义补充 | 记忆/反思/计划的内容正误判断 | 0.5–0.75 |

### 诊断者自己也被上了「镣铐」

诊断Agent被skill严格约束：
- **禁止编造Action** — 动作必须来自真实工具调用或明确动作标签
- **禁止反推** — 不能因为Action/System失败就倒推「Planning一定也错了」
- **禁止修改项目文件** — 只跑分析与校验脚本，零副作用
- **输出必须是纯结构化JSON** — 不许夹带自然语言碎碎念

### 降噪闸门：只报真问题

逐step全量检测会产出海量低级问题，只有满足以下条件之一才会提升为关注的finding：
- 直接导致最终失败或结果偏差
- 问题没有被恢复，或恢复代价明显
- 造成额外轮次、额外工具调用、额外成本或明显延迟
- 违反硬约束、安全约束或关键用户约束
- 重复出现、具备明确优化价值

### 两套并行引擎

这是Agent Insight最关键的设计：

- **认知诊断（cognitive）** — 三阶段：系统预检 → 逐step五模块检测 → 根因归因。原则是**「找最早的、修复后最可能改善轨迹的错误」**作为根因。擅长**单点定位**。
- **轨迹诊断（trajectory）** — 由确定性代码直接读取原始交互记录的结构化元数据，零LLM成本。专门检测跨区间的时序与模式信号——同一文件反复读取、Token单调上涨却无进展、任务状态长期不更新。擅长**宏观模式**。

### 长上下文策略：三层数据 + 按需点读

- **第一层·执行摘要**（≤8000字符）
- **第二层·归一化Step摘要**（约40000字符，长trace每轮次压到约85字符）
- **第三层·完整Trace资料包**落盘到磁盘

## 四、认识JiuwenSwarm

**JiuwenSwarm** 是openJiuwen开源的蜂群智能体框架，核心公式：`Agent = Model + Harness`。把单兵Agent编织成**「蜂群」**：

- **分级自主协同** — Leader Agent动态组队、规划、审批；Teammate Agent各自执行
- **团队工作空间** — 每个成员在隔离独立空间运行，上下文互不污染
- **模型路由** — 按任务难度动态分配模型，Token用量可降低约三成
- **安全护栏与停止条件** — Rails钩子对权限、预算、调用边界施加约束
- **技能复用与自演进** — 成功协作可沉淀为标准化技能包

已在政企场景规模化落地：**中国邮政储蓄银行**基于它打造PSBC-Claw金融专属蜂群；被**华为云、鸿蒙、昇腾/鲲鹏**全系内置；与中国科学技术大学、昇思MindSpore共建「灵境造物」科研平台。

## 五、实战：一次「设计评审死循环」的自动化定位

### 故障现场

`aet-engineering-team-swarm`是一个基于JiuwenSwarm的多Agent研发团队，由五个专业Agent串成流水线：需求分析师 → 分析评审 → 系统设计师 → **设计评审** → 实现者。其中`design-reviewer`（设计评审员）必须读取完整的《功能设计说明书》才能给出评审结论。

诡异之处：界面上每一项「健康指标」都是绿的，流水线「按预期推进」，可任务就是**永远卡在G4评审、永远等不到结果**。

### 根因分析

根子在框架的一个善意机制上。JiuwenSwarm的`MessageSummaryOffloader`会把超过阈值的大工具结果**自动压缩为摘要并offload到磁盘**以节省上下文。于是死循环诞生了：

> reviewer拿到摘要 → 判定被截断需要全文 → 重新读取文件 → 又被offloader压缩 → Leader催促后再重读…… **无限空转，下游任务永久阻塞**

代价：**十多个小时、600多步、约900万Token**，而传统监控自始至终显示一切正常。

### 轨迹诊断介入

轨迹诊断器直接读取原始交互记录的结构化元数据，立刻连成一片清晰的模式：

| 检测信号 | 在本案例中的表现 |
|:--|:--|
| 同一文件反复读取 | `read_file(设计说明书)`在后段trace中出现数十次 |
| 任务状态不前进 | `update_task`在大量step中始终为`false` |
| input token单调上涨 | 每次offload的摘要不断累积进输入上下文 |
| 同一offload主题反复出现 | `compression + summary`模式在30+ step持续重复 |
| 无净进展时间跨度 | 从首次读取到最终中断，跨越数百个节点 |

**轨迹诊断结论：**
- 起点Span：节点#68（首次读取设计文档）
- 终点Span：节点#470（最终中断）
- 循环周期数：37次完整「读取-被压缩」循环
- 修复建议：在评审员提示词中加入防循环守卫，检测到连续3次相同文件读取且任务状态未更新时主动跳过

### 架构上的重要一课

> 有人会问，检测循环不就是grep一下重复读取吗？难点恰恰不在「发现重复」，而在判定**「无净进展」**——要把空转死循环和正常的重试、轮询、迭代区分开。

认知诊断与轨迹诊断**共享同一份`findings[]`**，UI按`kind`渲染不同卡片：
- 认知诊断回答**「哪里开始错的」**
- 轨迹诊断回答**「整体为什么不收敛」**

### 定位效果

从**数小时人工排查**到**一键10分钟**，定位质量稳定，给出可执行的防循环修复建议。

## 六、诊断不止于报告：从「观测→评测→诊断→优化」闭环到进化飞轮

Agent Insight构建了**「观测 → 评测 → 诊断 → 优化」**的完整闭环：

- **闭合方式一（平台内闭环）** — 诊断结论沉淀为可复用优化资产，错误模式、收敛性基线回流到观测与评测两端
- **闭合方式二（外溢给自进化框架）** — 诊断结果作为结构化`findings[]`喂给支持自进化的Agent框架（如JiuwenSwarm），由框架把改进归因到具体Skill并固化到SKILL.md

## 结语

Agent不再单兵作战，故障也不再是孤立的一个坏点。**Agent Insight**（openEuler孵化的AgentOps平台）为每个Agent提供「可观测、可评估、可自我进化」的底座能力，而**JiuwenSwarm**把单兵驾驭成系统、把系统编织成蜂群。两者互为表里。
