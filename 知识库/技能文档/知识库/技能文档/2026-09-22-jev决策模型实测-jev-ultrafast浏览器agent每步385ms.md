# Jev 决策模型实测：jev-ultrafast 浏览器 Agent 每步 385ms

## 概述

作者把爆火的 Jec/Jev 生态拆成两个名字讲清楚，并在两个真实系统上实测：**Jev 是 TypeSafe AI 出的决策模型（System One 模型），jev-ultrafast 是 Browser Use 用它搭的浏览器 Agent——名字像但不是一回事**。实测一是本地电商系统（元气购）从点类目到提交订单，订单真实落库（订单 #28，SKU 逐项精确匹配，库存 19→18）；实测二是 Selenium 官方 WebForm 页，8 项表单验证全通过，还顺带逼出一个传统写法会漏掉的真实缺陷。核心数据：决策延迟中位数 385ms（三次独立运行 p50 = 396/417/406ms，落在 20ms 区间内），全程 720K token 仅花 $0.0291。

## 01 概念区分：Jev 是模型，jev-ultrafast 是应用

- **Jev**：TypeSafe AI 旗舰模型，第一个 "System One Model"。定位与「生成文本给人读」的 LLM 相对——专门**做判断，输出程序能直接消费的结构化结果**。输入「状态 + 问题」，返回「带类型的值 + 概率分布」，本质是分类/决策模型。解决的是错配问题：强迫文本生成系统输出结构化决策，再解析回代码能依赖的东西。
- **三种 AI primitives（问法）**：可混在同一次 API 调用里，**并行、独立针对同一份状态评估**；官方口径 "Adding questions barely changes the response time"（多加问题几乎不增加响应时间），且避免 context-rot（每个问题独立评估不互相污染）。"输出免费"。
- **jev-ultrafast**：Browser Use 用 Jev 做决策层搭的浏览器 Agent，把「一步该做什么」压缩成一次网络请求。官方定位 "A browser agent with a dynamic, indexed action space"（动态带索引的动作空间）。
- **明确不做**：不处理弹窗新标签页、不操作 password/file/hidden 输入框、不做站点级硬编码。
- 比喻（引自腾讯技术工程文）：**Jev 是拿手柄的玩家，普通代码是游戏本身**——代码把局面整理成结构化数据，模型只选动作；它看的是状态描述，不是屏幕截图。

## 02 架构：两级模型 + 一个真实浏览器

三层架构，核心一句话：**两级模型不是同一模型的两次调用，而是两个厂家、不同职责的模型；Jev 一个字都不写，生成模型一个决策都不做**。

1. **决策层 = Jev，硬编码不可替换**。endpoint 写死 `https://api.typesafe.ai/v1/systemone`，只能用 `TYPESAFE_API_KEY`。换 GPT/Claude 在设计上就不成立——Jev 返回的不是文本而是经约束校验的结构化答案，`validate_choice()` 四项硬校验：选择必须在候选集内 / 概率必须覆盖所有候选 / 概率必须归一化（Σ≈1±0.02）/ 选中的必须真是最大值。任何一项不过直接抛 `Invalid TypeSafe response`。**零重试、零格式错误**。实测返回版本号 `jev-1.13.0`（请求写 `jev-latest`）。
2. **二级文本模型只在需要写字时唤醒**（仅 `TYPE_TEXT` 操作触发）。标准 OpenAI 兼容接口，可接 DeepSeek/Gemini/GLM/火山方舟。作者用**火山方舟 doubao-seed-2.0-mini**。
3. **执行层是真实浏览器**：browser-harness 用 CDP 连**当前正在用的 Chrome**——登录态、Cookie、插件全在，反爬基本不成立；代价是要给 Chrome 开远程调试权限。每次 `Agent.__init__` 自建一个后台标签页，从头到尾只操作这一个，不支持切换标签页。

## 03 工作原理：一次请求，两个决策

- **每轮观察**：`snapshot.js` 产出一张编号元素表（role + label + 可用操作）。三条关键过滤规则（后面所有坑的根源）：
  - `safe()`：排除 `password / file / hidden` 类型输入框；
  - 安全 + 可见 + 未禁用：`disabled` 的元素**根本不进元素表**；
  - 必须在视口内：折叠线以下（y > innerHeight）的元素不可见。
  - `SCROLL_DOWN` 只有页面还能往下滚才出现在候选里，步长固定 560px。
- **一次 POST 问多个原子问题**：`operation`（做什么：CLICK/SCROLL_DOWN/WAIT/DONE/BLOCKED）+ `click_target`（点哪个）。**`click_target` 是投机性的**——选了 CLICK 才用得上，否则作废。一次网络往返拿到「做什么」和「对谁做」，这就是 385ms 的来源：**不是模型快，是省掉了整个"先想再找"的二段式流程**。
- **返回的是概率分布**，不是一句"我觉得应该点这里"：`{"operation": "BLOCKED", "confidence": 0.42, "operation_probabilities": {...}, "latency_ms": 1671}`。confidence + 概率分布天然是**可观测信号**：置信 0.97/P 1.00 = 放心执行；置信 0.35 = 模型在候选间犹豫（通常是 goal 写得不清楚或页面有多个候选）。⚠️ **confidence 不是"正确概率"**，做自动告警前需先校准。
- `recent_actions` 只带最近 10 条，页面状态不做语义理解——**"快"建立在"无记忆"之上**。

## 04 API Key 申请

typesafe.ai 官网（需 Google 账号 + 科学上网）→ console.typesafe.ai/login → API Keys 创建（**只显示一次**）。新用户送 $5（一个月有效）。两套 key（TYPESAFE / TEXT_MODEL）完全独立，最易配错。

## 05 用法与四个坑

**安装**：`git clone` → `uv sync` → 填 `.env` → `uv run jev` → `http://127.0.0.1:8766` 控制台。控制台 Debug 面板实时显示元素表、operation/target 概率分布、实际动作；`Choose next` 可暂停在执行前，调 goal 神器。也可当库用（`Agent(url, goal)`），推荐第三种用法：**自己接状态流落 JSON**——`state["history"]` 每步有 operation/confidence/probability/latency_ms，`decisions[]` 里有发给模型的完整请求体，这是做质量度量的真价值。

**调 goal 三条血泪经验**：① 写清「不要做什么」（一句"不要点返回购物车"省 50 步）；② 明确提示滚动（"看不见就 SCROLL_DOWN"写进 goal，否则模型倾向判 BLOCKED——滚动行为不是它自己想到的，是你告诉它的）；③ 分阶段写（【阶段一】【阶段二】远胜流水账）。

**坑一：模型配置**。一级/二级报错完全隔离，二级配错只在"写字"时才炸。`TEXT_MODEL` 填模型名不是 URL。
**坑二：`TEXT_MODEL_REASONING` 方言**。DeepSeek 用 `thinking`，其他家默认 `reasoning.effort`，`none` 统一覆盖成 `reasoning.enabled=false`。方舟对 reasoning 字段敏感，换厂商报 400 先查这里。
**坑三：Chrome 远程调试 `DevToolsActivePort not found`**。Chrome 136+ 默认 profile 禁止自动开远程调试，144+ 要求手动授权（`Local State` 里 `devtools.remote_debugging.user-enabled: null` = 从没开过）。解法：手动授权 `chrome://inspect/#remote-debugging` / `uv run browser-harness mac-approve` / 独立实例 `--remote-debugging-port=9222 --user-data-dir=/tmp/cdp-profile`。附加坑：daemon 附着的标签页闲置两小时会话失效报 `Runtime.evaluate timed out`，`pkill -f browser_harness.daemon` 后 `--doctor` 重连。
**坑四：密码框不在模型视野**。`safe()` 主动屏蔽 password 输入框。实测模型在"手机号"框里连填 4 次（置信度 0.96→0.70 递减）后 BLOCKED——页面上有两个输入框但它只能看见一个。**结论：登录环节先人工做好，Agent 直接拿登录态**。支付扫码同理（外部凭证环节 Agent 天然无解）。

## 06 案例一：元气购下单（goal 三版演进，最精彩的部分）

同一模型/代码/动作空间，只改 goal 措辞：

| 版本 | 措辞 | 结果 |
|------|------|------|
| v1 | 流水账 | 4 步卡死 BLOCKED（颜色在视口外+购买按钮 disabled 不进元素表——"它要选的看不见，想点的不存在"） |
| v2 | 加滚动提示 | 23 步走到结算页但震荡（提交订单按钮在视口外，反复点"返回购物车/去结算"，置信度 0.17-0.22——模型自己都知道不靠谱） |
| v3 | 分阶段+明确禁令 | **10 步 7.456 秒打通**，第 8/9/10 步置信度 0.91/0.93/0.97 |

- v3 关键措辞：确认订单页三项都已默认选中"不要再点击"、"返回购物车"是回头路不要点、提交按钮在表单最下方先 SCROLL_DOWN 几次、只有滚到底确认没有才准选 BLOCKED。
- **订单真的落库**：订单 #28，SKU 488（24GB/1TB/深空灰）逐项精确匹配，库存 19→18。
- **隔夜复现**：相同代码+goal 第二天重跑，10 步逐步骤一模一样，p50 相差 4ms（385 vs 381）。
- **结构性边界**：提交后"微信支付"环节重复点了 50 次耗尽 60 步预算，置信度 0.88→0.42 衰减——不是偶发 bug，是外部凭证环节的结构性边界，两次运行都雷打不动点 50 次。

## 07 案例二：Selenium WebForm（8/8 通过 + 逼出隐藏缺陷）

公网页面（不能作弊）、字段类型齐全、被全世界教程用过无数遍。密码框再次从元素表消失——**同一过滤规则在完全不同站点表现一致，是引擎的确定性行为**。处置同案例一：底层 JS 通道注入密码，其余步骤 Agent 决策。6 个动作步 12.1 秒，服务端 URL query 回显 8 项验证全过（my-text/my-password/my-select/my-datalist/my-radio/my-date）。**顺带逼出一个 datepicker 缺陷**："值在 DOM 里但提交时丢失"，靠逐步骤探针+事件日志精确定位到 blur 那一刻——它不是被"跑通"发现的，是被真实交互序列逼出来的。

## 08 实测数据汇总

- **延迟稳定性**：元气购 60 步样本 p50=385ms；三运行 p50 = 396/417/406ms，两站点两任务类型落在 20ms 区间。第一步冷启动规律性 ~1716ms（HTTP/2 建连+服务端冷启动）。
- **耗时构成（提效边界的关键表）**：元气购全程零文本生成 → 决策模型占 73~83%，优势完全释放（10 步 6.5s）；WebForm 有 3 个字段要填 → 文本模型吃掉 63%（6 步 12.1s）。二级模型单次 1.9~3.9s，比一级决策慢近一个数量级。**选型第一判断：任务里"要写字"的比例有多高**。
- **二级模型调用**：7 次生成 7 次准确，零编造（含从上下文理解 datalist 该填 New York）。
- **反直觉发现**：同一页面零历史单步决策，两次独立采样 confidence 0.42/0.44、分布只差 0.01——判 BLOCKED 而非"先滚一下"。输出稳定性极好，不是随机抽卡。
- **成本**：两场景多次实测共 720K token，$0.0291。

## 写在最后：作者判断

- **价值排序（"快"只排第三）**：① **决策可观测性**——把"下一步操作哪个元素"从代码选择器和 LLM 黑箱里的隐式逻辑，变成带概率、带置信度、可断言、可告警的显式决策数据（UI 自动化第一次有了"决策可观测性"）；② **可定位性**——元素表 vs 页面文本对照一眼看出谁被过滤了，trace 落盘不用重跑就能回放（"Selenium 挂了你得猜定位器错了还是页面变了；jev 挂了你看元素表就知道"）；③ **延迟确定性**——"每次都一样快"比"快"值钱，意味着**可以给 Agent 算 SLA**；④ 真实业务产出（有服务端凭据对账）。
- **但划清边界**：给的是**决策层的可观测性，不是执行层的可靠性**——浏览器慢、页面超时、元素定位失败一个都没解决。定位是"决策引擎"，不是 UI 自动化框架的替代品。省的是**编写时间**不是运行时间，定位是"补充"不是"替代"。
- **核心结论**：Agent 的能力上限不取决于模型多强，取决于你怎么把任务描述给它——v1 卡死到 v3 十步完成，差的是一段结构化任务描述。这与写测试用例的逻辑相通：把"不要点返回"这种边界条件写进用例，Agent 才不会踩；写"订单列表最新订单 SKU 必须是 488"它才知道看哪儿。
- **边界声明即安全声明**：屏蔽密码框/不支持新标签页，起初像缺陷，实则是明确边界——认证、支付、跨标签页交给人。**一个知道自己不该做什么的 Agent，比什么都敢试的 Agent 更好用**，因为你敢把它放到生产流量旁边。
- **Jev 的生态位**：上被大模型厂商挤压（结构化输出/低延迟小模型/蒸馏），下被传统分类器和专用小模型挤压（任务稳定标签固定时更便宜）。甜点区 = 需要通用语义理解 + 规则候选变化频繁 + 不愿为每个小判断单独训模型。**浏览器自动化正好落在这里**：网页千变万化不能写死规则，但每步候选动作有限。判断次数 : 写字次数 ≈ 17:2 时这个架构划算；写字越多，价值越被生成调用淹没。
- 单次"跑通"没价值，**能每天在 CI 里稳定跑通 N 次才是测试开发该干的事**。

## 战略分析

这篇是知识库浏览器 Agent 技术路线带的最新节点：[[2026-07-03-GUI-Agent全景-Page-Agent-browser-use-Stagehand-Skyvern技术路线解析]]（五路线横评，browser-use 属"LLM 看截图"派）→ [[2026-08-09-桌面自动化探究-AI-GUI-Agent四项目对比]] → [[2026-09-02-BrowserOS-带登录态本地AI浏览器]]（登录态路线）。**本文记录的是 browser-use 官方自己的路线转向信号**：从"截图 → 大模型 → 文本 → 解析"转向"结构化 DOM → 决策模型出概率分布"，且 6 天 1.7 万星（MIT、Python、2026-09-16 创建，实测日核实）——这个热度说明"决策/生成分离"击中了一个真实的工程痛点。

与现有栈（Hermes Agent 的 browser_exec CDP 工具链）对照：Hermes 的浏览器决策走 LLM 直接推理，输出是"黑箱"文本动作；Jev 路线的差异化主张是**每步决策带概率分布 + confidence，可断言、可告警、可算 SLA**。对测试场景（本文主战场）这是从"AI 魔法"到"工程组件"的分水岭；对通用 Agent 任务，价值取决于"判断次数远多于写字次数"的任务构成。

可直接借鉴、不依赖 Jev 本身的三个点：① **goal 工程化三原则**（分阶段、写明禁令、显式滚动提示）对包括 Hermes browser_exec 在内的一切浏览器 Agent 任务描述通用——v1 卡死到 v3 十步打通的对比就是证据；② **validate_choice 式的四项硬校验**是"结构化输出零重试零格式错误"的落地范式，值得在任何 Agent 工具调用层复刻；③ **trace 落盘 + 决策可观测**的思路（每步操作/置信度/概率/延迟全记录）可以直接用于 Hermes 浏览器任务的调试与质量度量。

落地边界要清楚：需 Google 账号 + 科学上网 + TypeSafe key（新用户 $5/月额度）；Chrome 136+ 远程调试授权是本机第一个会撞的坑（mac-approve 可解）；密码/支付/新标签页是设计上就不碰的边界——这反而是它敢放在生产流量旁边的原因。判断：**架构思想（System One 决策模型品类、决策可观测性）比项目本身更值得关注**；若要实测，优先跑"零写字"的高判断密度流程才能看到优势全释放。
