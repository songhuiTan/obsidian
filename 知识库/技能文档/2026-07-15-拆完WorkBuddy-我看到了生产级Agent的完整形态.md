> 为什么 90% 的 Agent，最终都进不了生产环境？

Agent 一旦放进生产环境，问题立刻暴露：漏步骤、传错参数、长任务跑散、用户确认过的下一次又重问、失败只能从头再来。Demo 很封面，现实很骨感。

## 一、找场景 > 选框架

传统产品起点是功能，Agent 产品起点是 Use Case。第一步不是选模型、选框架，而是明确用例。

> 现阶段不存在通用 Agent，先找真实场景里的高价值闭环。

场景价值公式：
> 场景价值 = 任务价值 × 可执行程度 × 可验证程度 ÷ 失败风险

## 二、三类典型 Agent 场景

| 类型 | 代表场景 | 核心关键 |
|------|---------|---------|
| 生产力工具型 | AI Coding、AI 文档、AI 研究助手 | 工程能力 + 用户体验（上下文管理、工具调用、任务状态） |
| 业务流程型 | 数字员工、CRM 自动化、工单处理 | 模型推理能力 + 业务 KnowHow + 系统集成 |
| 多模态 AIGC | 图片/视频/海报生成 | 效果评估复杂、依赖模型组合与资产管线 |

AI Coding 是天然适合 Agent 闭环的场景：输入输出明确、工具链成熟、可测试验证、可 diff/review/回滚。

## 三、SaaS → Workflow → Agent 演进链

> SaaS 记录业务状态 → Workflow 执行固定流程 → Agent 理解上下文并泛化行动 → 数字员工承担稳定工作

Agent 没办法凭空替代 SaaS，它站在已有系统、流程和数据之上，承担原本需要人类去理解上下文、做判断、推进动作的那一层。

Agent 要打通四类能力：
1. **外部工具** — 搜索、网页、邮箱、代码仓库、第三方 SaaS
2. **内部工具** — 企业 CRM、ERP、工单、知识库、审批系统
3. **数据 API** — 用户数据、业务数据、行为数据、财务数据
4. **业务 SOP 和 KnowHow** — 流程规则、异常判断、专家经验、组织偏好

Workflow 和 Agent 不存在谁替代谁，核心是根据**步骤明确度与失败代价**来分配自由度。

## 四、生产级架构：双视角

### 用户视角四层

1. **入口层** — Chat、模板、文件、事件、集成入口（越贴近工作环境越容易被使用）
2. **执行层** — 核心是可观测性：用户能看到计划、步骤、工具调用、中间结果。可打断、可审阅是衍生
3. **产出层** — 产出必须是完整的、一致的、可保存可修改的
4. **治理层** — 可控、可信、可复盘、可改进，对应第二层的基础设施

### 工程视角五大系统

1. **大脑系统**（Model + Agent Loop）— 循环：观察 → 理解 → 计划 → 选工具 → 执行 → 观察结果 → 更新状态。核心是控制失控
2. **行动系统**（Tools + Runtime）— 工具不在多，选错成本高。最危险的 Tools 是 Coding 本身。Runtime 解决安全与权限
3. **工作台系统**（State + Context + Memory）— 生产级 Agent 设计的核心难点
4. **经验系统**（Prompt + Skill + Workflow）— 薄 Harness，厚 Skill
5. **控制系统**（HITL + Guardrails + Eval）— 高风险动作前让人确认，权限边界安全防护，系统可衡量可改进

## 五、生产级 Agent 的六个阶段

1. **能聊** — Chat UI + 模型调用 + 流式输出 + 历史消息（解决体验入口）
2. **能用工具** — Tool calling，按业务场景渐进，不要一上来接很多工具
3. **能做任务** — 引入 task、step、status、artifact（用户看到完整任务在推进）
4. **能跑长任务** — Runtime、checkpoint、compression、pause/resume、retry policy、cost tracking
5. **能被治理** — 安全权限、Token 成本面板、操作日志、回滚能力
6. **能沉淀能力** — 高频有效经验沉淀为 Skill，包括工程经验和 Agent 参数

> 大家走到哪里了呢？

## 六、常见问题

**Agent 不遵循要求** — 纯 ReAct → 复杂动作封 tool → 对 Agent 友好的代码接口 → Skill → 稳定路径启用 Workflow mode。

**工具调用不稳定** — 名称清晰、参数少而准、输入输出结构化、危险动作需确认。必要时不要让 Agent 手动拼底层工具，直接 dispatch 到 workflow。

**长任务跑散** — checkpoint、step cache、pause/resume、durable execution、artifact 与状态持久化。

> 长任务如果没有状态中心，Agent 看起来像在工作，实际上每一步都像在重新开始。

**记不住用户偏好** — Memory 存储需区分用户偏好、项目事实、业务知识和执行经验，并设计写入策略、召回策略与过期机制。

**用户不敢交出去** — 可观测、可打断、可审阅是重点。用户需要可控的感觉。

### 薄 Harness、厚 Skill

- **Harness** 承载通用能力：Agent Loop、工具注册、状态管理、上下文拼装、Runtime、日志、权限与 HITL
- **Skill** 沉淀场景经验：触发条件、任务边界、工作流步骤、工具协议、数据口径、人工确认节点、产物标准、错误恢复与评估规则

> Harness is built to detail — 在业务场景里的重复失败，反过来逼出 Harness 与 Skill 的边界。

## 七、观测性与自进化

可观测性三层：
1. **工具层** — 工具是否正确选择、参数正确、错误码清晰
2. **Skill 层** — 能否从输入跑到产物、步骤完整、Checkpoint 出现
3. **任务层** — 任务是否完成、用户是否采纳、人工修改率是否下降

> 能用脚本和结构校验解决的，尽量不要交给模型。

生产级 Skill 五个评估维度：正确性、稳定性、覆盖率、成本、可用性。

## 八、结语

生产级 Agent 的核心目标：**让模型在真实任务中稳定地完成工作。**

上生产后，稳定和成本 > 聪明。稳定来自四件事：
1. 场景足够真实
2. 工具调用治理
3. 可观测性
4. 人工补丁（别信自动进化的鬼话）

## 战略分析

这篇文章几乎就是 WorkBuddy（以及延伸的 OpenClaw/Hermes 类 Agent）架构设计的"教材式拆解"。叶小钗把生产级 Agent 从场景定义到工程实现到治理评估的完整链条讲得非常清楚，而且**几乎所有核心概念都跟我们的现有工作直接映射**。

### 与现有体系的对照

| 维度 | 文中概念 | 我们当前状态 |
|------|---------|------------|
| 入口层 | Chat + 模板 + 文件 + 事件 + 集成 | 微信端 Chat 入口为主，事件/Webhook 入口已有（cronjob） |
| 执行层可观测 | 计划展示、步骤进度、Tool 调用日志 | 已有基础进度输出，但缺少结构化任务状态 |
| 工作台/Memory | State + Context + Memory 三层 | TencentDB Memory 已实现 L0-L3 四层，NexSandglass 已备份 |
| 经验系统 | "薄 Harness、厚 Skill" | Hermes 设计理念完全一致，Skill 体系已建立 |
| 控制系统 | HITL + Guardrails + Eval | HITL 在 WeChat 交互中有基础，Guardrails/Eval 待建设 |
| 六个阶段 | 能聊→能用工具→能做任务→能跑长任务→能被治理→能沉淀 | 约在阶段 3-4（能做短任务+部分长任务），治理层薄弱 |

### 关键差距与借鉴点

1. **长任务状态持久化** — 文中的"checkpoint、pause/resume、durable execution"正是我们当前的瓶颈。Hermes 的 cronjob 虽然支持周期性任务，但 Agent 内的长任务（如多步工具调用链）中断恢复仍缺乏 checkpoint 机制。

2. **工具命名与描述打磨** — 文中特别提到"工具越多模型选错成本越高"，提醒我们现在注册工具时命名和描述需要反复推敲，否则 Agent 会在错误的工具上浪费大量 Token。

3. **用户视角的治理层** — "用户不敢把动作交给 Agent"这个问题非常真实。我们的 OpenClaw 和 WorkBuddy 用户反馈中，缺乏"可观测、可打断、可审阅"的体验正是核心痛因。

4. **Skill 的评估维度** — 五个维度（正确性/稳定性/覆盖率/成本/可用性）为我们提供了 Skill 质量度量的框架，可以作为未来 Skill 审核机制的参考标准。

### 值得整合的具体建议

- 将文中"六个阶段"作为 Hermes Agent 的发展路线图参考，制定阶段化演进计划
- 借鉴"Workflow vs Agent 分配自由度"的方法论，在技能系统中显式标记哪些 Skill 适合自由模式、哪些适合 Workflow 模式
- 工具注册时引入"危险等级"和"确认节点"机制，对应文中的 HITL 设计

总的来说，这篇文章不是"该不该做 Agent"的讨论，而是"怎么把 Agent 做好"的工程落地方案，与我们当前的工作阶段高度契合。
