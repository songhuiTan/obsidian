# AI Coding 实战：10年祖传系统，54万行代码，2周重构结束

## 项目背景

- 运行 10 年的老系统
- 54 万行 PHP 代码
- 2 周交付窗口
- 核心电商链路
- PHP → Java 迁移
- 全程依靠 AI，按时平稳交付

## 老系统重构三大难点

1. **量太大，看不完** — 54万行代码无法短时间建立可靠理解，接口调用链复杂，文档缺失，弱类型代码多
2. **时间太紧** — 没有时间完整读透、补文档、从容设计，必须按时交付
3. **风险极高** — 核心系统行为悄悄变化 = 真实损失（金额、库存、导购分支等）

## 核心策略：建立行为基线

**不先追求完整理解，而是先还原系统真实行为。**

以 URL 接口为最小单元做行为还原：
- 实际收什么参数
- 经过哪些逻辑分支
- 返回什么结果
- 访问哪些数据库
- 产生哪些副作用
- 异常情况表现

行为基线立住后 → AI 生成代码有标准、测试有依据、差异分析有锚点。

**核心原则：任务驱动，先完成，再优化。**

## AI 改变的三件事

### 1. 压缩认知成本（最核心价值）
把庞杂无文档的代码压缩成可读、可讨论、可验证的结构化结果：
- 批量梳理接口调用关系
- 提炼参数逻辑和异常分支
- 生成架构图、逻辑图、说明文档
- 提取入参/出参/数据库操作/副作用
- 辅助识别弱类型字段的真实数据分布

> **AI 在遗留系统改造里最大的价值，不是先替你写代码，而是先替你压缩认知成本。**

### 2. 大规模机械翻译和重复改造
- PHP 转 Java 初稿生成
- 函数拆解与重构
- 工具类提取、DTO 化改造
- 强类型替换、冗余逻辑清理

人工注意力集中在：业务逻辑有没有偏、新旧行为有没有变、边界情况有没有漏。

> **AI 可以吞掉翻译成本，但不能替代业务判断。**

### 3. 验证、比对、排障
- 自动生成测试用例（正常/异常/边界场景）
- 辅助白盒测试
- 日志分析和 Debug
- 自动生成新旧差异清单

## 工程化方法论

### 风险分层
| 层级 | 范围 | 策略 |
|------|------|------|
| P0 核心层 | 20%接口/80%风险 | 人工主导，AI 辅助 |
| P1 关键层 | 关键业务 | AI 主导实现，人工严格审核 |
| P2 外围层 | 外围功能 | AI 自主度高，允许技术债务 |

### 强制 Plan 模式
AI 先输出完整实施计划（改哪些文件、分几步、风险点、影响范围、需要确认的点）→ 人工审计划 → 允许执行

> **Plan 模式最大的价值是把 "AI 先开干" 改成 "AI 先暴露思路"。**

### Prompt 升级为规则系统
- 全部按原代码实现，不擅自简化
- PHP→Java 不应用反射
- PHP 中 API 访问统一封装到 Feign
- 改动前必须确认不影响其他逻辑
- 有疑问就问，不允许 AI 自作主张
- Bug 分析必须端到端追踪完整数据流

### 三层验收标准
1. **能跑** — 编译、启动、走通
2. **能对** — 关键行为与旧系统一致
3. **能稳** — 性能、并发、可维护、灰度、回滚能力达标

## 上线策略

影子验证 → 小流量灰度 → 分批切流 → 全量替换 → 观察复盘

回滚预案提前准备好，确保分钟级回滚。

## 核心结论

1. **遗留系统改造被 AI 覆盖** — 理解成本高、重复劳动多、验证链条长，恰恰是 AI 最擅长提效的地方
2. **边界很重要** — 会写提示词 ≠ 会做交付；真正的门槛是风险拆解、边界定义、验证设计、灰度发布和回滚兜底
3. **工程师能力模型变化** — 更重要的是快速理解系统、拆解问题、识别边界、设计工作流、对结果负责

## 典型踩坑

AI 把 `Result<T>` 替换成 `BaseResponseDTO<T>`：
- `message` 变成了 `msg`
- `costTime` 字段丢失
- 调用方依赖 `message` 字段拿值，现在直接拿不到

→ 后端看起来正常，但前端和调用链已经悄悄坏了。

**教训：改动前必须先对比两个类的完整结构，做检查清单。**
