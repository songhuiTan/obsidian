## 一、候选人项目简介

**项目名称：** Depore Search  
**定位：** 面向学术论文检索和综述生成的 Agent 系统  
**核心能力：** 用户开放式输入 → 问题拆解 → 多源检索 → RAG 重排 → 证据级筛查 → 综述生成

**三层架构：**
1. **Agent 架构设计** — 基于 LangGraph / LangChain 的状态机，Plan→ReAct 混合，解决 ReAct 黑盒和死循环问题，每步可知可回溯
2. **检索系统** — 混合检索（语义搜索 + BM25 全文检索 + 多 API 源）→ RAG 重排 → 证据级筛查
3. **数据飞轮** — Bad Case 归因 → 加入策略库 → 逐步提升

## 二、面试拷打要点总结

### 1. 架构选择辩护

**Q：为什么用 Plan→ReAct 而不是纯 ReAct？**
- 纯 ReAct 是黑盒，容易死循环（infinite loop）
- Plan→ReAct 通过状态机全局控制，知道每步在做什么，出错能定位到具体阶段
- 条件边（conditional edges）处理：用户输入不明确 / 目标冲突 → 直接反馈要求澄清

### 2. 检索系统深度

**多源检索策略：**
- Semantic search + BM25 混合检索
- Google Scholar / 内部论文库等多 API 源（兜底网络问题）
- RAG 重排 → 输出 Top-20 → 拆分子段落 → 重新评分 → 筛选 Top-5

**Q：评估指标有哪些？**
- Paper Recall（论文召回率）
- Evidence Support（生成回答是否有证据支撑）
- Citation Accuracy（引用真实性）
- Groundedness（回答是否锚定在证据上）

**关键发现：** 发现指标低后，拆分为"没召回论文"和"召回但证据不足"两个子指标→实验发现召回是瓶颈→针对优化

### 3. 坏例分析与数据飞轮

- 每步记录完整日志：用户意图 → 工具调用 → 召回结果 → 各阶段分数
- 定位 Bad Case 归因到具体阶段
- Bad Case 入库 → 下次类似情况规避
- 例：用户说"帮我找计算机视觉最新论文" → 提取 topic=CV, time=2026, count=3

### 4. 记忆与缓存系统

- 跨轮对话：上下文窗口存摘要（不存全文）
- 材料化：每步生成结构化摘要（用户意图 + 检索结果摘要）
- 两级缓存：内存缓存（近期） → 数据持久化（论文标题/摘要）
- 多用户隔离：不同用户不同数据空间

### 5. 工程化追问

**Q：并发怎么做的？**
- 简单 4 线程，未做深度优化（单人项目无大流量）
- **面试官建议：** 动态线程池、缓存淘汰策略（LRU/TTL）、中间结果持久化便于复盘

**Q：多 Agent 有必要吗？**
- 当前流水线式工作流，单 Agent 够用
- **面试官挑战：** 流水线也可以多进程——前端的检索、后端的重排、最后的评测可拆成独立进程，通过 IPC 通信

### 6. 场景题：电商客服 Agent

**场景：** 用户问商品能否退货（需查订单状态 + 商家规则库）

**候选人回答：**
- 需要后端规则 + 订单状态联合判断
- 出现冲突（规则说可退但订单已签收）→ 优先级排序
- 补充人工客服兜底

**面试官补充：**
- 需要优先级体系（退换货时效 > 商家规则）
- 同等优先级冲突 → 转人工
- 规则条数增加后，需要分层（硬性规则 vs 柔性规则）

## 三、高频面试陷阱

面试中暴露的常见问题（💡 踩坑点）：

| 问题                    | 暴露点                                            | 改进方向                         |
| --------------------- | ---------------------------------------------- | ---------------------------- |
| "没用过多 Agent，因为流水线不需要" | 对多 Agent 的理解局限在"分工不同子任务"，没意识到流水线各阶段也可独立成 Agent | 多 Agent ≠ 多模型，是职责拆分 + IPC    |
| "并发就设了 4 个线程"         | 工程化经验不足，未考虑动态扩容和压测                             | 加锁/线程池/Cache 淘汰策略            |
| "指标低，拆了两个子指标"         | 分析方法论好，但缺少中间状态粒度                               | 每阶段的中间结果（召回列表、评分）都要存，不光存最终指标 |
| "Memory 存在内存里，没考虑容量"  | 缓存淘汰策略缺失                                       | LRU/TTL/过期策略是必问题             |

---

## 四、面试官给的建议

1. **评测要拆到阶段级** — 不只看最终指标，每阶段的输入/输出/分数都要记录，才能精准归因
2. **中间结果可视化** — 完成 log 追踪后，建议做可视化 dashboard（工具如 LangSmith / MLflow）
3. **考虑规模化** — 从"单人可行"到"多人可维护"的差距在于：缓存策略、并发控制、数据隔离、配置化
4. **多 Agent = 职责分离** — 不是只有分工不同的 Agent 才算多 Agent，流水线的不同阶段拆分后通过 IPC 连接就是多进程架构
5. **面试答不上的地方别硬扛** — 说"还没考虑到"比硬编合理，但要能说出如果要做会怎么做
