## 文章概述

本文以一个最小化的 Go 项目 `crypto-snapshot-cli`（CoinPaprika API → JSON 快照导出 CLI）作为贯穿全文的实战案例，从零讲解如何搭建一套完整的 Harness Engineering（脚手架工程）框架。人没有写一行生产代码——所有代码由 AI 完成，人的全部精力放在系统性搭建 Harness 框架上。

---

## 核心概念体系

| 概念 | 作用 | 类比 |
|------|------|------|
| **Rule（规则）** | 告诉 AI 边界在哪里，强制底线约束 | 团队开发政策 |
| **Skill（技能）** | 告诉 AI 在这些边界内如何执行固定动作，标准化高频操作 | 标准操作流程（SOP） |
| **Sub-Agent（子智能体）** | 把大任务拆成多个分工协作的专门角色 | 兵种分工 |
| **Workflow（工作流）** | 规定角色按什么顺序、在什么时候交接 | 接力赛规则 |
| **Script（脚本）** | 根本不指挥 AI，直接客观验证工作是否真的完成 | 安检闸门 |
| **MCP（模型上下文协议）** | 将 AI 连接到外部知识、工具和宿主系统 | 标准化电源接口 |
| **Dev-Map（开发导航图）** | 帮 AI 快速把握项目结构和既有模式 | 项目地图 |
| **Task Board（任务看板）** | 项目级的任务登记表，记录阶段和决策历史 | 态势感知 |

---

## 7 个 Sub-Agent 角色分工

1. **PM（项目经理）**：纯路由型，只管理工作流状态和交接，不做专业/技术判断
2. **需求分析师**：把模糊请求澄清成结构化规范
3. **方案架构师**：把规范转化为可执行的技术设计
4. **Gatekeeper（可行性把关者）**：在编码开始前校验可行性和风险
5. **开发者**：实现代码和技术细节
6. **Code Reviewer（代码审查者）**：校验技术质量、规范对齐和设计还原度
7. **QA/Tester（测试者）**：校验功能正确性、稳定性和边界情况

> 每个角色不是为了复杂而复杂，而是一个个被实际生产中的失败暴露出来后浮现的。

## 关键架构决策

### 结构化编排 vs 去中心化协作
- 固定角色 + 固定流程（结构化编排）是生产工程唯一可行的路径
- 去中心化动态协商在长期维护中会退化成"看起来很厉害但难以维护"
- **Token 不是贵的东西，失去控制才是**

### 模型分级分配
- PM：轻量级模型（只做路由和状态检查）
- 需求/设计/Review/QA：重型高能力模型（深度推理和分析负担）
- 不上所有角色都用最强模型——按任务匹配工具

### 文档边界纪律
- 下游 Agent 不允许直接修改上游产物
- 产物不满足要求 → 提出 blocker → PM 将工作流回滚到上游 Agent 修正
- 每一份产物都有一个唯一的、可追溯的归属者

## 演进路径（从 0 到 1 的步骤）

1. **打磨 SPEC（设计规范）** — 和 AI 反复迭代直到目标/边界/验收标准清晰
2. **加关键 Rule** — 聚焦 AI 经常翻车或偷懒的底线（编译→测试→校验）
3. **沉淀 Skill** — 把高频固定动作（编译、测试、校验）标准化
4. **单 Agent 失稳时才拆 Multi-Agent** — 不要第一天就上多角色
5. **加工作流定义和角色契约** — 阶段/回滚/交接倍增时提取为结构化资产
6. **迭代阶段上 Dev-Map 和 Task Board** — 代码库越大越关键
7. **MCP 留到最后** — 先把内部开发回路闭好

## 主校验脚本（Master Validation Script）

### 核心价值
- 把"完成"从 AI 自我汇报切换成系统可验证的状态
- 合上完整的反馈回路：执行 → 校验 → 发现问题 → 回滚/修复 → 重新校验

### 三层检查
- **A 类（静态规范）**：硬编码密钥、非结构化日志、错误上下文包装缺失等
- **B 类（交付阈值）**：编译零错误、测试 100% 通过、覆盖率不低于基线
- **C 类（工程一致性）**：依赖同步、生成文件未被提交、新增文件纳入构建目标

### 基线对比机制
1. 改动前先跑完整校验套件，保存基线
2. 改完后再跑一遍
3. 两份报告 diff → 任何新增失败/警告/违规 = 必须修复

## 特色观点

- **Harness Engineering 不是关于信任 AI，而是关于设计出让偷懒无处可藏的机制**
- **AI 记忆在生产中是负担** — 成熟的 Harness 用工程产物（git 里的 SPEC/Dev-Map/Task Board）取代 AI 需要"记住"的需求；AI 不需要记忆，它需要导航
- **Rule 是软约束，不是硬关卡** — AI 会遗忘、选择性失效、偷懒绕过；脚本是无争议的最终裁判
- **一个成熟的 Harness 最终会越来越依赖脚本，越来越少地依赖 Prompt**
- **Harness Engineering 的核心：自由之前先立约束 → 信任之前先有反馈 → 百科全书之前先有索引 → 完美之前先有演化**

## 与我当前 Hermes 生态的关联

本文的 Harness Engineering 理念与当前 Hermes Agent + Skills + Memory 体系高度同频：

| Harness 概念 | 当前 Hermes 对应 |
|---|---|
| Rule | Hermes 的配置约束、系统提示词 |
| Skill | Hermes Skills（`skill_manage`/`skill_view`/`skills_list`） |
| Sub-Agent | Hermes OPC 模式（协调/研究员/写作者/构建者）+ `delegate_task` |
| Script | 本地脚本（`terminal` 工具）配合校验 |
| MCP | Hermes 原生 MCP 客户端（Firecrawl 等） |
| Dev-Map | Obsidian 知识库（技能文档索引） |
| Task Board | Task Board 规划方式 |
| 反馈回路 | 主校验脚本 → 基线 diff |

但本文在多个方面为当前 Hermes 提供了进一步迭代的方向：

- **结构化 Multi-Agent 编排**：OPC 模式 vs 本文的 7 角色接力赛模型，可借鉴 Gatekeeper 和角色契约机制
- **后置校验脚本**：目前缺少统一的 Master Validation Script 和基线对比机制
- **文档依赖图**：本文的工作流定义文件 + 角色契约 + 校验脚本的三层维护思路，可优化当前知识库的级联更新
- **内存 vs 工程产物的权衡**：本文"用 git 记录取代 AI 记忆"的思路值得在 TencentDB Memory 和 Obsidian 知识库之间做更清晰的职责划分
