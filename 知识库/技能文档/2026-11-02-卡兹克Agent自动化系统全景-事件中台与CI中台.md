# 折腾了整整1年，毫无保留地分享一下我这套 Agent 自动化系统

> 原文：数字生命卡兹克 · 2026-11-02
> **这篇是他开源前的母本。** 11-04 那篇《开源我这折腾了 1 年的 Agent 自动化系统》讲的是重写后开源的 **Agent-Autoloop** 这个项目；这一篇讲的是**他真实跑了一整年的完整系统**——包括开源版没有的部分：事件中台、CI 中台、双 Mac 本地部署、飞书批奏折、决策文件。

## 引子：朱元璋的注意力

开篇引 DeepSeek 技术文章《Super-agent 设计探索》里的一句：

> 「一个人通常只能同时跟进 3 到 5 个活跃的会话。在这种设计下，单任务的上限取决于模型能力，多任务的上限取决于人的注意力。」

作者接着讲了个历史故事：1380 年朱元璋借胡惟庸案废中书省和丞相，六部直通皇帝。洪武十七年九月，给事中张文辅报账——**八天，1,660 件奏札，3,000 多件待办，平均一天两百多份、一天要处理 400 多件事**。朱元璋自己绷不住了，说了句：

> 「朕一人处此多务，岂能一一周遍。」

**皇帝的注意力，跟普通人的，其实差不了多少。**

六百多年后，每个人都成了自己的皇帝，只不过递奏折的不是六部九卿，是一个个 Agent。**如何设计 Agent 的调度系统，解放自己的注意力、只做最关键的决策**——这个特质叫**领导力**。

## 1. Agent 自动化的核心认知

现在大部分人用 Agent 还是聊天方式：打开 Claude Code 或 Codex，给任务，看着它干，检查，再给下一个。

**弊端：所有事情的起点都是你。** 你只要不打开那个窗口，什么都不会发生。所以不管模型多强，你能同时推进的事，永远就是你盯得过来的那几个窗口。

> **要把任务发生的起点，从人的身上拿掉，用各种信号来触发 Agent 工作，而不是必须等待你下命令。**

想象你是朱元璋：不是所有任务都需要推到面前，也绝对不是你不说话底下就不干活——大臣遇见事情能自己处理的就处理掉，只有拿不准、必须上升到你这决策的，才会推到你面前。

**一个好的团队，从来不会什么事都跟你汇报。** 它会自行推进，只把需要你拍板的事拿给你，剩下自己去干掉，你需要的给与的是充分信任。

整套系统里，**作者唯一要做的事就是最后一步：批奏折。** 飞书里 AI 助理「小卡」弹一张卡片，点一下，Agent 收到决策继续干活。

## 2. 自动化中台：把「何时触发」变成一件可设计的事

### 事件是唯一的抽象

任何信号触发都可以归纳为一个**事件**：

- **定时任务** = 事件的搜寻行为（固定每分钟/每小时轮询去发现事件）。Claude 和 Codex 自己的应用里已经做得很好，作者也有一大批定时任务放在那边跑。
  - 实例：每天下午 Codex 从微信群聊记录、X、小红书、抖音搜大家对 **AIHOT** 的最新讨论和反馈，汇总成报告 + 可评估建议；每周操控浏览器去豆包、DeepSeek、千问、元宝、ChatGPT、Gemini 逐个问 GEO 问题，判断 AIHOT 的 GEO 情况；AIHOT 开源后，Claude 每天晚上 6 点扫一遍 GitHub 的 issue 和 PR 并处理。
- **Webhook** = 有事时那边系统主动推消息过来。**定时轮询天生不及时**——同事提了意见、线上突然报错，总不能等第二天早上。

### 为什么必须自建中台

事件来源五花八门（飞书消息、机器人、邮件、各种系统告警），每种长得都不一样；而且**不同模型擅长的任务不同，为了性价比和省 token，事件触发后要叫醒的 Agent、模型、推理深度也都不一样**：

- 某些事件 → **Claude Code + Claude Opus 5.5 high** 推理
- 某些事件 → **Codex + GPT-6.1 Terra xhigh** 去做浏览器搜索（拿正常拿不到的数据）
- 某些事件 → **GPT-6.1 Sol xhigh** 去修 BUG

> **每接一种事件就单独写一套脚本，做三五个还行，做到十几个、几十个，一定会乱成一锅粥。**

所以自建了一个很小的独立服务，部署在一台轻量服务器上，有自己的网址和数据库。**所有事件先发到这里，由它统一决定交给哪个 Agent、统一叫醒、统一把结果收回来，真需要决策时再通过飞书弹卡片。**

### 第一件事：统一事件格式

不管从哪来，发到中台的都是**一条很短的消息**：从哪来、什么类型、对象是谁、一句话摘要、一个回到原处的链接。

> 例：虚实中台发来 `feedback.new #12` = 同事给虚实中台又提了一条新意见，编号 #12。

### 第二件事：查规则（rules.json）

```json
{
  "name": "中台意见",
  "when": {
    "source": "virxact-hub",
    "types": ["feedback.new", "feedback.followup", "feedback.decided"]
  },
  "to": "m5-claude",
  "cwd": "~/code/work/virxact-hub",
  "skill": "hub-feedback",
  "ask": "按其中"被 Agent 自动化中台叫起来的"一节处理。",
  "group": "hub-feedback",
  "parallel": 3,
  "tell": "needed"
}
```

**翻译成人话**：产品新意见、同事补充、我拍过板的决定，都交给 M5 上的 Claude Code，在虚实中台代码目录里用 `hub-feedback` 这个 skill 处理；给 Agent 的指令就一句「按 skill 里对应的那一节办」；每条意见单独开一轮，同一条同时只跑一轮，**最多三条一起跑**；做完了**只在需要决策时才告诉我**。

### 第三件事：怎么叫醒内网里的 Mac

技术上有个小问题：Webhook 能把消息推到中台，**但中台推不到作者的 Mac**——两台 Mac 都在家里和办公室的内网里，外面根本连不进来。

> **反过来做**：每台 Mac 上跑一个**接单程序**，一直挂在中台上等活，**一次最长等 50 秒**，有活立刻接走，没活就再挂上去接着等。这样 Mac 不用暴露到公网，速度跟实时推送差不多。

### 中台带来的五件事

1. **接新事件特别简单** — 不用写新脚本，`rules.json` 加一条规则即可。跟 Agent 说一句，改完文件、过了检查，几分钟生效。
2. **换 Agent 特别简单** — 哪类事交给谁就是规则里的一行字。今天 Claude Opus 5.5，明天换 GPT-6.2 Astra，改一行。
3. **去重** — 自动化跑起来后同一件事被发好几遍是常态（网络抖一下来源以为没发出去、同事提完意见又补一句话贴一张图）。**每来一条就叫醒一次 Agent，同一件事会有好几个 Agent 同时在干，这个改一遍那个又改一遍，最后绝对乱得要死。**
4. **所有消息只有一个出口** — 不管哪个 Agent、哪个任务要找你，都只走「小卡」这一条路。每条规则写清楚**只在必须判断和决策时才说**，避免脚本发一条、机器人发一条把飞书刷屏，尽最大可能保护精力。
5. **数据沉淀** — 每件事都留底：什么时候来的、从哪来的、交给哪个 Agent、最后结论、有没有需要留意的、后来怎么解决的。点开任何一件任务能直接跳到当时 Agent 干活的会话。**攒久了哪条流水线最忙、哪个 Agent 干得最多、哪类事老出问题，一眼看出来**，以后换模型改规则有数据依据。

> 附赠一个「爽感」设计：作者做了个网页把流水线像种田游戏一样可视化展示，**跟现实世界时间和天气打通——现实下雪，自动化小镇里也下雪**。（视频 1:19，未转录）

## 3. Agent 执行：多模型调度 + 双 Mac 本地部署

### 前提：token 不是无限的

**即使开了 200 刀的 Claude 会员，猛用下来 3 天就能用完近 90%。** 且几个主流模型擅长的能力点确实不一样，所以才需要调度，为整体性价比最优。目前是 **200 刀 Claude + 100 刀 GPT**，基本够用。

| 模型 | 分工 |
|------|------|
| **Claude Opus 5.5** | **主力开发**。AIHOT 的自动化开发、同事对公司中台的意见这类复杂、需要主观能动性且能做决策的活。几个核心项目的大部分代码都是它写的 |
| **GPT-6.1 Sol** | **运维**。告警、每天早上的系统日报、各种到期复查；出问题去查，查到 BUG 或问题直接修。**这类活效果极好，性价比极高** |
| **GPT-6.1 Terra** | **浏览器 & 电脑操控**。直接操控 Mac Mini 上登录好各种账号的 Chrome，处理没有接口、正常拿不到的数据（全网舆情扫描、GEO 巡检） |

> **一条重要判断**：日常主动触发的任务用 Claude 处理。作者见过很多人用 Grok 或其他弱一点的模型来指挥 Claude——**"做决策和做管理的模型，一定得是智力和主动性最强的，你不能用笨逼来指挥聪明的，这样会乱套的。"**

### 为什么不上云

两台 Mac Mini：**M5 Pro**（主力日常用机）+ **M4 Mac Mini**（去年买的，**跑所有 Agent 自动化任务**），局域网互通，基本都在本地。

理由：

- 代码仓库、发布权限、飞书身份、登录好各种账号的 Chrome，**全在这两台 Mac 上**。放云上就得在每一家云复制一份登录和权限，既麻烦又不安全。
- **很多国内的东西海外云端 Agent 根本没法用**——跨境访问北京的服务器动不动就慢就超时；浏览器类任务更别说，像微信换到云上虚拟机浏览器直接崩。
- 两台 Mac 本来就是现成的，一直开着无所谓，**功耗极低**。

日常用 M5 Pro 操控 M4，直接 Agent 操控或 UU 远程。

### Skill：把任务 SOP 沉淀下来

**每个自动化任务基本都配一个专属 Skill**——本质是沉淀下来给 Agent 用的 SOP，附带规则、参考和脚本。

> 例：每周日早上的**大扫除定时任务**，配的 Skill 写的就是「把这一周合进来的屎山找出来删掉」——同一件事写了两遍的、为个案打的补丁、停用了却没拆干净的、变成流水账的文档，能删的直接删掉，再上线。

**好处是清晰、可控、可管理**：想改任务详情直接改 Skill，不用改 Agent 执行逻辑本身，尽可能解耦。

## 4. CI 中台：五步流水线

**Agent 的活干到「提交代码、开一个合并请求」就结束了，它自己不能上线。** 后面所有事全交给 CI 中台。

### 为什么自建

GitHub 自带 CI 每月会员也只有 3,000 分钟免费额度。**光 AIHOT 一个项目，10 月就合进了近 1,000 个合并请求，平均一天二三十个，每个还要来回跑好几遍检查。** 按 PR 数量算，用 GitHub CI 每月超额费用得交 **50 美金以上**。

所以在家里的老 M4 Mac Mini 上自建了一台 CI 中台：机器现成不用花钱、性能强得多、还在北京、跑得比 GitHub CI 快多了。

### 五步

| 步 | 内容 | 关键细节 |
|----|------|----------|
| **1. 审查** | **Claude 写的代码，合并前必须过 Codex（GPT-6.1 Sol）的审查** | 见下方详解 |
| **2. 检查** | 类型检查、全部测试、构建，还有**数据库只能加不能改**这类硬规矩，有一条不过就不能合 | 跑在 M4 Mac Mini 上，**每个任务开一台全新虚拟机，跑完连机器带身份一起删掉**。Agent 写的代码从来不会直接在 Mac 本机上跑 |
| **3. 合并** | 审查和检查都过了，GitHub 自动合并 | **这两项写死在 GitHub 规则上**：没审过、没检查过的代码，不管哪个 Agent、哪个工具，都合不进主干 |
| **4. 发布** | 合进主干后 GitHub 自动启动发布流程 | 派给 M4 单独开一台**专门发布的虚拟机** |
| **5. 核实** | M4 上的交付程序等 GitHub 发布流程全跑完，**再去线上问一遍：现在跑着的版本是不是已经包含了这次的改动** | 确认真的上线了，把结果写回 GitHub，这一轮才算结束 |

**五步走完，从 Agent 交代码到真正上线，中位数两三分钟**，全程不需要人管，上线的质量大大提高，几乎很难有 BUG 或返工。

### 第一步「Agent 审查」值得单说

**之前踩过坑：Codex 能无限审查和挑错，磨磨唧唧审 10 轮。** 后来学了 Anthropic 自己的文章《How the Claude Code team does code review》——**每个改动合并前都审一遍，但最多审 3 次。**

**最近两周实测：四个项目，298 个合并请求，Codex 报了 333 条问题，306 条在合并前被修掉，其中最严重那一档 51 条。**

审查的三条规矩：

1. **Codex 只读** — 只能看不能改，连不了网，读不到任何钥匙
2. **只报真会出错的问题，不报代码风格** — 否则它能挑几十条「可以写得更好」，打回去能改到天荒地老
3. **成本可控** — 一次审查中位数两分多钟，约占该次任务 5%–15% 的 token

> **这套设计可以整套复用到任何项目上**，作者说这是有了 CI 中台之后最省心的部分。

## 5. 在飞书上批奏折

### 票拟与批红

朱元璋的子孙慢慢摸索出了一套办法：**票拟**——奏章送上来先交内阁，大学士把建议处理意见写在小票上贴在奏章上；**批红**——皇帝看一眼，同意就用红笔批下去。

> **「我的决定卡片，就是 Agent 给我写的票拟。」** 人只做判断，点击即可，等着审批的 Agent 接着往下干，卡片自己改成结论。

真实案例：某晚某个「龟儿子」进了 AIHOT 的飞书群，把推送机器人移除了然后自己退群——作者都不知道还有这个漏洞，报错触发了整个自动化工作流，推了一条卡片过来。

### 什么事才配推到我面前

**之前踩过很多坑，有时候一天推几十条，严重影响注意力。** 现在必须先问的只有这几类：

> **删数据 · 停服 · 花钱 · 对外发消息 · 改产品方向 · 新建或轮换密钥 · 修改权限**

剩下的 Agent 自己全权做完上线。

### 两份决策文件

- **「卡兹克定的事」** — 仓库里一份文件，只记作者亲口做的决定，**带原话和日期**。定过的事 Agent 不会问第二遍。
- **「定了不做的事」** — 拒绝过的，Agent 以后再碰到直接照着回答，不会再拿来烦。

### 唯一不交给 Agent 的：用户反馈

**每一个都亲自看，然后把有价值的亲自发给 Agent 去做后续执行。** 用户反馈会复制粘贴给 Agent 解决，解决完给对方邮箱发一封真诚的回信。**「可能这也是最后的一种仪式感吧。」**

## 战略分析

### 这篇和 11-04 开源篇的关系：不是重复，是上下集

| 维度 | 11-02（本篇） | 11-04《Agent-Autoloop 开源》 |
|------|--------------|---------------------------|
| 讲什么 | **他真实跑了 1 年的完整系统** | **重写后开源的那个项目** |
| 事件层 | 自建事件中台（统一格式 + rules.json + 50 秒长轮询接单 + 五类去重/沉淀收益） | 内核收事件，插件化事件源 |
| 执行层 | 多模型调度（Opus 5.5 / Sol / Terra 分工）+ 双 Mac 本地部署 + Skill 解耦 | 内核派活给插件化 Agent（Claude Code / Codex / ACP / 通用命令） |
| 交付层 | **CI 中台五步**（审查→检查→合并→发布→核实），Codex 只读审查最多 3 轮 | `deliver` 标签→审码→等 CI→合并→等部署→核线上版本 |
| 人机接口 | 飞书卡片 + 票拟批红 + 两份决策文件 | 通道插件 + 「需拍板才找你」 |
| 心智模型 | 朱元璋 / 领导力 / 内阁票拟 | Pi 极简内核 + 「一切皆插件」 |

> **结论：11-04 是「他开源了什么」，11-02 是「他为什么这么设计、真实跑起来是什么样」。** 两篇互补，缺一篇理解都不完整。

### 对你（Hermes + Obsidian + 微信）最值钱的四条

**1. 「事件是唯一抽象」直接对应你的 cron + webhook**

你的栈里 cronjob 已经有（`cronjob_manage`），但缺的是**统一格式 + 规则路由**这一层。你现在是「一个定时任务一个 prompt」，加到十几个就开始记不清哪个任务干什么。规则文件（`rules.json` 那种：when → to → cwd → skill → tell）比散落的 cron 表达力强得多，而且**加新事件不用写代码**。

**2. 「50 秒长轮询接单，Mac 不暴露公网」是你现在的直接约束**

你的 Hermes 跑在这台 Mac 上，也是内网。任何「外部事件触发本地 Agent」的需求，正解不是端口映射，而是**让本地进程主动去拉**。这个设计能直接搬。

**3. 「必须先问的只有七类」这张清单值得抄成常设规则**

删数据 / 停服 / 花钱 / 对外发消息 / 改产品方向 / 新建轮换密钥 / 修改权限。**这七类是普适的，不分项目。** 抄进 memory 或某个 skill，比每次临场判断可靠。配套的两份决策文件（「定的事」带原话+日期 / 「定了不做的事」）解决的是**同一个问题不被问第二遍**——这也是你明确表达过的偏好。

**4. CI 五步里的「核实」这一步，绝大多数人漏掉**

不是「部署成功」，而是**部署完再去线上问一遍：跑着的版本是不是包含了这次改动**。你的 `deployment-ops` skill 里有 health check 和验证步骤，但「回查线上版本号是否含本次 commit」这个动作更硬。**Agent 说完成了 ≠ 完成了**，这和 NorthCUA 那篇「actor 完成 ≠ 评估通过」是同一个洞察。

### ⚠️ 泼冷水：这套系统有门槛，且门槛不在技术上

- **成本结构**：200 刀 Claude + 100 刀 GPT = **约 2,200 元/月**，且「猛用 3 天就消耗 90%」。这套系统的性价比建立在他有**百万月活的真实业务量**之上——每月近 1,000 个 PR 才撑得起自建 CI 中台。你的量级现在是「一天几篇归档」，**照搬整套是过度工程**。
- **「他踩过的坑」比「他的方案」更有价值**：Codex 无限审查磨 10 轮 → 学 Anthropic 限 3 轮；一天推几十条卡片 → 缩到七类；每接一种事件写一套脚本 → 做中台。**这些是他交了学费才收敛到的形状，直接抄形状比重新试探快，但不抄他的复杂度。**
- **全部数据都是作者单机自述**：298 PR / 333 条问题 / 306 条修掉 / 中位数两三分钟上线——没有第三方验证，也不清楚统计口径（比如「问题」怎么算一条）。当方法论看，不当 benchmark 看。
