## 概述

腾讯开源企业级 RAG 平台 WeKnora 的完整生产化纪实。作者把 WeKnora 二次开发成面向某垂直领域的"专家助手"并推上公网生产，按 RAG 流水线（解析→分块→检索→生成→增量→发布）逐一讲透了选型、十几轮对照实验调优、踩坑和最终配置。所有技术细节、配置参数、评测指标都是真实的工程记录。

## 一、整体架构：编辑台与服务台分离

核心设计原则：**编辑台（内网）与服务台（公网）物理分离**。

- **编辑台**：跑完整 WeKnora（docreader 解析器、向量库、知识图谱、Langfuse 可观测）
- **服务台**：只保留最小集合（前端、应用服务、PostgreSQL 向量+全文检索、Redis），**砍掉了解析器、知识图谱、可观测全套**

内容生产与内容服务彻底解耦：知识只在编辑台录入解析，通过 CI/CD 按文档粒度增量同步到服务台。服务台只读，唯一增长的数据是客户对话记录。

## 二、二次开发覆盖层：让定制不污染上游

### 复用 viewer 角色做客户模式

不新建角色（避免跟上游分叉），直接复用 `viewer（只读）`角色当"客户"。门控收敛到一个计算属性：

```
isCustomerMode = !isSystemAdmin && currentTenantRole === 'viewer'
```

**管理员零误伤**——系统管理员恒短路为 false，不论切到哪个租户。

### 覆盖层（overlay）设计

所有定制收敛到 `brand-overlay/` 目录 + 两个幂等脚本，四种手段按优先级使用：

1. **同名资产替换**（logo/favicon，零冲突）
2. **新增独立组件**（不动上游文件）
3. **设计变量覆盖**
4. **锚点补丁**——每段补丁带 marker（已存在跳过，幂等）和 anchor（定位点）。**上游改版导致 anchor 失配时立即 FAIL 报错**，而非静默失效。

升级流程：`git pull 上游 → 跑 apply-brand.sh → 重新构建前端镜像`

## 三、解析：材料切坏了，后面全白搭

按文档类型分层路由到不同解析引擎：

| 类型 | 引擎 | 关键点 |
|------|------|--------|
| PDF（原生文本） | PyMuPDF | 直接提取 |
| PDF（扫描件/图文） | **MinerU**（纯 CPU OCR） | 中文识别≈99%，表格完整还原，全面碾压 markitdown 和 RapidOCR |
| Excel（xlsx） | **自研 structured_table** | 填合并单元格 → 两级分块 → 每行带完整层级路径 → 两道质量守门（宁可不够好，绝不错乱） |
| Word/PPT | markitdown | 转 markdown 保留标题层级 |

**Excel 合并单元格教训**：不处理合并单元格时，顶层大类丢失 → 召回准确率掉 15~25 个百分点。修复后 chunk 自带完整分类路径（大分类：XX / 中分类：XX(0804) / 末级条目）。

## 四、分块：chunk 尺寸 + 标题面包屑

### chunk size：768 → 512

用长文档内部细节题实测（而非强术语单文档题），结论彻底翻转：

| chunk size | Recall@1 | MRR |
|------------|----------|-----|
| **512（新）** | **75%** | **0.844** |
| 768（原） | 0% | 0.335 |
| 1024 | 37% | 0.567 |

**教训**：早期"chunk 无差异"的结论是用错了测试题（强术语题有天花板效应）。

### 标题面包屑（ContextHeader）

改 WeKnora 分块器源码（0.6.2+ Go 实现），加 **6 级 markdown 标题追踪**：embedding 时把完整标题路径拼到正文前一起向量化，但存储/展示还是纯正文。

> embedding 的是"面包屑 + 正文"，召回时能借标题语境；落库/展示的是干净原文。这是索引阶段的语义增强，不是 prompt 技巧。

## 五、检索与召回：试错实录

### 翻车最佳实践

| 方法 | 结论 | 原因 |
|------|------|------|
| Contextual Retrieval（Anthropic） | **不采用**，R@1 75%→66% | 数据本身上下文完整，加标注反而稀释 |
| LLM 二次重排 +50 点 | **测量假象** | 只是忘了按 score 排序 |
| GraphRAG 自动图扩展 | **关掉** | 劫持向量召回，召回从全错恢复精准 |
| **Wiki 概念层** | **开，且权重很重** | 不是"提升向量召回"的工具，而是另一条互补的检索路由 |

### Wiki 的真正用法：hybrid-rag-wiki

实测 5 道题分析智能体检索行为：

- 4 道概念题 → 智能体全部重度走 wiki，答案几乎完全由 wiki 概念页成文
- 1 道精确取数题 → 先用 wiki 理解概念，再切回原文 chunk 取准确条文

**wiki 不是塞进向量召回的，而是作为独立概念路由让 Agent 按需调用。**

### 32K 上下文溢出修复

根因链：rerank 返回 top_k child → 被替换为 parent chunk → 重叠合并放大 → 10×6000 字 ≈ 30K tokens → 爆。

叠加 `enable_query_expansion` 跨 5 个查询变体复制 5 份 → 50 个 `<context>` 块瞬间撑爆。

修复组合拳：**关查询扩展 + rerank_top_k=5 + max_completion_tokens=4096 + 总字符预算上限兜底**。

### 最终生产配置

| 配置 | 值 |
|------|-----|
| chunk_size/overlap | **512 / 80** |
| 标题面包屑 | 开（6 级标题追踪） |
| embedding | **bge-m3**（1024 维）|
| embedding_top_k | 40 |
| rerank | **bge-reranker-v2-m3**（保持开启）|
| rerank_top_k | **5** |
| 对话模型 | DeepSeek-V4（早期 Qwen3.6-35B）|
| temperature | 0.3 |
| max_completion_tokens | **4096** |
| enable_query_expansion | **关** |
| kb_selection_mode | **selected**（只查本库）|
| agent 形态 | **hybrid-rag-wiki（smart-reasoning / ReAct）** |
| 自动图扩展 | **关** |

## 六、智能体：5 Agent → 1 Agent + 4 Skill

**第一代**：5 个独立 agent 各绑一个业务场景，全部 quick-answer（纯单步 RAG）——被动妥协，因为 smart-reasoning 会爆 32K。

**第二代**：收敛成 **1 个总 Agent + 4 个 Skill**，hybrid-rag-wiki 形态。靠 ReAct 渐进式披露在 wiki（概念）和 chunk（精确取数）间自动分流。

A/B 实测：
- 关键点命中率：smart-reasoning **97%** vs quick-answer 59%
- 黄金文档召回：65% vs 57%

**Skill 机制**：本质是 `SKILL.md` 文件（YAML header + 结构化方法论），触发不是关键词路由，而是 LLM 渐进式披露。

### 防幻觉四原则（高风险领域必备）

1. 只引用检索到的实际内容，绝不用训练数据补全
2. 严禁编造任何统计数字
3. 实体名严格限定于召回片段出现的内容
4. 承认未知——不用"通常""一般来说"兜底

效果：某题修复前模型编了十几条假数据（3261 字）→ 修复后 789 字、诚实告知"信息不完整"。

### 防指令注入

**显式指令边界防御段**——6 类攻击各 5 次（共 30 次）**100% 防住**，从概率性防御变成确定性防御。

## 七、评测尺子

迭代四代，最终稳定方案：
- **22 道 golden_set**：每道题标注唯一命中子串，可审计可自动判 Recall@K
- **多跑取均值**：难题检索随机性大（rank 1↔99），必须多跑
- **LLM-judge 三维打分**：忠实度（groundedness，防幻觉）+ 正确完整性 + 检索相关性

**三条铁律**：① 难题必须多跑；② 消费 references 必须先按 score 降序排；③ 任何调参不以"这 22 题涨分"为目标（防过拟合）。

**经典案例**：一道分级判定题，二元关键词判定 8/8 全过，但 LLM-judge 揪出其中一题忠实度仅 2 分——答案给了不存在的支撑。**关键词命中 ≠ 答对**。

## 八、增量更新：企业 RAG 最难的不是召回率

文档稳定身份：`doc_id`（这是谁）+ `source_hash`（变没变）。

增量更新状态机：内容判断 → 删旧 chunk → 写新 chunk → 更新业务表，配 `SYNCING / READY / FAILED` 状态。

**反直觉行为**：
1. "同步删除"勾选了也基本是 no-op——宁可漏留也不误删
2. 首次同步游标为空，增量自动降级成全量

> RAG 表面上是"检索增强生成"，本质上是 **知识数据工程**。增量更新和传统 CDC、版本治理、快照管理是同一类问题。

## 九、CI/CD：双轨发布

**Track A（代码镜像）**：git push → 构建 dist + docker → 部署 → 验 /health。保留上一版本用于回滚。

**Track B（知识内容同步/bundle-CDC）**：由于服务台近乎"气隙"（只能传文件，不能有常驻连接），走了 bundle-CDC：
- 水位 watermark（`updated_at` 单调递增）
- 内容哈希（抖了但内容没变就跳过）
- 幂等灌入（`ON CONFLICT DO UPDATE`，重复结果一样）
- 软删必须（物理 DELETE 水位看不到，退化为一次 update）

**删除是唯一的坎**：物理 DELETE 后行就没了 → 服务台永久残留。所以必须软删（`deleted_at=now()`）。

**文档为原子单位、chunks 整组替换**：向量在 PG 行内，binary COPY 精确搬 float、不重算。

## 十、效果与成本

### before → after 关键改动

| 改动 | 指标 | before | after |
|------|------|--------|-------|
| chunk 768→512 | 细节题 Recall@1 | 0% | **75%** |
| 按 score 排序 | MRR | 0.67 | **0.87** |
| quick→smart-reasoning | 关键点命中率 | 59% | **97%** |
| 防注入指令边界 | 30次攻击防御 | 概率性 | **100%** |

### 最终上线指标
- Recall@5 ≈ **0.81** · MRR ≈ **0.87**
- 关键点命中率 ≈ **97%** · 编造引用 chunk_id **0/11**
- 单查询 ≈ **62 秒**（瓶颈在生成端自回归，非检索）

### 诚实的边界
1. **大规模聚合题是软肋**（跨 31 地区统计对比，纯向量只覆盖 ~16%）
2. **中文关键词检索偏弱**（PG 全文检索没有中文分词）
3. **多版本文档是向量的天生软肋**（文本 99% 雷同，向量分全在 0.97~0.99）

### 成本结构

| 阶段 | 成本 | 性质 |
|------|------|------|
| 解析（PDF/Excel） | 纯 CPU，几乎零 LLM 成本 | 一次性 |
| 分块+向量化 | 一次 embedding（轻） | 一次性 |
| **wiki 编译** | 3 分钟/篇，四百多篇 ≈ 22 小时 | 离线异步 |
| **图谱抽取** | **最重——每 chunk 一次 LLM，6 万次调用** | 离线 **且已沉没** |
| 线上推理 | ≈ 7.4K token/查询 | 按次计费 |

**最扎心**：图谱抽取那 6 万次调用最后是沉没成本——在检索阶段自动图扩展被关掉了，图谱只作为离线关系资产保留。**别在没验证图谱对检索的正收益前，就全量跑图谱抽取。**

## 八条方法论

1. RAG 是检索工程问题，不是模型问题
2. 业界"最佳实践"必须在自己数据上+对的智能体模式下验证
3. 连自己的实验结论也要回查测量口径
4. 没有稳定的尺子，调优就是玄学
5. 材料切坏了，后面全白搭
6. 企业 RAG 最难的不是召回率，是别让知识库越用越脏
7. 二开要对升级友好（覆盖层+幂等补丁+anchor 失配 FAIL）
8. 编辑台和服务台分离

## 战略分析

### 与知识库体系的对照

| 维度 | 本文方案 | 当前知识库体系 |
|------|---------|---------------|
| RAG 平台 | WeKnora（腾讯开源）| Obsidian wiki + Hermes Agent |
| 检索策略 | hybrid-rag-wiki（向量+全文+wiki 概念路由） | 基于文件系统的 wiki 链接引用 |
| 分块策略 | 512/80 + 标题面包屑 + bge-m3 | 无结构化分块 |
| 评测体系 | 22 题 golden_set + LLM-judge 三维打分 | 无 |
| 增量更新 | bundle-CDC（水位+哈希+幂等）| 手动归档 |
| 二开策略 | 覆盖层 overlay + 锚点补丁 | skill 系统（新建不修改） |
| 生产化 | 编辑/服务分离 + 双轨 CI/CD | 无 |

### 可直接借鉴的工程模式

1. **编辑/服务分离**——内容生产与内容服务解耦，非常适合上述知识库体系的扩展方向
2. **覆盖层 overlay 模式**——"四种手段优先级"+ 锚点失配立即 FAIL，是与 Hermes skill "宁建新不改旧"异曲同工的工程防护
3. **标题面包屑（ContextHeader）**——将标题路径拼入 embedding 的索引增强策略，可独立于任何 RAG 平台实现
4. **bundle-CDC**——气隙环境下的增量同步方案，如果未来知识库需要从单一机器扩展到多节点，可直接复用
5. **防幻觉四原则 + 指令防御段**——任何 Agent 输出场景都应内置的 prompt 防护

### 差距与启发

- 当前知识库体系缺乏系统化的 **评测尺子**（golden_set + LLM-judge）。文中评测方法论（多跑取均值、消费 references 先排 score、防过拟合）可直接迁移
- chunk 调优（512/80 + ContextHeader）对 wiki 级文档同样适用——归档的公众号长文如果未来需要 RAG 化，分块策略可直接参考
- **"最贵的一步关了"的教训**——验证后再全量，这条原则适用于任何新能力的引入
