## 1. 一句话定位

**Raven = 「Harness 的 Harness」**。它自己不是最强的 Agent，它的野心是**当所有 Agent 的总调度**：把 Claude Code、Codex、Hermes Agent、OpenClaw 这些独立开发的 Agent 注册进来，当成 DAG 里的**节点**，由其 Host Agent 拆解目标、匹配子任务、协调依赖、整合结果。

官方一句话：**"One Surface, All Agents."**

## 3. 架构：它到底怎么"管"

### 3.1 Host Agent + 可组合单元

核心抽象（论文原文）：**把每个「可执行的 模型–harness 配对」当作智能的组合单元**（each executable model–harness pair as a composable unit of intelligence）。

流程：
1. **Host Agent** 接收目标 → 生成 **DAG**（有向无环图）子任务图
2. 每个节点匹配一个**专用 Agent**（内置专家或第三方）
3. 按依赖调度执行，依赖成环/缺失时触发**异常上抛**
4. 整合结果成最终交付物

### 3.2 四个内置专家

| Agent | 职责 |
|---|---|
| **Raven-Research** | 自主深度研究、文献综述、技术分析，输出带可溯源引用的结构化报告 |
| **Raven-Code** | Agentic 软件开发：功能实现、调试、重构、数据处理与分析 |
| **Raven-Design** | 视觉设计：PPT、品牌资产、图表、图示意图、Web 界面 |
| **Raven-Oncall** | 无人值守工作流自动化、巡检 |

### 3.3 通过 ACP 接入第三方

配置预设可接 **Claude Code、Codex、OpenCode、Hermes Agent、OpenClaw**，通过 **ACP（Agent Client Protocol）**统一接口。**执行适配器保留各 Agent 自己的工具和内部执行策略**——不是把它们阉割成统一形态，而是保留原生能力再对接调度层。

**这一点很关键**：Raven 的定位不是替代这些 Agent，而是**在它们之上加一层编排**。

### 3.4 记忆与自进化：EverOS + Skill Forge + Raven Evolver

- **EverOS**：跨会话携带记忆与上下文（独立项目 `EverMind-AI/EverOS`）
- **host archive**：保留跨任务经验
- **Skill Forge**：把经验转化为**可复用过程**
- **Raven Evolver**：**独立工具**，把 Raven 当库调用，对候选 harness 变更跑 benchmark 评估——**它在 Agent 之外开发 Agent，不运行在 Agent 内部**

Raven 明确说自己是为 **RSI（recursive self-improvement，递归自我改进）** 而生。

## 4. 核心跑分：MAOB 基准（论文实测）

它自己造了个基准 **MAOB（Multi-Agent Orchestration Benchmark）**：

- **140 个请求**，取材 137 个不同职业、140 个模板
- 每个请求配一张**参考 DAG**（固定 4 个专家子 Agent 的 roster）
- 平均 **2.72 节点 / 1.84 边**，共 257 条参考边
- 四个指标：**Node F1**（选对专家）、**Edge F1**（连对依赖）、**POA**（偏序准确率）、**Exact Match Rate**（整图完全一致）
- **只测规划，不派发 worker**——提交的图被截获评分，不实际执行

### 实验结果（Qwen3.8-27B 为 backbone）

| 指标 | Raven | 最强基线 | 差距 |
|---|---|---|---|
| **Node F1** | **0.923** | **0.776** | +14.7 pt |
| POA | 0.950 | — | — |
| **Exact Match** | **0.711** | **0.607** | +10.4 pt |
| Edge F1 | — | — | **+0.068** |

### 实验结果（DeepSeek-V4-Flash-0731 为 backbone）

| 指标 | Raven |
|---|---|
| Node F1 | **0.963** |
| Edge F1 | **0.897** |
| Exact Match | **0.867**（基线 0.762，+10.5 pt） |

**三个系统在相同 backbone、相同 140 题、相同协议下对比，且要求三者都跑过才上报结果。** 这个设置是规范的。

### 基准设计的严谨处（值得单独记）

- **Elicitation Parity（提示对齐）**：三个系统收到**逐字相同**的请求文本和委派指令，领域描述**只通过各自的编排工具 schema 提供**，不加额外系统级 preamble。→ 控制住了"给谁的提示更好"这个混杂变量
- **两个 backbone 交叉验证**：不同模型家族上都领先，且**基线的相对排名会变**（Qwen 下 Hermes 领先 Claude Code，DeepSeek 下 POA 反过来）——**Raven 在排名变动中仍稳居第一**，这比单模型单次结果可信得多
- **四项指标不合并成单一分数**

## 8. 战略分析

### 8.1 「Harness of Harnesses」这个词组的真实含义

Raven 的论文标题和核心命题，是把问题从 **"如何为一个领域造更强的 harness"** 转成 **"如何自动构造专用 harness、通过经验改进它们、并跨领域编排它们"**。

这是**抽象层级的上升**，不是能力提升。类比：
- Claude Code / Codex 是**执行者**
- 各种 Harness（AutoResearch 的 LOOP、阿里的 LongHorizon、Orca 的 worktree 编排）是**一个领域的组织方式**
- **Raven 想当"组织方式的调度器"**

**它的赌注是：Agent 的数量会爆炸，以至于"谁来调度"本身会成为独立且更有价值的一层。** 这和自动化的历史规律一致——但风险也在这里：**如果上游 Agent 自己开始内置编排能力（Claude Code 已在做 subagent），中间层的存在理由就会被侵蚀。**

### 8.2 它真正稀缺的东西，是「可验证的失败」

Raven RSI 那个案例值得多看两遍：**172 次训练零崩溃**。

这个数字背后的工程难度不在"能跑"，而在**连续 7 轮、172 次实验没有一次把环境搞死**。自进化系统最常见的死法就是：某一轮改坏了 harness，之后所有轮次都在错误基础上继续，最后产出一堆看起来合理实则无意义的数字。

Raven 的解法是论文里那句关键设计：**评估标准不可修改**（"evaluation criteria it cannot modify"）。**它把裁判权从被优化对象手里拿走了。** 这和昨天 AutoResearch 的"以可解释性作为入库门槛"是同一思路的两种实现——**给自进化系统装一个它自己动不了的刹车。**

### 8.3 三个我判断它可能出问题的地方

1. **MAOB 是自己造的基准。** 140 题、参考 DAG 由自己标注、且只测规划。**规划图漂亮 ≠ 任务完成**。README 用三个 showcase 补这个缺口，但 showcase 是挑选过的。
2. **pre-alpha + 5,580 星 + 82 issues。** 现在用它做生产编排，等于把 orchestration 层建在一个会快速变动的接口上。**Raven 的接口变更会直接传导到你的整个工作流**——这是把所有鸡蛋放进一个 pre-alpha 篮子。
3. **它依赖上游 Agent 的接口稳定性。** 通过 ACP 接 Claude Code / Codex / Hermes，任何一个上游改协议，Raven 的适配器就可能断。**这层脆性不在 Raven 的掌控范围。**

### 8.4 值得注意的身份重叠

**Raven 用自己写了这份 README，并且用自己做了产品发布套件。** 这在展示能力上是加分的，但在**信息可信度上是减分的**——它的所有对外材料都经过"最会推销自己的那个系统"的加工。今天早上那篇阿里的 zg 文章是"AI 生成营销物料"，Raven 的 README 是"自进化 Agent 生成的营销物料"，**两者的核查待遇应该一样：只信仓库和论文里的可验证部分，不信文案。**

## 9. 对你的可用结论

### 9.1 现在别装，但值得盯

理由：
- **pre-alpha** 接口会快速变（README 自己说的）
- **5,580 星、5 个月、82 open issues**——工程成熟度不够
- 你的工作流已经跑在 Hermes 上，**再套一层 pre-alpha 编排器，故障域从 1 个变成 2 个**
- 但你今天归档的 Orca（10 万星）解决的是**编码 Agent 并行**，Raven 解决的是**跨领域 Agent 编排**——**它们不冲突，是两个不同层级**

### 9.2 真正值得你现在抄的三点

1. **"evaluation criteria it cannot modify"** —— 给任何自进化/自动优化系统，**裁判权必须独立于被优化对象**。这个原则可以直接用在你设计 Hermes 的 cron/自动化任务上：**验证逻辑不能放在被验证的那段逻辑里。**
2. **双 backbone 交叉验证 + 报告"基线排名会变"** —— 这是做任何 A/B 评估的范本：**别只在一个模型上跑一次就下结论，且要主动汇报不一致的地方。** 论文主动写"基线排名在换 backbone 后翻转"这种不利信息，反而增加了可信度。
3. **异常上抛机制（Exception Resolution）** —— 节点失败时发结构化报告：**哪个节点、哪个 agent、缺了什么条件、证据是什么、阻塞了哪些下游、还剩几次尝试、决策截止时间**，并附上可直接调用的解决工具。这个"失败报告 = 完整决策包"的设计，比单纯的 retry 高明一个层级。**可以直接借到 Hermes 的 delegate_task 失败处理上。**

### 9.3 与今天前三篇的关系

今天四篇（Quarkus / AutoResearch / Orca / zg）我已经指出同一收敛点：**用一次性预处理换运行时确定性**。Raven 是**第五个，而且它换的是"裁判权"**：

- Quarkus：把反射挪到构建期
- AutoResearch：把已证伪方向写进状态文件
- Orca：把会话状态挪进 daemon
- zg：把索引挪到事前
- **Raven：把评估标准挪到被优化对象之外**

**前四个都是"把不确定性前置"，Raven 是唯一一个"把不确定性交出去"**——交给一个不可修改的外部裁判。这在逻辑上更彻底。

### 9.4 一条给知识库的判断线

今天归档的五个东西，可以排成一个清晰的层级：

| 层级 | 代表 | 解决什么 |
|---|---|---|
| 执行 | Claude Code / Codex | 单个任务怎么干 |
| **并行** | **Orca** | 多个任务怎么同时干 |
| 领域内编排 | AutoResearch LOOP / LongHorizon | 一个领域内的任务图 |
| **跨领域编排** | **Raven** | 多个 Agent/领域怎么被统一调度 |
| 检索供给 | zg | 编排时去哪找证据 |

**这张图比任何单篇文章都有用**——它解释了为什么这五个项目看起来都在做"Agent 编排"却互不冲突。
